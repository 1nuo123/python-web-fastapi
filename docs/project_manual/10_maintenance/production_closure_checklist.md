## 3. 状态口径

### 3.1 缺陷状态与证据状态分离

- `open`：当前仍可触发，或缺少根因修复/当前影响面回归。P0/P1 `open` 必须阻断合并和发布。
- `fixed`：根因已经修复，当前定向及影响面回归已经通过，但旧版本失败复现或远端证据不完整。
- `verified`：除 `fixed` 条件外，还具备可信旧版本失败复现和完整晋升证据。
- `rejected`：经证据判定不成立或路线被淘汰，必须保留原因。

当前 13 个 P1 `fixed` 不可因缺少旧版历史自动降回 `open`。只有出现当前基线失败、真实可达触发路径或修复回退证据时，才允许重新打开。

### 3.2 阻断等级

| 等级 | 阻断条件 | 动作 |
| --- | --- | --- |
| P0 | 数据不可逆损坏、认证完全绕过、密钥大规模泄漏、系统主链路不可用 | 立即停止写入/发布，回滚或隔离，根因修复后全量验证 |
| P1 | 关键业务错误、越权、安全 fail-open、事务/任务一致性破坏、生产启动失败、确定性资源泄漏 | 阻断合并/发布，补最小复现、根因修复和影响面回归 |
| P2 | 有明确影响但存在可靠规避，未破坏关键正确性 | 可进入当前迭代，指定责任人与验收条件 |
| P3 | 文档、历史证据、远端留痕、非阻断 warning 或优化项 | 跟踪处理，不得冒充 P0/P1 重启全量整改 |

## 6. 停止循环规则

从本文件生效后，7 月 13 日系列方案转为历史审计资料，不再作为循环生成新清单的入口。当前维护入口固定为本清单、项目手册和可执行质量门禁。

禁止以下行为：

- 不得仅因 `fixed` 未晋升 `verified` 再次全量扫描或改写修复。
- 不得因同一基线重复运行产生新时间戳而声称质量提高。
- 不得把第三方 warning、缺少远端 URL、未来业务性能未知升级为当前 P0/P1。
- 不得在没有失败证据时继续重构已通过的基础设施。
- 不得通过扩大 ignore、降低覆盖率、增加 skip/xfail 或删除断言维持绿色。

只在以下触发器出现时重新打开对应范围：

1. 发生可复现测试失败、运行时异常、数据不一致、安全事件或资源泄漏。
2. 修改公共 HTTP 契约、配置键、迁移、消息协议或阶段证据契约。
3. 修改 auth/security/task/persistence、事务、并发、生命周期或 fail-closed 主链路。
4. 升级直接依赖、基础镜像、Python、PostgreSQL、Redis、RabbitMQ 或部署平台。
5. 静态、安全、覆盖率、真实依赖、镜像或文档门禁失败。

重新打开时只审查触发器影响面；除非出现跨模块公共契约变化或多个独立 P1，禁止自动扩大为整个工作区全量审查。
