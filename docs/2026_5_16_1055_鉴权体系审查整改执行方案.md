# 鉴权体系审查整改执行方案

## 任务目标
最终要交付一套基于现有 PostgreSQL 鉴权基建的整改落地方案，补齐会话吊销闭环、授权接入、安全加固与回归测试，使当前鉴权体系在可用性、可维护性、可扩展性、安全性上达到“可上线维护”的工程基线。

完成判定是：
- `/auth/revoke` 对应的会话吊销语义闭环成立，旧 access token 不再可继续访问受保护接口。
- 现有角色与 scope 从“仅存储”升级为“真实生效”。
- 登录与刷新链路补齐必要的轻量安全治理与维护性修复。
- 代码、测试、配置样例与文档保持一致；若文档与源码冲突，以源码为准，并标记文档可能过期。

## 全局约束
- 严格遵守 `docs/standard/编码规范.md`、`docs/standard/命名规范.md`、`docs/standard/测试规范.md`。
- 以当前源码为准，不为过期测试或旧文档回退实现。
- 保持现有分层边界：`core / application / infrastructure / api`，禁止将授权判断散落到路由细节中。
- 保持现有统一响应与异常风格，继续使用 `ResponseEnvelope`、既有错误码体系、既有日志方案，日志/异常/注释统一使用中文。
- 禁止弱类型扩展：稳定结构使用 `BaseModel`、`dataclass`、`TypedDict`；禁止 `dict[str, Any]`、`metadata`、`extra_payload`。
- 契约统一采用“公共头字段 + 强类型扩展字段”模式；扩展字段使用 Pydantic 判别联合；扩展模型必须包含 `kind`、`schema_version`，并启用 `extra="forbid"`；外层类型与内层扩展类型必须一致。
- 禁止无边界复杂化。本次整改优先复用现有 `JWT`、`CacheStore`、`UnitOfWork`、`Repository`、`AuthorizationPolicyEvaluator` 能力，避免引入新的重型鉴权框架。
- 固定值、公共字段、错误码、策略名必须收敛为常量或枚举，禁止新增魔法字符串与魔法数字。

## 验收标准
- 被吊销会话中的旧 access token 访问受保护接口时稳定返回鉴权失败，不再依赖自然过期。
- 受保护入口能够基于角色与 scope 返回稳定的授权结果，缺少权限时返回明确的 403 语义。
- 认证中间件不再为每次请求加载完整身份聚合，而是优先使用 JWT 恢复主体，仅做必要的主体状态与会话状态校验。
- 登录成功后可按当前算法策略完成密码重哈希回写；bootstrap 管理员不再每次启动无条件重写密码哈希。
- `/auth/token`、`/auth/refresh` 具备轻量失败频控或短时锁定能力，Bearer 头解析兼容大小写差异。
- 单元、路径、初始化、契约、接口、异常、边界、集成、用法规约测试全部通过，且资源正确回收。
- 配置样例、设计说明、接口契约示例与最终源码一致。

## Phase 1
### 目标
修复当前“认证已通、会话吊销不闭环”的直接问题，建立稳定的 access token 会话校验链路，并将认证中间件从“每次请求加载完整身份”收敛为“JWT 恢复主体 + 轻量状态校验”。

当前阶段完成后的中间结果是：
- `/auth/revoke` 与 access token 校验的会话语义一致。
- 旧 access token 在会话被吊销后立即失效。
- 认证中间件只查询必要状态，不再每次拼装完整角色与 scope 聚合。

### 依赖
- 依赖现有 `JWT` 中已写入的 `token_session_id`。
- 依赖现有 `RefreshTokenRepository`、`AuthIdentityRepository`、`UnitOfWork`、`AuthenticationBindingMiddleware`。
- 依赖现有 `auth_refresh_token` 表与相关索引；若文档描述与当前表结构不一致，以源码与迁移结果为准。

### 模拟用法
```http
POST /auth/revoke
Content-Type: application/json

{
  "refresh_token": "<refresh-token>"
}
```

```http
GET /auth/me
Authorization: Bearer <old-access-token>
```

```json
{
  "data": {
    "kind": "http_fault",
    "error_code": "auth.token.revoked"
  }
}
```

### 契约
| 英文名 | 中文名 | 中文说明 |
|---|---|---|
| TokenPayload | 令牌载荷 | 继续作为 JWT 强类型载荷，明确 `token_session_id` 是 access/refresh 共享的会话标识，保留 `kind`、`schema_version` 与 `extra="forbid"`。 |
| TokenSessionStatusPayload | 会话状态载荷 | 新增强类型会话状态模型，描述 `token_session_id`、主体标识、吊销状态、吊销时间等最小必要字段，用于中间件校验。 |
| AuthIdentityStatusPayload | 主体状态载荷 | 新增轻量主体状态模型，仅承载 `subject_id`、`is_active` 等认证必要状态，避免每次请求查询完整身份聚合。 |

### 任务清单
- [x] 明确 `/auth/revoke` 的源码语义为“按 `token_session_id` 吊销整个登录会话”，不回退为“仅禁用 refresh token”。
- [x] 扩展 `RefreshTokenRepository` 契约与实现，补充按 `token_session_id` 读取会话状态的能力。
- [x] 扩展 `AuthIdentityRepository` 契约与实现，补充按 `subject_id` 读取轻量主体状态的能力。
- [x] 调整 `AuthenticationBindingMiddleware`，先用 JWT 恢复主体，再校验主体启用状态与会话未吊销状态。
- [x] 统一 access token 因会话吊销而失败时的错误码、异常语义与中文日志。
- [x] 将 Bearer 解析改为大小写不敏感，避免合法客户端因头部大小写差异被拒绝。

```python
class TokenSessionStatusPayload(BaseModel):
    model_config = ConfigDict(extra="forbid")

    kind: Literal["token_session_status"] = "token_session_status"
    schema_version: Literal["1.0"] = "1.0"
    token_session_id: str
    subject_id: str
    is_revoked: bool
    revoked_at_epoch: int | None
```

```python
token_payload = token_service.decode_token(token, expected_use=TokenUse.ACCESS)
principal = token_service.build_principal(token_payload)
```

### 校验
- 使用已吊销会话中的旧 access token 访问 `/auth/me` 时，返回稳定鉴权失败。
- 认证中间件可直接从 JWT 恢复主体，不再依赖每请求查询完整角色与 scope 集合。
- Bearer、`bearer`、`BEARER` 三种头前缀均可被正确解析。

## Phase 2
### 目标
修复当前“授权模型存在但未接入业务入口”的直接问题，建立统一的路由级授权断言入口，让角色与 scope 真正参与访问控制。

当前阶段完成后的中间结果是：
- 授权不再停留在 `AuthorizationPolicyEvaluator` 单体能力。
- 受保护入口可稳定基于角色与 scope 返回 403。
- 授权判断收敛到统一入口，避免路由散落 if/else 判断。

### 依赖
- 依赖 Phase 1 已完成的稳定主体恢复与会话校验。
- 依赖现有 `AuthorizationPolicy`、`AuthorizationPolicyEvaluator`、`DependencyContextAccessor`、`ResponseEnvelope`。
- 依赖源码中现有受保护 HTTP 入口；若旧文档仍描述“仅认证不授权”，视为文档过期。

### 模拟用法
```python
policy = AuthorizationPolicy(
    required_scopes=["system:read"],
    required_roles=["admin"],
)
```

### 契约
| 英文名 | 中文名 | 中文说明 |
|---|---|---|
| AuthorizationPolicy | 授权策略 | 继续作为角色与 scope 的统一策略契约，固定 `required_scopes`、`required_roles`，并保持强类型与 `extra="forbid"`。 |
| AuthorizationDecision | 授权结果 | 继续作为授权判定结果，承载 `allowed` 与稳定原因文本，用于统一转译为 403 异常。 |
| RouteAuthorizationRequirement | 路由授权要求 | 新增路由级授权要求模型，作为路由接入授权的统一扩展体，包含 `kind`、`schema_version` 与绑定策略信息。 |

### 任务清单
- [x] 新增统一授权守卫对象，作为路由层唯一授权断言入口。
- [x] 将 `AuthorizationPolicyEvaluator` 接入实际 HTTP 入口，至少覆盖当前已需要受保护的读取与受限动作接口。
- [x] 在 `DependencyContextAccessor` 中补齐读取主体、触发授权断言、转译授权失败的统一调用路径。
- [x] 统一角色缺失、scope 缺失时的 403 错误码与中文错误消息。
- [x] 禁止在路由函数中散落字符串式角色/权限判断，统一收敛为策略对象。

### 关键代码片段
```python
decision = authorization_policy_evaluator.evaluate(principal, policy)
if not decision.allowed:
    raise HttpFaultException(
        status_code=HTTPStatus.FORBIDDEN,
        error_code=AuthErrorCode.ACCESS_FORBIDDEN,
        message=decision.reason or "当前主体无权访问。",
    )
```

### 校验
- 缺少所需 scope 的主体访问受保护接口时，稳定返回 403。
- 缺少所需 role 的主体访问受保护接口时，稳定返回 403。
- 授权入口只存在一套调用路径，不在路由中出现重复的权限判断实现。

## Phase 3
### 目标
修复当前“安全治理与维护性不足”的直接问题，补齐密码重哈希落地、登录/刷新轻量频控、bootstrap 启动行为与兼容性问题。

当前阶段完成后的中间结果是：
- 密码算法升级能力从“只存在方法”变成“真实可生效”。
- 登录与刷新具备轻量失败治理，不引入过重复杂度。
- bootstrap 管理员行为更可控，不再每次启动无条件重写密码哈希。

### 依赖

- 依赖现有 `PasswordHasher`、`CacheStore`、`SharedResourceMount`、`BootstrapAdminSettings`、鉴权配置加载器。
- 依赖现有缓存后端装配；若测试环境仅使用内存缓存，以当前源码配置为准。
