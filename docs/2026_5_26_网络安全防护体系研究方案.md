## 1. 目标定位

本方案用于当前 FastAPI 基础设施项目的后续快速开发交付。目标不是一次性建设完整企业级安全平台，而是在现有鉴权、缓存、日志和中间件基础上，补齐一套轻量、可扩展、能快速接单落地的网络安全防护规格。

本阶段重点只做三件事：

- 统一风控与流控入口。
- 补齐常见 Web/API 防护。
- 形成可审计、可测试、可后续扩展的安全事件链路。

## 2. 当前代码审查结论

当前项目已经具备以下基础能力：

- JWT Bearer 认证、issuer/audience 校验、access/refresh token 用途校验。
- refresh token rotation，发现 refresh token 重复使用时撤销 token session。
- 认证失败节流，登录和刷新令牌失败会进入缓存计数与锁定。
- 请求体大小保护，支持 `Content-Length` 预检和流式累计读取。
- 安全响应头，生产环境可启用 HSTS 和 CSP。
- 生产安全配置校验，禁止生产环境继续使用开发密钥、内存认证节流和 bootstrap admin。
- 日志脱敏，覆盖 Bearer、JWT、URL 凭据和 password/token/secret 键值。

历史主要缺口当前状态：

- 统一风控/流控入口、通用 `RateLimitMiddleware`、安全事件契约、SSRF 防护和部署边界文档已落地。
- 项目仍不内置完整 WAF、SIEM、外部 KMS/HSM、依赖漏洞扫描平台或 DAST 平台；这些能力保留为部署侧或后续治理项。

## 3. 统一风控流控设计

### 3.1 设计原则

风控和流控统一接入，但职责分开：

- 流控负责判断“多不多”：请求频率、并发压力、失败次数、资源消耗。
- 风控负责判断“险不险”：异常登录、令牌复用、敏感操作异常、疑似扫描或撞库。
- 两者统一输出安全决策和安全事件，便于日志、告警和后续扩展。

### 3.2 统一入口

当前已新增轻量安全防护门面：

```text
SecurityProtectionGuard
  - RateLimitGuard
  - AuthThrottleGuard
  - RiskSignalGuard
  - SecurityEventBuilder
```

当前实现不引入复杂规则引擎，采用规则枚举、计数器和运行时策略配置。

统一决策结果：

```text
allow
deny
throttle
record_only
```

统一处置动作：

```text
pass
return_401
return_403
return_413
return_429
revoke_token_session
emit_security_event
```

## 4. 轻量防护范围

### 4.1 通用 API 流控

新增 `RateLimitMiddleware`，覆盖所有 HTTP 请求。

建议第一版支持：

- 按 IP 限流。
- 按已认证 subject 限流。
- 按 path + method 限流。
- 对 `/auth/token`、`/auth/refresh` 提供更严格策略。
- Redis 不可用时沿用 `rate_limit` fail-closed。
- 超限返回 429，并带 `Retry-After`。

默认策略建议：

```text
global: 120 requests / minute / ip
auth_token: 10 requests / 5 minutes / username_or_ip
auth_refresh: 20 requests / 5 minutes / refresh_token_digest_or_ip
write_api: 60 requests / minute / subject_or_ip
```

流控数据分层：

- 高频请求计数只放 Redis/cache，不直接写数据库。
- 临时限流锁只放 Redis/cache，依赖 TTL 自动释放。
- 明确的 IP 封禁记录必须落数据库，便于审计、人工解除和后续查询。
- 请求链路优先读 Redis 中的封禁缓存，缓存缺失时再查数据库并回填缓存。

已新增 IP 封禁记录：

```text
SecurityIpBlockRecord
  block_id
  ip_digest
  reason_code
  source_event_type
  blocked_until_epoch
  status
  created_at_epoch
  released_at_epoch
  released_reason
```

当前不保存明文 IP；如确有排查需求，可以后续增加加密存储字段。

### 4.2 认证风险控制

保留现有认证失败节流，并轻量增强：

- `/auth/token` 同时按 username、IP、username+IP 三个维度计数。
- 用户名不存在、密码错误、禁用用户继续保持相同外部响应。
- 多账号同 IP 失败过多时记录 `auth.password_spray_suspected`。
- refresh token reused 继续视为高风险事件，并撤销对应 token session。

### 4.3 请求资源保护

继续沿用现有 `PayloadGuardMiddleware`：

- `Content-Length` 明确超限时直接拒绝。
- chunked 或伪造长度时继续按实际读取字节累计。
- 默认 1 MiB 可保留，后续可按路由覆盖。
- 拒绝时记录 `payload.too_large` 安全事件。

### 4.4 安全响应头

继续沿用现有 `SecurityHeaderMiddleware`：

- 开发环境保留较宽松配置。
- 生产环境开启 HSTS 和 CSP。
- 继续禁用 middleware trace header。
- 后续如接入前端页面，再按真实资源来源细化 CSP。

### 4.5 SSRF 轻量防护

对 outbound HTTP client 增加 URL 安全校验器。

第一版只做明确阻断：

- 只允许 `http` 和 `https`。
- 禁止 `localhost`、`127.0.0.0/8`、`::1`。
- 禁止私有地址段、link-local、metadata IP。
- 禁止空 host、非法端口、非标准 scheme。
- 后续如有业务需要，再增加 allowlist。

### 4.6 安全事件审计

新增统一安全事件契约：

```text
SecurityEventPayload
  event_type
  severity
  decision
  reason_code
  request_id
  trace_id
  path
  method
  status_code
  subject_id
  ip_digest
  user_agent_digest
  policy_name
  occurred_at_epoch
```

第一版事件类型：

```text
auth.login.failure
auth.login.throttled
auth.password_spray_suspected
auth.refresh.reused
auth.token.invalid
authz.denied
rate_limit.blocked
payload.too_large
ssrf.blocked
config.security_rejected
```

审计要求：

- 不记录明文密码。
- 不记录明文 token。
- 不记录完整 refresh token。
- IP 和 User-Agent 默认记录摘要。
- 需要能通过 request_id 串起访问日志、异常日志和安全事件。

## 8. 验收标准

- 单 IP 超过全局限流阈值返回 429。
- `/auth/token` 超过认证策略阈值返回 429。
- Redis 不可用时，`auth_throttle` 和 `rate_limit` 均 fail-closed。
- 明确封禁的 IP 会写入数据库，并同步写入 Redis 封禁缓存。
- Redis 封禁缓存缺失时，可以从数据库封禁记录回填。
- refresh token 复用后，对应 token session 被撤销。
- 超大请求体在 `Content-Length` 和 chunked 两种路径下都返回 413。
- outbound URL 指向本机、内网或 metadata IP 时被拒绝。
- 日志和安全事件中不出现明文 Bearer、JWT、refresh token、password、secret。
- 生产环境继续关闭公开 OpenAPI，开启 HSTS/CSP。

## 9. 实施顺序

1. 先实现 `RateLimitMiddleware`，把已有 `rate_limit` 缓存策略用起来。
2. 再实现统一安全事件契约，先接入已有认证和请求体保护链路。
3. 然后补 SSRF URL 校验器。
4. 最后做轻量风险信号聚合，例如密码喷洒、令牌重放、异常失败突增。
