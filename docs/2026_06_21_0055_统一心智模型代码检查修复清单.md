# 2026_06_21_0055 统一心智模型代码检查修复清单

## 检查说明
本次检查目标不是找零碎代码味道，而是聚焦会破坏功能闭环、运行时事实源、授权模型、模块边界和维护心智模型的问题。

这次实际启用了 6 个 `gpt-5.4`、`reasoning_effort=xhigh` 子智能体做分域审查：
- Web 主链路与路由装配
- 鉴权、管理员身份与 RBAC
- 任务运行时与消息总线
- 配置加载、资源生命周期与部署入口
- 安全防护、日志与可观测
- 持久化、迁移与测试边界

其中 3 条子智能体线路因平台 `429 Too Many Requests` 中断；这部分已由主智能体在当前工作区做了本地交叉审查补位。最终清单以下述证据为准：当前源码、配置、测试、已有设计文档，以及当前版本官方最佳实践。

## 全局判断
当前项目已经明显在朝“统一契约 + 强类型 + 分层运行时”的方向收敛，但还残留几处会持续撕裂心智模型的关键断层：

1. 运行时事实源没有完全收口  
   后台返回的运行时信息、资源命名、注册表可见性与真实 backend 组合仍有偏差。

2. Web 主链路没有完全统一  
   大部分模块已经走 `RequestExecutionBridge`，但仍有个别管理路由直接在 async route 内执行业务/仓储，形成例外分支。

3. 安全链路的“客户端 IP”事实源分散  
   token binding、限流、封禁、事件记录各自读取 `request.client.host`，代理部署下会天然漂移。

4. 配置入口与测试入口还有遗留漂移  
   `.env` 样例、Docker 样例、测试默认值和开发数据库命名没有完全对齐，容易让“同一环境”指向不同事实。

如果你要的是统一、良好、模块化、可维护的做法，那么这里最值得做的不是零敲碎补，而是继续把“运行时事实源”和“安全/IP 事实源”彻底收口。这个重构收益明显高于继续打补丁。

## 当前版本最佳实践依据
以下依据均在 2026-06-21 直接核对过官方文档：

- FastAPI 官方文档 `Lifespan Events` 页面明确写到：推荐使用 `FastAPI(..., lifespan=...)` 处理启动/关闭逻辑；如果提供 `lifespan`，`startup` / `shutdown` 事件处理器不会再被调用。这说明当前版本最佳实践确实是统一生命周期入口，而不是混用两套机制。
- Pydantic 官方文档当前 `Unions` 页面继续强调判别联合（discriminated unions）是复杂协议对象的推荐表达方式，尤其适合减少 union 错误噪音、稳定区分扩展载荷；这与本项目大量 `kind + schema_version + extra="forbid"` 的协议建模方向一致。
- SQLAlchemy 官方文档当前是 `2.0.51`（页面显示发布日期为 2026-06-15），`Transactions and Connection Management` 页面继续推荐显式 `Session.begin()` / 事务边界管理，并强调测试场景下通过外部事务或 savepoint 控制隔离。这与“仓储不偷偷承担事务职责、UoW 负责提交/回滚”的设计判断一致。

## 修复清单

### 1. P1 `create_app()` 永远绕过 assembler 的默认 task binding 收口语义
- 定位：
  - [src/api/asgi_entry.py](E:\python_web_fastapi\work\src\api\asgi_entry.py:39)
  - [src/infrastructure/fastapi_app_assembler.py](E:\python_web_fastapi\work\src\infrastructure\fastapi_app_assembler.py:301)
- 现象：
  - `AsgiApplicationFactory.__call__()` 在 `task_bindings is None` 时，先执行 `self.task_binding_provider.build()`，再把结果作为显式参数传给 assembler。
  - `FastApiAppAssembler._resolve_task_bindings()` 只有在 `task_bindings is None` 时才会进入自己的默认语义；当前主入口永远传入列表，因此这条语义在真实主入口里失活。
- 风险：
  - 主入口、测试入口、显式传参入口对 stale binding/default binding 的处理可能不一致。
  - 这是典型“代码看起来支持一条语义，真实入口永远走不到”的过时入口问题。
- 建议修复：
  - 把 task binding 的默认解析下沉到 `FastApiAppAssembler`，让 `create_app()` 只表达“没有显式覆盖”。
  - 或者把 binding 来源建模为“default / explicit”，避免 `None` 和空列表承载两层语义。
- 验证：
  - 新增测试覆盖真实 `create_app()` 路径下的 declared/stale binding 过滤行为。

### 2. P1 任务运行时对外暴露了 `message_backend`，但内部资源命名仍混用“message bus”与“broker”
- 定位：
  - [src/infrastructure/resource_mount/runtime_resource_bootstrapper.py](E:\python_web_fastapi\work\src\infrastructure\resource_mount\runtime_resource_bootstrapper.py:500)
  - [src/infrastructure/shared_resource_mount.py](E:\python_web_fastapi\work\src\infrastructure\shared_resource_mount.py:1437)
  - [src/application/admin/read_admin_task_runtime_usecase.py](E:\python_web_fastapi\work\src\application\admin\read_admin_task_runtime_usecase.py:41)
  - [src/api/endpoint_admin_task/contract_admin_task.py](E:\python_web_fastapi\work\src\api\endpoint_admin_task\contract_admin_task.py:196)
- 现象：
  - 现在确实会根据配置构建 `LocalMessageBus` 或 `RabbitMqMessageBus`，这比早期状态更好了。
  - 但资源接口仍使用 `shared_message_bus`、`get_message_bus()`、`message_bus_backend` 这套命名，同时实际任务发布主路径又由 `TaskDispatcher/FunboostTaskBootstrapper` 驱动。
  - 对管理端而言，`message bus`、`task backend`、`broker`、`publisher` 几层概念仍然缠在一起。
- 风险：
  - 后续开发者容易把“任务调度后端”和“底层消息传输后端”误当成同一抽象。
  - 运行时诊断页可能继续显示“能看到字段，但不知道它是否真的参与当前任务路径”。
- 建议修复：
  - 这是一个适合重构的点。建议明确拆成两层事实源：
    - `task_runtime_mode`：local inline / local queued / funboost producer / funboost consumer
    - `transport_backend`：local / rabbitmq
  - 后台 runtime payload 直接返回“当前节点角色”和“有效传输层”，不要只返回抽象名称。
  - 同时把资源命名从泛化的 `message_bus` 收敛到更贴近真实职责的名字。
- 验证：
  - `/admin/tasks/runtime` 与实际装配对象、消费者启动行为、发布路径一致。

### 3. P1 `/security/ip-blocks` 管理路由没有走统一 `RequestExecutionBridge`
- 定位：
  - [src/api/endpoint_security_protection/route_security_protection.py](E:\python_web_fastapi\work\src\api\endpoint_security_protection\route_security_protection.py:121)
  - [src/api/endpoint_system_overview/route_system_overview.py](E:\python_web_fastapi\work\src\api\endpoint_system_overview\route_system_overview.py:98)
- 现象：
  - `system_overview` 已经通过 `read_request_execution_bridge(...).run_sync(...)` 执行同步用例。
  - `security_protection` 的 `list/create/get/release` 直接在 async route 中创建 UoW、实例化 repository、调用 guard、拼装事件。
- 风险：
  - Web 主链路出现例外分支，破坏“路由只负责契约与授权，用例负责业务”的统一心智模型。
  - 后续如果桥接层加入 tracing、超时、线程池、统一异常包装，这一组路由会天然漏掉。
- 建议修复：
  - 将 IP block 管理操作收敛成同步 usecase 或 adapter，路由层统一经 `RequestExecutionBridge` 调用。
  - 顺手把 `SecurityEventBuilder()` 的直接 new 也通过依赖容器提供，避免路由继续承担装配职责。
- 验证：
  - `security_protection` 所有管理接口都通过 bridge 执行，HTTP 行为保持不变。

### 4. P1 客户端 IP 读取分散，代理部署下安全事实源会漂移
- 定位：
  - [src/infrastructure/security/ip_block_guard.py](E:\python_web_fastapi\work\src\infrastructure\security\ip_block_guard.py:306)
  - [src/infrastructure/security/rate_limit_guard.py](E:\python_web_fastapi\work\src\infrastructure\security\rate_limit_guard.py:180)
  - [src/infrastructure/security/security_protection_guard.py](E:\python_web_fastapi\work\src\infrastructure\security\security_protection_guard.py:142)
  - [src/infrastructure/middleware_chain/authentication_binding_middleware.py](E:\python_web_fastapi\work\src\infrastructure\middleware_chain\authentication_binding_middleware.py:167)
  - [src/api/endpoint_auth_access/route_auth_access.py](E:\python_web_fastapi\work\src\api\endpoint_auth_access\route_auth_access.py:327)
- 现象：
  - 多处重复实现 `_read_client_ip()`，统一逻辑都是 `request.client.host`。
- 风险：
  - 在 Nginx / Ingress / ELB 后面，拿到的可能是代理地址。

### 6. P1 RabbitMQ 发布结果仍把“发布成功”与“被路由成功”折叠为同一结果
- 定位：
  - [src/infrastructure/task/rabbitmq_message_bus.py](E:\python_web_fastapi\work\src\infrastructure\task\rabbitmq_message_bus.py:109)
- 现象：
  - `publish()` 在 `basic.publish(...)` 返回后直接构造 `MessagePublishResult(published=True, routed=True, ...)`。
  - 代码对 `publisher_confirm_enabled and result is False` 做了 nack 检查，但没有看见 returned-message 分支的显式建模。
- 风险：
  - 对 RabbitMQ 来说，“broker 接收 publish” 与 “存在匹配 binding 并成功路由”不是同一个事实。
  - 当前结果模型虽然有 `routed` 字段，但实现实际上把它写死成 `True`，这会误导运维和上层逻辑。
- 建议修复：
  - 如果保留 `routed` 字段，就必须完整承接 unroutable 语义；否则删掉该字段，避免伪能力。
  - 更推荐沿用当前字段，但把 returned message / mandatory 失败建模成明确失败结果或异常。
- 验证：
  - 无 binding 的 exchange/routing_key 组合下，接口和执行记录能够准确反映“未路由”。

### 7. P1 Funboost 失败回调遇到不存在的执行记录时不具备兜底弹性
- 定位：
  - [src/infrastructure/task/funboost_task_bootstrapper.py](E:\python_web_fastapi\work\src\infrastructure\task\funboost_task_bootstrapper.py:313)
  - [src/infrastructure/task/task_execution_store.py](E:\python_web_fastapi\work\src\infrastructure\task\task_execution_store.py:322)

  - `TaskExecutionStore._update_record()` 在找不到记录时直接抛 `RuntimeError(TASK_EXECUTION_RECORD_NOT_FOUND_MESSAGE)`。
  - Funboost 消费失败场景如果遇到历史消息、手工消息或记录被清理，会有二次异常覆盖原始失败。

- 建议修复：
  - 在 failure callback 链路中把“记录不存在”视为可恢复异常，至少写入 `FailedTaskRecorder` 和结构化日志。
  - 更好的方案是允许按消息内容补建一条 FAILED 记录。
- 验证：
  - 模拟不存在 deduplication key 的失败消息，不再二次抛错，失败信息仍可观察。

## 建议重构顺序
1. 先收口运行时事实源  
   任务 runtime、transport backend、注册表可见性、message bus/broker 命名统一。

2. 再统一 Web 主链路  
   `RequestExecutionBridge`、依赖容器、route/usecase 边界全部一致。

3. 再收口安全 IP 事实源  
   提炼 `ClientIpResolver`，统一 token binding、rate limit、ip block、audit event。

4. 最后清理配置与测试入口  
   `.env` 入口、数据库命名、production web runtime、测试默认值完全对齐。

- 早期方案文档中的历史表述残留  
  只要不再作为当前运行依据，可以在后续文档整理时顺手清理，不值得单独为此改代码。
