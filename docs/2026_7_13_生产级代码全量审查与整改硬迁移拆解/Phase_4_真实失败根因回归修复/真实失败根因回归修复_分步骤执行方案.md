# 真实失败根因回归修复分步骤执行方案

> 2026-07-16 最终复核：26 份 RegressionRecord、旧版复现、行为级定向和影响面索引已重建。当前 `fixed=14, verified=12`；13 个 P1 缺少可信旧版失败历史，REG-023 缺远端 CI 证据，本阶段保持部分完成。

## 阶段目标与硬迁移边界

对 Phase 3 暴露的问题做根因修复，保持测试可信度和外部兼容性，直至阻断项清零并形成稳定回归结果。

本阶段采用一次性硬迁移：在已冻结契约下直接收敛到最终最佳实践实现，不设计新旧双轨、兼容分支、临时兜底或渐进切换。硬迁移针对内部实现；已声明的公共 API、配置键、迁移 head、状态码和外部行为不得发生未声明变化。所有失败先形成证据并确认根因和影响面，再修改源码、测试、配置或环境入口。

## 依赖关系

| 依赖项 | 输入与约束 |
|---|---|
| Phase 3 失败证据 | 失败命令、结构化结果、日志、环境快照和性能轮次记录必须完整可追溯。 |
| 失败分类 | 每个失败先归类为源码、测试、环境、数据、文档或不稳定性，不凭猜测修改。 |
| Phase 2 测试资产 | 修复涉及测试或影响测试覆盖面时，回退到 Phase 2 补充或修正测试，再进入 Phase 3 真实回跑。 |
| Phase 3 真实环境 | 修复后按影响面回退到 Phase 3，使用真实 PostgreSQL、Redis、RabbitMQ、容器、迁移、镜像和负载环境复验。 |
| 工程规范 | 遵循 `docs/standard` 中编码、命名和测试规范；测试应可重复、独立、可自动化并能定位问题。 |

阶段内部顺序固定为：证据冻结与分类 → 最小复现 → 根因及影响面确认 → 一次性根因修复 → 定向回跑 → 影响面回跑 → 全量与真实环境回归 → 状态收口。不得跳过会影响公共契约、数据结构、跨模块调用链、迁移或用户可见行为的风险判断。

## 阶段契约

| 英文名 | 中文名 | 中文说明 |
|---|---|---|
| `RegressionHeader` | 回归公共头 | 记录 finding ID、影响模块、严重级别和关联测试运行 ID。 |
| `RegressionDetailUnion` | 回归扩展联合 | 以 `kind` 判别 `source_fix`、`test_fix`、`environment_fix`、`documentation_fix`；每种 detail 含 `schema_version` 且禁止额外字段。 |
| `RegressionStatus` | 回归状态 | 固定为 `open/fixed/verified/rejected`；只有定向与影响面回归均通过才可 `verified`。 |
| `RerunScope` | 回跑范围 | 明确 `failed`、`module`、`critical-path`、`full-suite` 四级，公共契约、迁移、组合根变更必须全量回跑。 |

契约实现继续遵守公共头与强类型扩展字段规则：Pydantic 判别联合使用 `kind`，每个扩展模型显式提供 `schema_version`，公共头、扩展模型和外层 envelope 使用 `ConfigDict(extra="forbid")`，外层声明与内层实际类型保持一致，不使用开放扩展字典。

## 代码现状、目标形态与修改路径

Phase 4 不预设具体失败文件，也不凭历史描述猜测代码状态；每项“代码现状”必须从 Phase 3 的失败证据和当前源码重新确认。修改路径只落到该 finding 的真实调用链及受影响测试，公共契约、数据结构、跨模块调用链、迁移或用户可见行为变化必须先完成引用分析和关键路径判断。

| 步骤 | 代码现状 | 目标形态 | 修改路径 |
|---|---|---|---|
| 证据与记录 | Phase 3 已产生失败命令、日志、结构化结果或性能轮次，但尚不能据此宣告根因已确认。 | 每个独立根因对应唯一 `open` finding，并能追溯测试运行 ID、环境和原始失败证据。 | 从失败运行定位当前源码、测试、配置或环境入口；先建记录，不改实现。 |
| 最小复现 | 失败可能仍受夹具、数据、时钟、共享状态或真实依赖干扰。 | 旧实现上的最小用例稳定复现一个主要行为，断言、触发条件和可观察结果明确。 | 在对应测试类型目录局部补充或修正用例；环境阻塞保持 `open`。 |
| 根因与影响面 | 当前观察可能只是症状，回跑范围尚未确定。 | 根因、影响模块、外部兼容性和 `RerunScope` 均有证据。 | 沿真实调用链检查引用、契约、事务、资源、并发、缓存、消息、迁移及依赖版本。 |
| 根因修复 | 问题实现、错误测试资产、配置或环境入口仍存在。 | 单一最终实现符合分层、类型、异常、事务和资源边界，测试可信度与已声明外部行为不下降。 | 只修改已证实根因所在边界；涉及测试覆盖时回退 Phase 2，涉及真实依赖时回退 Phase 3。 |
| 定向与影响面回跑 | 根因修复完成只代表 `fixed`，尚无充分验证证据。 | 旧版复现、新版定向通过、影响面回归三类证据齐全后才 `verified`。 | 按最小失败集、模块、关联契约/边界/集成、真实依赖、全量的顺序回跑。 |
| 不稳定性修复 | flaky 失败可能依赖时钟、随机源、执行顺序、端口、数据库隔离或等待条件。 | 测试隔离、可重复，重试仅保留明确业务或协议依据。 | 注入时钟/随机源，隔离状态和资源，修复夹具与事务清理，以可观察条件替代无依据等待。 |
| 性能回归 | Phase 3 已冻结基线和轮次，单轮变化不能证明参数更优。 | autotuner 多轮记录可复现，最优配置相对基线稳定且无错误率或资源风险恶化。 | 仅在 `test/performance/autotuner/` 搜索关键参数；无连续收益时淘汰并恢复上一晋升配置。 |
| 最终收口 | finding、测试、扫描、迁移、镜像和性能证据可能仍分散或存在阻断项。 | P0/P1 与真实测试阻断项清零，P2/P3 有可审计结论，最终交付事实冻结。 | 更新状态后执行完整门禁与真实环境回归；全部退出条件满足后进入 Phase 5。 |

以下片段只说明原始契约要求的目标形态；实际模块位置和冻结版本值必须以当前源码与 Phase 1/Phase 3 证据为准，不据此新增一套并行契约：

```python
from typing import Annotated, Literal

from pydantic import BaseModel, ConfigDict, Field


FindingSeverity = Literal["P0", "P1", "P2", "P3"]
RegressionStatus = Literal["open", "fixed", "verified", "rejected"]
RerunScope = Literal["failed", "module", "critical-path", "full-suite"]
SchemaVersion = Literal["<冻结版本>"]


class RegressionHeader(BaseModel):
    model_config = ConfigDict(extra="forbid")

    finding_id: str
    affected_module: str
    severity: FindingSeverity
    test_run_id: str


class SourceFixDetail(BaseModel):
    model_config = ConfigDict(extra="forbid")

    kind: Literal["source_fix"] = "source_fix"
    schema_version: SchemaVersion


class TestFixDetail(BaseModel):
    model_config = ConfigDict(extra="forbid")

    kind: Literal["test_fix"] = "test_fix"
    schema_version: SchemaVersion


class EnvironmentFixDetail(BaseModel):
    model_config = ConfigDict(extra="forbid")

    kind: Literal["environment_fix"] = "environment_fix"
    schema_version: SchemaVersion


class DocumentationFixDetail(BaseModel):
    model_config = ConfigDict(extra="forbid")

    kind: Literal["documentation_fix"] = "documentation_fix"
    schema_version: SchemaVersion


# 判别联合封闭允许的修复类型，未知 kind 和额外字段必须被拒绝。
RegressionDetailUnion = Annotated[
    SourceFixDetail
    | TestFixDetail
    | EnvironmentFixDetail
    | DocumentationFixDetail,
    Field(discriminator="kind"),
]


class RegressionRecord(BaseModel):
    model_config = ConfigDict(extra="forbid")

    header: RegressionHeader
    detail: RegressionDetailUnion
    status: RegressionStatus
    rerun_scope: RerunScope
```

## 分步骤执行方案

### 步骤 1：冻结失败证据并建立回归记录

为 Phase 3 的每个失败建立唯一 finding ID，以 `RegressionHeader` 关联影响模块、P0-P3 严重级别和测试运行 ID；保留原始命令、返回码、失败日志摘要、环境与数据快照、测试计数、覆盖率、安全扫描、镜像摘要或性能轮次。状态初始化为 `open`，blocked 只能记录可复现的外部前置条件，不能记为通过。

验收点：每个失败均可从回归记录定位到原始运行证据，不存在合并多个根因、证据缺失或“未审查即通过”。

### 步骤 2：分类并保留最小复现

将失败归类为源码、测试、环境、数据、文档或不稳定性；为每个失败保留最小复现，确认是稳定失败还是 flaky。测试失败必须有明确断言，且每个测试只验证一个主要行为；不得因修复需要而删除有效断言、扩大忽略、吞异常、降低覆盖率或性能阈值。

验收点：旧版最小复现稳定失败，失败类别、触发条件和可观察结果明确；无法复现时保持 `open` 或给出可复现的阻塞条件，不得判为 `fixed`。

### 步骤 3：确认根因、影响面与回跑范围

沿真实调用链定位根因，区分症状与根因，并分析公共 API、契约、迁移、鉴权、安全、组合根、资源生命周期、依赖版本、事务、并发、缓存和消息链路的影响。按 `RerunScope` 选择 `failed`、`module`、`critical-path` 或 `full-suite`；公共契约、迁移、组合根变化必须选择 `full-suite`。

验收点：每项记录根因、影响面、拟修改边界、回跑范围和外部兼容性判断；修改跨层调用链、数据结构或公共契约前已完成引用与关键路径分析。

### 步骤 4：一次性实施根因修复

根据已确认类别修改源码、测试、配置或环境入口，以单一最终实现替换问题实现，不保留新旧双轨。源码修复保持接口层、业务层、数据访问层和模型层分离，使用现代类型标注和稳定结构模型；纯逻辑与副作用分离，只捕获可处理的具体异常。测试或夹具问题同步修复测试资产和执行配置，不通过放宽断言、跳过测试或回退正确实现规避。事务仍由 UoW 统一管理，Repository 不得提交、回滚或释放外层会话。

验收点：修改解决已证实根因，没有跨层特判、隐藏异常、临时兼容分支或未声明外部行为变化；修复后状态可置为 `fixed`，但尚不得置为 `verified`。

### 步骤 5：按影响面逐级回跑

回归顺序固定为：最小失败集 → 阶段相关/模块测试集 → 关联 contract、boundary、integration 测试 → 依赖型真实集成测试 → 全量测试。项目测试入口优先使用：

```powershell
# 使用项目解释器执行全量测试，避免导入路径和依赖版本漂移。
.\.venv\Scripts\python.exe -m pytest -q
```

需要真实依赖时，先确保 Docker 依赖就绪：

```powershell
# 启动 Phase 3 已声明的真实依赖；健康检查通过后再执行集成回归。
docker compose -f compose.yml up -d
```

先回跑失败用例，再回跑模块测试和关联 contract/boundary/integration 测试。公共契约、迁移、鉴权、安全、组合根、资源生命周期或依赖版本变化后执行全量回归。

验收点：每个拟 `verified` 项同时具有旧版复现、新版定向通过和影响面回归证据；无外部服务时 unit/contract/boundary 仍可独立运行，不触发未声明的外部资源。

### 步骤 6：消除不稳定性而非掩盖不稳定性

对 flaky 用例逐项检查时钟、随机数、共享状态、端口、数据库隔离和等待条件；修复时间与随机源注入、资源唯一性、夹具生命周期、事务清理及可观测等待条件。不得仅增加无依据的 `sleep` 或 `retry`，测试之间不得依赖执行顺序或共享状态。

验收点：同一用例在隔离、重复、乱序或并发条件下结果稳定；任何重试均有明确的业务或协议依据，而不是掩盖竞态。

### 步骤 7：处理性能回归与调参结论

性能回归只依据 Phase 3 已记录且冻结的机器、版本、数据规模、并发模型和基线调整。涉及容量参数时，必须使用 `test/performance/autotuner/` 的自动搜索与结构化轮次记录，比较吞吐、p50/p95/p99、错误率、池等待、队列深度、资源峰值和恢复时间。仅连续多轮稳定、无错误率或资源风险恶化的配置可以晋升；若调参无连续收益，淘汰该路线并恢复上一晋升配置。

验收点：保留最优配置与失败配置对比、每轮配置/结果/结论和“是否继续”判断；性能结论至少复跑一次，单轮偶然最优不得晋升，p95 相对冻结基线不劣化超过 20%。

### 步骤 8：清零阻断项并冻结最终证据

更新 finding 状态、修复证据和剩余风险。只有定向与影响面回归均通过才从 `fixed` 置为 `verified`；不成立的方向置为 `rejected` 并记录原因。持续回归直至 P0/P1 与真实测试阻断项清零，P2/P3 均有风险说明、处置或明确延期依据。

最终执行编译、格式/静态检查、类型检查、架构依赖检查、单元/契约/边界/接口/异常/初始化/路径/集成测试、全量回归、安全与供应链扫描、迁移、生产镜像及必要负载场景，并冻结命令返回码、测试计数、覆盖率、扫描结果、迁移 head、镜像摘要和性能报告。

验收点：全量测试、安全扫描、迁移、镜像和必要负载场景最终再次通过；无未解释 error、死锁、连接泄漏、无界增长、敏感信息暴露或门禁降级。

## 最终校验与退出条件

| 校验域 | 通过条件 |
|---|---|
| 单项回归 | 每个 `verified` 项同时具有旧版复现、新版定向通过和影响面回归证据。 |
| 全量回归 | 全量测试、安全扫描、迁移、镜像和必要负载场景最终再次通过。 |
| 修复真实性 | 无通过降低门禁、隐藏异常或改变未声明外部行为产生的伪修复。 |
| 阻断项 | P0/P1 与真实测试阻断项为零；P2/P3 有可审计处置结论。 |
| 外部兼容 | 公共 API、配置键、迁移 head、OpenAPI 和关键响应无未声明变化。 |
| 下一阶段门禁 | 最终代码、迁移 head、配置键、OpenAPI、测试计数、覆盖率、镜像和性能报告冻结后，方可进入 Phase 5 文档回归。 |
