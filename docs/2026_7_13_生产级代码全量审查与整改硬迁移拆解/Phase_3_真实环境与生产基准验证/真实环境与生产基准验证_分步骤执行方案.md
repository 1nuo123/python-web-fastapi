> 2026-07-16 最终复核：static、offline、regression、security、migration、image 和 load TestRun 均绑定代码基线 `66dbff1e97561b4620af04de7930ef9e3fc7a8f786a33a35a318a9652a9dffc0`，真实环境、覆盖率、生产镜像和负载验证完成。

## 阶段目标与硬迁移边界

在可复现的本地与容器环境中，一次性执行完整质量、安全、离线测试、真实依赖集成、迁移、生产镜像和并发基准验证，形成可作为生产就绪判断依据的真实结果，不以 mock、历史报告或单轮偶然结果替代。该阶段只验证 Phase 1、Phase 2 已完成的硬迁移终态，不设计新旧实现并存、双轨运行、兼容开关或渐进式迁移。

事实优先级固定为“当前源码与迁移 > 可执行配置与测试 > 当前项目手册 > 历史方案”。若结果冲突，记录为结构化失败并进入 Phase 4 根因修复，不通过降低阈值、扩大 ignore、删除断言、无理由 skip/xfail 或回退实现获得通过。

执行顺序不可跳跃：环境与基线冻结 → 静态/安全门禁 → 无外部服务快速层 → 真实迁移 → 真实集成 → 全量覆盖率 → 生产镜像 → 负载与故障 → autotuner 复验 → 证据汇总与生产就绪判定。前序阻断不得被后序成功覆盖。

## 阶段契约

| 英文名 | 中文名 | 中文说明 |
|---|---|---|
| `TestRunHeader` | 测试运行公共头 | 记录运行 ID、代码基线、环境、开始时间和命令入口。 |
| `TestRunDetailUnion` | 测试运行扩展联合 | 以 `kind` 判别 `static`、`unit`、`integration`、`security`、`migration`、`image`、`load` 结果；均含 `schema_version` 并禁止额外字段。 |
| `TestRunStatus` | 测试状态 | 固定为 `passed/failed/blocked`；`blocked` 必须给出可复现的外部前置条件，不能记为 `passed`。 |
| `BenchmarkPromotion` | 基准晋升结论 | 固定为 `promoted/rejected/candidate`，同时记录相对基线、稳定性和过拟合/偶然性判断。 |

契约继续遵守全局“公共头字段 + 强类型扩展字段”：扩展字段使用 Pydantic 判别联合，具有 `kind`、`schema_version`，所有模型启用 `ConfigDict(extra="forbid")`；禁止 `dict[str, Any]`、`metadata`、`extra_payload`，外层类型、判别值与内层扩展类型必须一致。运行结果至少保存命令、返回码、测试计数、耗时、环境摘要、失败摘要和证据路径；敏感值只保存脱敏摘要。

对应的强类型契约形态如下；实际模型归属 Phase 1，本阶段只按该口径校验序列化结果，不在验证阶段另建第二套模型：

```python
from datetime import datetime
from pathlib import Path
from typing import Annotated, Literal, Self

from pydantic import BaseModel, ConfigDict, Field, model_validator

from src.core.contract_header import ContractHeader


TestRunStatus = Literal["passed", "failed", "blocked"]
BenchmarkPromotion = Literal["promoted", "rejected", "candidate"]


class TestRunHeader(ContractHeader):
    """记录一次真实验证的稳定公共字段。"""

    schema_version: Literal["1.0"] = "1.0"
    run_id: str
    code_baseline: str
    environment: str
    started_at: datetime
    command_entry: str


class TestRunDetailBase(BaseModel):
    """收敛各类结果共有的证据字段，禁止开放字典扩展。"""

    model_config = ConfigDict(extra="forbid")

    schema_version: Literal["1.0"] = "1.0"
    status: TestRunStatus
    command: str
    exit_code: int | None
    test_count: int | None
    duration_seconds: float
    environment_summary: str
    failure_summary: str | None
    evidence_path: Path


class StaticRunDetail(TestRunDetailBase):
    kind: Literal["static"] = "static"


class UnitRunDetail(TestRunDetailBase):
    kind: Literal["unit"] = "unit"


class IntegrationRunDetail(TestRunDetailBase):
    kind: Literal["integration"] = "integration"


class SecurityRunDetail(TestRunDetailBase):
    kind: Literal["security"] = "security"


class MigrationRunDetail(TestRunDetailBase):
    kind: Literal["migration"] = "migration"


class ImageRunDetail(TestRunDetailBase):
    kind: Literal["image"] = "image"


class LoadRunDetail(TestRunDetailBase):
    kind: Literal["load"] = "load"


TestRunDetailUnion = Annotated[
    StaticRunDetail
    | UnitRunDetail
    | IntegrationRunDetail
    | SecurityRunDetail
    | MigrationRunDetail
    | ImageRunDetail
    | LoadRunDetail,
    Field(discriminator="kind"),
]


class TestRunRecord(BaseModel):
    """组合公共头与判别联合，并校验外层类型和内层判别值一致。"""

    model_config = ConfigDict(extra="forbid")

    header: TestRunHeader
    kind: Literal["static", "unit", "integration", "security", "migration", "image", "load"]
    detail: TestRunDetailUnion

    @model_validator(mode="after")
    def validate_kind_consistency(self) -> Self:
        """拒绝外层类型与扩展结果类型不一致的记录。"""
        if self.kind != self.detail.kind:
            raise ValueError("测试运行外层类型与扩展类型不一致")
        return self
```

核验点：未知字段被拒绝；七类 `kind` 均可判别；缺少或错误的 `schema_version` 被拒绝；外层 `kind` 与 `detail.kind` 不一致被拒绝；`blocked` 记录具有可复现前置条件；证据中不保存敏感原文。

## 分步骤执行

### 步骤 1：冻结真实运行基线

确认 Phase 1、Phase 2 的完成证据，生成唯一运行 ID，冻结源码/迁移/配置/OpenAPI 快照、Python 与锁文件版本、容器镜像基底、主机 CPU/内存/操作系统、数据规模、并发模型和测试入口。检查测试数据库命名与密钥隔离；任何生产凭据、生产数据库或未知历史均不得参与测试。

验收点：同一基线可重复创建等价环境；环境差异可检索；前置条件缺失准确记为 `blocked`；不得开始带破坏性的数据库测试。

### 步骤 2：执行编译、质量、安全与供应链门禁

按固定顺序执行编译、Ruff、Mypy、import-linter、Bandit、pip-audit、锁文件和敏感信息扫描。工具配置必须来自 Phase 1 固化的 `pyproject.toml`/`noxfile.py`，不得在运行时放宽。

保留的原始命令入口及对应语义如下：

```powershell
# 校验锁文件与声明依赖一致且可复现。
uv lock --check

# 校验 src 全量 Python 源码可编译。
python -m compileall -q src
```

Ruff、Mypy、import-linter、Bandit、pip-audit 与敏感信息扫描使用项目统一 nox/CI 入口；每项独立记录返回码、工具版本、发现数量和豁免依据。依赖漏洞扫描不得存在未豁免的高危/严重项，密钥不得入库或进入日志。

验收点：所有门禁通过；`core`、`domain`、`application` 不依赖 `api`/`infrastructure`，`infrastructure` 不依赖 API 路由常量；任何失败保留原始命令与脱敏摘要。

### 步骤 3：在无外部服务环境执行快速测试层

断开 PostgreSQL、Redis、RabbitMQ 和网络后，依次执行 unit → contract → boundary → interface/exception/path/initialization。单元、契约、边界测试不得连接数据库、缓存、消息队列或网络；每个测试相互独立，不依赖执行顺序和共享状态，断言覆盖输入、输出、异常和边界。

```powershell
# 使用项目解释器，按既定顺序运行不允许依赖外部服务的快速测试层。
.\.venv\Scripts\python.exe -m pytest -q test/unit_test
.\.venv\Scripts\python.exe -m pytest -q test/contract_test
.\.venv\Scripts\python.exe -m pytest -q test/boundary_test
.\.venv\Scripts\python.exe -m pytest -q test/interface_test test/exception_test test/path_test test/initialization_test
```

验收点：快速层全部通过且未触发外部资源夹具；测试收集无 marker 警告；失败可定位到具体行为。外部服务缺失不得把快速层连带变为 error。

### 步骤 4：启动真实依赖并验证迁移

使用测试专用配置启动 PostgreSQL、Redis、RabbitMQ，等待健康检查通过后执行 Alembic 空库升级、受支持旧版本升级、重复升级、升级失败回滚和 Compose migration job 门禁。数据库重置只允许名称满足 `_test` 安全规则。

```powershell

docker compose -f compose.yml up -d --wait postgres redis rabbitmq

# 执行显式真实依赖迁移测试，不由全局 autouse 夹具隐式触发。
.\.venv\Scripts\python.exe -m pytest -q test/integration_test/test_migration_job_integration.py
```

验收点：空库与旧版本均到达冻结 migration head；重复升级幂等；失败时事务回滚且应用不会越过 migration gate 启动；迁移前后数据和约束兼容。

### 步骤 5：执行真实依赖与生产安全集成测试

在健康的真实依赖环境中执行 PostgreSQL、Redis、RabbitMQ、Funboost、密钥、分布式锁、日志、任务 Outbox 和生产安全集成测试。覆盖事务提交/回滚、重复投递、发布确认不确定、进程中断恢复、幂等冲突、鉴权/RBAC、SSRF/DNS 重绑定、代理头、CORS、限流、请求体以及日志/指标泄密；鉴权、鉴权缓存和限流按生产要求 fail closed。

验收点：真实模块调用链打通；异常时补偿、回滚、降级或告警符合契约；UoW 是唯一事务边界；日志和指标无密钥、令牌、密码等敏感原文；每个失败能区分代码、配置或外部前置条件。

### 步骤 6：执行全量回归与覆盖率门禁

在真实依赖可用后执行全量 pytest 与 line/branch 覆盖率门禁，纳入 unit、path、class inheritance、initialization、integration、interface、contract、exception、boundary 和 convention usage 测试。任何 skip/xfail 必须有明确且仍有效的原因，不得用于规避失败。

```powershell
# 项目规定的全量测试入口；覆盖率参数与阈值由 Phase 1 固化配置统一控制。
.\.venv\Scripts\python.exe -m pytest -q
```

验收点：全量测试通过；总体 line/branch 不低于 85%，auth/security/task/persistence 关键路径不低于 90%；新增和变更分支覆盖成功、拒绝、超时、回滚、幂等与资源释放；记录测试计数、skip/xfail 原因和覆盖率报告。

### 步骤 7：验证生产镜像与容器生命周期

构建生产镜像并记录不可变摘要；使用 `compose.yml` 与 `compose.production.yml` 合成的生产约束执行配置解析、迁移单入口、容器启动、存活/就绪、非 root、最小 capability、`no-new-privileges`、只读文件系统与临时写目录、资源限制、SIGTERM 优雅停机和重启恢复测试。

```powershell
# 解析生产 Compose，确保所有必需环境变量由隔离测试环境提供。
docker compose -f compose.yml -f compose.production.yml config

# 构建与实际测试相同的生产镜像。
docker compose -f compose.yml -f compose.production.yml build
```

验收点：镜像构建、启动、健康检查、迁移 gate、非 root、最小权限、读写边界、资源限制和停机恢复全部通过；镜像摘要写入报告；测试退出后清理测试容器与数据卷，但不删除任何生产资源。

### 步骤 8：执行稳定、突发、过载、降级与多实例基准

使用 Phase 2 在 `test/performance/scenarios/` 固化的成熟负载工具场景，在冻结机器、数据集和并发模型上依次执行稳定负载、突发负载、过载、依赖降级和多实例横向扩容。观测吞吐、p50/p95/p99、错误率、池等待、队列深度、CPU/内存、线程/连接数和恢复时间；同时检查超时、背压、拒绝、幂等、低基数指标和无状态扩容边界。

验收点：无未处理 5xx、死锁、连接/线程/内存泄漏或无界增长；过载按契约背压/拒绝而非雪崩；p95 相对冻结基线不劣化超过 20%；依赖恢复后系统在记录的时间内恢复。

### 步骤 9：运行 autotuner 多轮搜索与复验

只在 `test/performance/autotuner/` 使用自动搜索关键容量参数，不盲调。每轮记录配置、吞吐、p50/p95/p99、错误率、资源峰值和结论；输出最优配置与失败配置对比，并判断该路线是否值得继续。候选最优配置必须在相同基线下至少复跑一次，并用多轮、不同种子/负载验证稳定性。

晋升规则：只有多轮稳定、无错误率或资源风险恶化、无过拟合/偶然性证据且优于冻结基线的结果可标记 `promoted`；只提升训练/单轮吞吐而验证负载无收益或下降的结果标记 `rejected`；证据不足标记 `candidate`。单轮偶然最优不得晋升，后续调整必须基于已记录元数据。

### 步骤 10：汇总证据并作生产就绪判定

按 `TestRunHeader + TestRunDetailUnion` 汇总所有运行结果、环境快照、命令与返回码、测试计数、覆盖率、安全扫描、镜像摘要、失败日志摘要、性能轮次、最优/失败参数对比和生产就绪结论。失败日志只保留必要上下文和 traceback，使用中文且完成脱敏。

验收点：P0/P1 为零；真实测试无未解释 error；所有 `failed`/`blocked` 均有复现条件、责任语义、风险和 Phase 4 入口；性能结论至少复跑一次；只有全部阻断门禁通过才能声明生产就绪。
