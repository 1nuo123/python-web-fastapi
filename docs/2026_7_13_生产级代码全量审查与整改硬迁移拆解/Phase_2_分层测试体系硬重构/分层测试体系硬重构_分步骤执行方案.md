# Phase 2：分层测试体系硬重构分步骤执行方案

> 2026-07-16 最终复核：核心分层、真实依赖回归、离线 guard、取消传播、五类负载契约、行为级 finding 映射、事务边界及 autotuner 晋升规则均已落地并通过当前基线验证。

## 阶段目标与硬迁移边界

一次性将测试体系重构为“离线快速测试 + 显式真实依赖测试”，为 Phase 1 的契约、架构、安全、事务、并发和部署行为提供可重复回归，并建立性能场景与自动调参元数据入口。

- 本阶段是硬迁移：同一批次完成夹具、marker、目录、覆盖率、性能入口和受影响测试切换；不保留新旧双轨、临时兼容夹具或渐进开关。
- 不改变 Phase 1 冻结的 HTTP 路径、状态码、响应语义、配置键、数据库兼容性和任务消息语义；测试不写死未冻结的内部实现。
- 单元、契约和边界测试不得依赖 PostgreSQL、Redis、RabbitMQ 或网络；集成测试必须通过显式 marker/fixture 请求真实依赖。缺少前置条件时给出可定位的失败/阻断信息，不得连带使离线测试 error。
- 测试环境变量只作用于测试进程；数据库创建、迁移、锁和重置只允许显式集成夹具执行，数据库名称必须满足 `_test` 安全规则。
- 不通过扩大 ignore、降低覆盖率阈值、删除/放宽断言、skip/xfail 或回退实现换取通过。
- 测试代码遵循 `docs/standard`：Python 3.11+、现代完整类型标注、稳定结构强类型建模、职责/副作用边界清晰；测试相互独立、可重复、可自动化、失败可定位，每个测试只验证一个主要行为，名称表达“被测对象_场景_预期结果”。

## 依赖关系与执行次序

| 依赖 | 输入/前置条件 | 本阶段约束 |
|---|---|---|
| Phase 1 | 已冻结的外部契约、每个整改批次和 P0/P1 风险清单 | 测试与源码批次一一映射，不提前固化未确定实现；新增失败用例须能在旧实现复现、在新实现通过。 |
| 版本与工具 | Python 3.11、项目解释器、`pyproject.toml`、锁文件及 Phase 1 接入的 pytest-cov/质量门禁 | 测试依赖必须直接声明并锁定；至少处理当前 `portalocker` 被测试导入但未直接声明的问题。 |
| 真实依赖边界 | PostgreSQL、Redis、RabbitMQ、Docker/Compose | 只允许 integration/performance 显式请求；真实执行留给 Phase 3，本阶段完成可收集、dry-run 和隔离证明。 |
| 下游 Phase 3 | 本阶段全部门禁与证据通过 | Phase 3 才可执行真实迁移、集成、镜像和负载验证。 |

固定顺序：契约映射与基线 → 夹具/marker 硬切换 → 离线回归 → 契约/架构/并发 → 事务/安全/部署 → 性能/autotuner → 覆盖率与阶段验收。发生失败时按规范执行“最小失败集 → 阶段相关测试集 → 依赖型集成测试 → 全量测试”。

## 阶段契约

| 英文名 | 中文名 | 中文说明 |
|---|---|---|
| `TestLayer` | 测试层级 | 枚举 `unit/contract/boundary/interface/integration/performance`，决定是否允许真实外部资源。 |
| `ExternalResourceMarker` | 外部资源标记 | 显式声明 `postgres/redis/rabbitmq/docker` 前置条件；未声明的测试禁止连接外部服务。 |
| `ContractCompatibilityCase` | 契约兼容用例 | 校验公共头、判别联合、`kind`、`schema_version`、`extra="forbid"`、外内类型一致及旧版本兼容。 |
| `LoadScenarioDetailUnion` | 负载场景扩展联合 | 以 `kind` 判别稳定负载、突发负载、过载、依赖降级等强类型场景；每种 detail 含 `schema_version` 且禁止额外字段。 |
| `TuningTrialDetail` | 调参轮次扩展字段 | 记录候选参数、吞吐、延迟、错误率、资源峰值、结论和晋升状态，不接受自由格式 metadata。 |
| `DatabaseResetPolicy` | 测试数据库重置策略 | 仅显式集成夹具可创建、迁移、加锁或重置数据库；重置目标名必须以 `_test` 结尾，否则拒绝。 |
| `OfflineResourceGuard` | 离线资源防护 | 离线层未声明外部资源时，任何数据库、缓存、消息队列或网络连接尝试都必须立即失败并指出违规测试。 |

`TestLayer` 保持原始六类契约。`docs/standard/测试规范.md` 规定的 `path_test`、`class_inheritance_test`、`initialization_test`、`exception_test`、`convention_usage_test` 和 `ad_hoc_test` 继续按既有目录组织，并分别归入离线快速验证或显式依赖执行档，不擅自扩展/改写上述枚举口径。

目标 marker 与显式集成夹具边界如下；片段只界定资源申请、安全校验和环境隔离口径，数据库准备细节沿用迁移后的单一实现：

```toml

pythonpath = ["."]
testpaths = ["test"]
# 注册真实外部资源标记，未显式声明的测试不得申请对应资源。
markers = [
    "postgres: 需要真实 PostgreSQL 的集成或性能测试",
    "redis: 需要真实 Redis 的集成或性能测试",

    "docker: 需要真实 Docker/Compose 的集成或性能测试",
```

```python
from contextlib import contextmanager


@contextmanager
def _prepared_integration_database(database_url: str) -> Iterator[None]:
    """在单一锁边界内准备并使用显式集成测试数据库。"""
    TEST_DATABASE_LOCK_DIRECTORY.mkdir(exist_ok=True)
    with portalocker.Lock(
        str(TEST_DATABASE_LOCK_PATH),
        timeout=TEST_DATABASE_LOCK_TIMEOUT_SECONDS,
    ):
        _ensure_test_database_exists(database_url)
        result = DatabaseMigrationCli().execute()
        if (
            result.detail.status != MigrationJobStatus.SUCCESS
            or result.detail.exit_code != DATABASE_MIGRATION_EXIT_SUCCESS
        ):
            raise RuntimeError("测试数据库迁移失败。")
        yield


@pytest.fixture
def postgres_database(
    request: pytest.FixtureRequest,
    monkeypatch: pytest.MonkeyPatch,
) -> Iterator[str]:
    """仅为显式声明 PostgreSQL 的测试准备安全测试库。"""
    if request.node.get_closest_marker("postgres") is None:
        pytest.fail("postgres_database 夹具必须与 postgres marker 同时使用")

    database_url = _build_default_test_database_url()
    _, database_name = _build_maintenance_conninfo(
        _to_psycopg_conninfo(database_url)
    )
    if not database_name.endswith(TEST_DATABASE_NAME_SUFFIX):
        raise RuntimeError("仅允许创建、迁移或重置名称以 _test 结尾的数据库")

    # 环境覆盖由 pytest 在当前测试结束时恢复，不污染其他执行档。
    monkeypatch.setenv("DATABASE_URL", database_url)
    with _prepared_integration_database(database_url):
        yield database_url
```

原始强类型契约在测试代码中的目标骨架如下；公共模型拒绝未知字段，场景和调参结果不得退化为自由格式 `metadata`：

```python
from enum import StrEnum
from typing import Annotated, Literal

from pydantic import BaseModel, ConfigDict, Field


class TestLayer(StrEnum):
    """测试层级，决定测试是否允许申请真实外部资源。"""

    UNIT = "unit"
    CONTRACT = "contract"
    BOUNDARY = "boundary"
    INTERFACE = "interface"
    INTEGRATION = "integration"
    PERFORMANCE = "performance"


class SteadyLoadScenarioDetail(BaseModel):
    """稳定负载场景扩展字段。"""

    model_config = ConfigDict(extra="forbid")
    kind: Literal["steady"] = "steady"
    schema_version: Literal["1.0"] = "1.0"


class BurstLoadScenarioDetail(BaseModel):
    """突发负载场景扩展字段。"""

    model_config = ConfigDict(extra="forbid")
    kind: Literal["burst"] = "burst"
    schema_version: Literal["1.0"] = "1.0"


class OverloadScenarioDetail(BaseModel):
    """过载场景扩展字段。"""

    model_config = ConfigDict(extra="forbid")
    kind: Literal["overload"] = "overload"
    schema_version: Literal["1.0"] = "1.0"


class DependencyDegradedScenarioDetail(BaseModel):
    """依赖降级场景扩展字段。"""

    model_config = ConfigDict(extra="forbid")
    kind: Literal["dependency_degraded"] = "dependency_degraded"
    schema_version: Literal["1.0"] = "1.0"


LoadScenarioDetailUnion = Annotated[
    SteadyLoadScenarioDetail
    | BurstLoadScenarioDetail
    | OverloadScenarioDetail
    | DependencyDegradedScenarioDetail,
    Field(discriminator="kind"),
]


class ResourcePeak(BaseModel):
    """记录调参轮次已观测到的资源峰值。"""

    model_config = ConfigDict(extra="forbid")
    cpu_percent: float
    memory_bytes: int
    thread_count: int
    connection_count: int


class TuningTrialDetail(BaseModel):
    """记录单轮候选参数、测量结果和晋升结论。"""

    model_config = ConfigDict(extra="forbid")
    candidate: RuntimeCapacityPolicy
    throughput_per_second: float
    latency_p50_ms: float
    latency_p95_ms: float
    latency_p99_ms: float
    error_rate: float
    resource_peak: ResourcePeak
    conclusion: str
    promotion_status: Literal["promoted", "rejected", "candidate"]
```

`RuntimeCapacityPolicy` 沿用 Phase 1 的容量策略契约；正式场景 detail 再按对应负载的确定字段补齐输入，不得改用开放字典。

## 分步骤执行方案

### 步骤 1：冻结测试映射与验收基线

将 Phase 1 每个整改批次、P0/P1 发现、外部契约和风险项映射到测试层级、成功/拒绝/异常/边界路径、目标文件和验收断言；同时盘点现有 `unit_test`、`path_test`、`class_inheritance_test`、`initialization_test`、`integration_test`、`interface_test`、`contract_test`、`exception_test`、`boundary_test`、`convention_usage_test`，只结构化归并重复覆盖，不删减原始语义。

验收点：每项 Phase 1 改动均有唯一可追踪测试责任；所有新增功能至少具备单元、路径、异常、边界测试，涉及继承/初始化/外部联动/公开接口/跨系统契约时补齐对应专类测试。

### 步骤 2：一次性硬切换夹具与外部资源标记

移除 `test/conftest.py` 的 session/autouse 数据库准备；将数据库 URL 装配、创建、迁移、锁、重置迁入 integration 专用显式夹具，并注册 `postgres/redis/rabbitmq/docker` marker。加入离线资源防护，确保未声明资源的测试无法连接外部服务。修正夹具和测试源码中的乱码中文注释/文档字符串，保留其关键语义。

当前源码证据：`test/conftest.py` 的 `_prepare_test_database` 使用 `@pytest.fixture(scope="session", autouse=True)`，并在全局测试会话执行 `portalocker.Lock`、数据库创建/重置及 `DatabaseMigrationCli().execute()`；这正是无 PostgreSQL 时全部离线测试被阻断的根因。硬切换后不保留该 autouse 路径。

验收点：测试收集无 marker 警告；断开全部外部服务后离线层不触发数据库夹具；非 `_test` 数据库重置请求被拒绝；测试环境变量不污染父进程或其他执行档。

### 步骤 3：完成离线快速层与 P0/P1 历史回归

为每项 P0/P1 根因修复补最小复现、成功、拒绝和历史回归测试。unit 使用 fake/mock/stub 隔离数据库、网络、文件系统和消息队列；path 覆盖关键分支、提前返回和错误路径；exception 验证异常类型、信息、状态一致性及补偿/回滚/降级；boundary 覆盖下/上/越界值与空、单个、多个集合；initialization 覆盖正常、缺失/非法配置、重复/延迟/失败初始化；class inheritance 验证父类契约、重写和多态。

验收点：unit/contract/boundary 在无 PostgreSQL、Redis、RabbitMQ 时可独立运行；错误外连防护测试可准确指出违规用例；关键路径不存在只执行不断言或依赖测试顺序/共享状态的用例。

### 步骤 4：完成契约、分层、资源生命周期与并发回归

补公共头与 Pydantic 判别联合的已知类型、未知 `kind`、未知字段拒绝、`schema_version` 版本兼容、外内类型不一致和序列化往返测试；接口测试对每个公开接口至少覆盖成功、参数错误、异常/失败，并断言状态码、结构和关键字段。补 import 分层、组合根、资源热交换、并发 reload、重复 shutdown、线程池/连接池耗尽、取消、超时和资源释放测试。

验收点：`core/domain/application` 不依赖 `api/infrastructure`，`infrastructure` 不依赖 API 路由常量；契约满足公共头、判别联合、`kind`、`schema_version`、`extra="forbid"` 和外内类型一致；并发与取消路径无泄漏、死锁或未释放资源。

### 步骤 5：完成事务、幂等、安全与部署行为回归

补事务 Outbox、重复投递、发布确认不确定、进程中断恢复、幂等键冲突、迁移前后兼容测试；明确 UoW 是唯一事务边界，Repository 不得 `commit()`/`rollback()`/释放外层会话。补鉴权越权、RBAC 权限矩阵、SSRF/DNS 重绑定、代理头伪造、CORS、请求体、日志/指标泄密和生产 fail-closed 负向测试。补生产镜像/Compose、健康检查、迁移 gate、优雅停机和配置样例 smoke test。

验收点：失败路径能证明回滚、幂等、恢复、脱敏和 fail-closed；镜像/Compose smoke 用例可被 Phase 3 在真实环境直接执行，且不会混入离线层。

### 步骤 6：建立性能场景与 autotuner

使用 Locust 等成熟工具在 `test/performance/scenarios/` 建立稳定、突发、过载和依赖退化强类型场景；在 `test/performance/autotuner/` 实现关键容量参数自动搜索，不盲调。每轮记录配置、吞吐、p50/p95/p99、错误率、资源峰值、结论和晋升状态，输出最优/失败配置对比与“是否值得继续”结论。后续调整只依据这些元数据；仅多轮、不同种子/负载均稳定且无明显过拟合或资源风险的结果可晋升。

验收点：autotuner dry-run 生成符合 `TuningTrialDetail` 的合法轮次记录、最优/失败对比和继续/淘汰结论；自由格式 `metadata` 被拒绝。Phase 2 只验证框架与 dry-run，真实多轮基准归 Phase 3。
