# Phase 1：生产级代码审查与硬整改分步骤执行方案

> 2026-07-16 最终复核：本阶段实现与当前基线验证已完成。代码、覆盖率、静态、安全、迁移、镜像、负载、模块审查索引和公开契约快照均绑定 `66dbff1e97561b4620af04de7930ef9e3fc7a8f786a33a35a318a9652a9dffc0`。

## 阶段目标与完成边界

建立可回滚、可量化的审查基线，完成全工作区逐层审查和 P0/P1 清零；以二级模块重构消除已确认的职责膨胀与反向依赖，并补齐生产安全、交付门禁和高并发所需的资源治理能力。阶段结果保持现有外部行为兼容。

本阶段是一次性硬迁移：基线和契约冻结后，在同一整改版本内完成目标结构切换，不引入新旧实现并行、双写/双读、功能开关或分批流量迁移。原方案要求保留的 `SharedResourceMount` 薄组合门面和 `AppSettingsLoader` 配置兼容入口，是最终稳定边界，不是临时兼容层；HTTP 路径、状态码、响应语义、配置键、数据库兼容性和任务消息语义保持不变。

当前基线仅能判定“基础能力较完整，但尚未达到可证明的生产就绪状态”：历史 P0/P1 整改已有基础，语法编译、锁文件及两套 Compose 配置校验通过；但全量 `pytest -q` 曾因会话级自动数据库夹具在 PostgreSQL 不可用时产生 `698 errors, 4 skipped`，所有单元测试被外部数据库阻断；静态检查、类型、覆盖率、依赖漏洞、架构依赖和持续集成门禁尚不完整。`shared_resource_mount.py`、`app_settings_loader.py`、管理员身份路由与仓储是已确认热点，另有 infrastructure 反向依赖 api、`portalocker` 未直接声明及少量乱码文档字符串等问题。因此不得在重新核验并清零前声明不存在 P0/P1。

## 依赖关系与执行顺序

| 依赖 | 用途 | 进入条件 |
|---|---|---|
| 当前源码、迁移、配置、容器入口及历史整改记录 | 审查与根因修复事实源 | 以当前源码与迁移为最高优先级 |
| 可回滚版本基线 | 支撑二级模块重构与整批回退 | 当前无可用 `.git` 元数据时，必须先接入原仓库或建立本地版本/备份基线，且不覆盖未知历史 |
| Python 3.11、uv、Docker/Compose | 编译、锁文件、容器和真实配置校验 | 版本与命令入口已记录 |
| 冻结的 OpenAPI、数据库 head、配置键、关键响应快照 | 防止硬迁移产生静默外部行为变化 | 跨模块移动前完成冻结 |
| Phase 2 | 承接稳定整改批次的测试建设 | 仅在 import-linter 边界通过且 P0/P1 为零后进入 |

内部顺序固定为：**审查冻结 → P0/P1 → 契约/分层 → 热点模块拆分 → 生产与并发基建 → P2/P3 收口**。公共契约、数据结构、跨模块调用链、删除、重命名和迁移均须先完成引用分析、影响面判断与关键路径验证；不得用“硬迁移”跳过风险判断。

## 阶段契约

| 英文名 | 中文名 | 中文说明 |
|---|---|---|
| `ContractHeader` | 公共契约头 | 统一承载契约标识、业务主键/追踪字段和外层类型；不得承载可变扩展字典。 |
| `ContractDetailUnion` | 强类型扩展联合 | 使用 `Annotated[Union[...], Field(discriminator="kind")]` 表达扩展模型，只包含业务允许的具体类型。 |
| `kind` | 扩展类型 | 每个扩展模型使用唯一 `Literal` 判别值；外层声明必须与内层实际类型一致。 |
| `schema_version` | 契约版本 | 每个扩展模型必须显式提供 `Literal` 版本，用于兼容和迁移判断。 |
| `model_config` | 模型约束 | 公共头、扩展模型和外层 envelope 全部使用 `ConfigDict(extra="forbid")`。 |
| `RuntimeCapacityPolicy` | 运行时容量策略 | 强类型描述数据库池、线程池、HTTP 池、任务 worker、队列上限、超时和过载行为；环境覆盖必须校验一致性。 |
| `FindingSeverity` | 问题等级 | 固定为 `P0/P1/P2/P3`；P0/P1 阻断生产就绪结论。 |

## 强制约束

1. 事实优先级为：当前源码与迁移 > 可执行配置与测试 > 当前项目手册 > 历史方案；冲突时按源码整改并标注文档可能过期。
2. 审查必须覆盖正确性、可读性、扩展性、维护性、稳定性、安全性、性能基建、数据一致性、部署和供应链；问题按 P0/P1/P2/P3 分级，P0/P1 先于结构优化。
3. 公共契约采用“公共头字段 + 强类型扩展字段”；禁止 `dict[str, Any]`、`metadata`、`extra_payload`，外层类型、判别值与内层扩展类型一致。
4. 使用 Python 3.11+ 现代类型标注；稳定结构分别使用 Pydantic、dataclass 或 TypedDict。接口层、应用层、领域层、核心契约和基础设施层分离，函数按基础动作、过程、编排、分发、入口、转换、校验、清理、持久化等单一主角色设计。
5. UoW 是持久化链路唯一提交、回滚与会话释放边界；只有 UoW 可执行 `commit()`、`rollback()` 与 `dispose()`。Repository 只读写并抛出无法处理的数据库异常，不得提交、回滚或释放外层会话；确需暴露数据库约束错误时可 `flush()`，但不得吞异常。
6. 单元、契约和边界测试不得依赖 PostgreSQL、Redis、RabbitMQ 或网络；集成测试使用显式 marker/fixture。不得扩大 ignore、降低阈值、删除断言、吞异常或隐藏错误以通过门禁。
7. 总体 line/branch 覆盖率不低于 85%，auth/security/task/persistence 关键路径不低于 90%；新增和变更分支覆盖成功、拒绝、超时、回滚、幂等与资源释放。
8. 生产安全默认 fail closed：密钥不入库、不入日志；鉴权、RBAC、SSRF、代理头、CORS、限流、请求体、迁移和初始管理员入口执行负向测试。镜像必须非 root，并验证最小权限、只读文件系统、资源限制和优雅停机。
9. 高并发以可扩展基建为目标：连接池、线程池、HTTP 池和队列有界；超时、背压、熔断或降级、幂等、横向扩容和低基数指标可配置、可观测、可测试。同步数据库访问继续由有界线程池隔离；无基准证据不得切换数据库并发模型。
10. 若进入参数调整，必须在 `test/performance/autotuner/` 自动搜索并逐轮记录配置、吞吐、p50/p95/p99、错误率、资源峰值、结论、最优/失败配置对比及是否继续；仅多轮、不同种子/负载稳定结果可晋升。
11. 清理 `__pycache__`、`tmp_pycache`、空数据库、日志等工作区产物，但不得把产物清理冒充业务整改；依赖直接声明，锁文件保持可复现。

### 步骤 1：建立可回滚基线并冻结外部契约

**目标与动作：**建立版本/备份基线；生成源码、依赖、配置、迁移、路由、任务、资源和测试清单；冻结当前 OpenAPI、数据库 head、配置键与关键响应快照。记录 Python、uv、Docker/Compose 版本和所有复现命令。当前没有可用 `.git` 元数据时，先接入原仓库或建立不覆盖未知历史的本地版本基线，再允许跨模块移动。

**依赖：**当前工作区及上述工具链。

**验收点：**基线可恢复；清单和快照可机器比对；后续每批改动均可关联到唯一基线。

### 步骤 2：逐层审查并复核历史高危修复

**目标与动作：**逐层审查 `api/application/domain/core/infrastructure` 的依赖方向、异常、事务、并发、资源释放、日志脱敏和失败降级，形成带文件行号、触发条件和复现方式的 P0-P3 清单。复核历史 P0/P1 是否仍在真实主链路生效，重点覆盖鉴权/RBAC、SSRF、代理 IP、刷新令牌、初始管理员、RuntimeBundle、Outbox、密钥环和日志缓冲。

**依赖：**步骤 1 的冻结基线；以真实调用链和可执行结果为证据，不以历史报告替代复核。

**验收点：**每项发现具有严重级别、影响面、证据、复现、根因、处置状态；不存在“未审查即通过”。

### 步骤 3：根因修复全部 P0/P1

**目标与动作：**先修全部 P0/P1；每项采用根因修复并附定向校验，不叠加跨层特判。对异常、事务、幂等、资源释放和安全 fail-closed 路径分别证明成功与拒绝行为；禁止以降级门禁、扩大 ignore、删断言或吞异常收口。

**依赖：**步骤 2 的结构化问题清单；每个改动先完成影响面与引用分析。

**验收点：**旧实现可复现、新实现定向检查通过、关联 contract/boundary/unit 检查通过；P0/P1 未关闭项为零。

### 步骤 4：统一公共契约并纠正分层依赖

**目标与动作：**全量审查公共契约，统一公共头与 Pydantic 判别联合；清除开放扩展字典及外内类型不一致，版本变化提供兼容测试。将授权策略与受保护 scope 从 API 路由模块一次性迁至 domain/core/application；移除 infrastructure 对 api 的反向依赖，并在 import-linter 固化 `core`、`domain`、`application` 不依赖 `api`/`infrastructure` 的边界。

**依赖：**步骤 3 已清除阻断性正确性/安全问题；步骤 1 快照用于验证外部行为不变。

**验收点：**契约满足 `ContractHeader`、判别联合、`kind`、`schema_version`、`ConfigDict(extra="forbid")` 和外内类型一致；无 `dict[str, Any]`、`metadata`、`extra_payload`；import-linter 无反向依赖；公共 API、配置键、迁移 head 无未声明变化。

### 步骤 5：一次性完成三个热点模块重构

**目标与动作：**在同一硬迁移版本内完成以下二级模块重构，并删除目标模块内部的新旧双轨实现：

1. 将 `SharedResourceMount` 拆为薄组合门面和按资源域管理器，统一启动、热重载、原子交换、退休资源延迟释放与幂等 shutdown；现有 `src/infrastructure/resource_mount/` 作为目标职责边界的一部分整合，不另建平行生命周期体系。
2. 将 `AppSettingsLoader` 拆为配置域模型、解析、环境覆盖和安全校验；整合现有 `src/infrastructure/settings/parsers/` 等职责，去除重复模型与“预留但不生效”字段，保留唯一配置兼容入口。
3. 将管理员身份 API 路由、契约和仓储实现按 scope/role/user 聚合拆分，复用现有应用层 `src/application/admin/identity/` 用例和公共分页/响应组件，保持 HTTP 路径和状态码不变。

**依赖：**步骤 4 的契约和依赖边界已冻结；跨模块引用、初始化路径、资源所有权和事务边界已分析。

**验收点：**组合根、配置加载、scope/role/user 可独立测试；启动、热重载、并发 reload、原子交换、退休资源释放、重复 shutdown、配置解析/覆盖/安全拒绝、管理员身份成功/拒绝路径通过；Repository 不越过 UoW 事务边界；无临时转发链、双写或双实现残留。

### 步骤 6：依赖、源码与交付物卫生收口

**目标与动作：**补齐直接依赖并移除未使用/过时依赖，至少处理 `portalocker` 非直接声明问题，执行锁文件和供应链审计。修复源码乱码文档字符串，清理生成物和空数据库；完善忽略规则，防止本地密钥、日志、缓存和数据库进入交付物。

**依赖：**热点重构后的最终 import 与运行时依赖图。

**验收点：**直接依赖和实际 import 一致；锁文件可复现；无未豁免高危/严重依赖漏洞；交付物不含敏感或生成产物；中文注释、文档字符串与日志可读。

### 步骤 7：加固生产镜像与 Compose

**目标与动作：**一次性落实非 root、只读文件系统/临时写目录、capability、`no-new-privileges`、资源限制、健康检查、迁移单入口、优雅停机和 Secret 注入边界；生产默认 fail closed。

**依赖：**步骤 5 的唯一组合根和资源生命周期，步骤 6 的确定依赖与锁文件。

**验收点：**生产 Compose/镜像可构建、启动且健康；迁移 gate、非 root、最小权限、只读写边界、资源限制、Secret、SIGTERM 优雅停机和重启恢复检查通过。

### 步骤 8：收口高并发资源治理

**目标与动作：**建立强类型 `RuntimeCapacityPolicy`，统一数据库池、线程池、HTTP 池、任务 worker、队列上限、超时、请求/队列背压、幂等、低基数指标和横向扩容无状态边界；环境覆盖必须一致校验。同步数据库访问继续通过有界线程池隔离，无基准证据不得切换数据库并发模型。

**依赖：**步骤 5 的资源管理器和步骤 7 的容器资源边界。

**验收点：**线程池/连接池/HTTP 池/任务队列均有界；耗尽、超时、取消、重复请求、过载和依赖退化按契约拒绝/背压/降级，无无界增长、泄漏或敏感高基数指标。确需调参时，autotuner 元数据与晋升规则完整，不盲调。

### 步骤 9：固化统一质量与 CI 门禁

**目标与动作：**在 `pyproject.toml`/`noxfile.py` 接入 Ruff、Mypy、import-linter、Bandit、pip-audit、pytest-cov 和统一 nox/CI 入口，保证本地与流水线命令一致；测试执行遵守“最小失败集 → 阶段相关测试集 → 依赖型集成测试 → 全量测试”。

**依赖：**步骤 4-8 的最终模块、依赖与配置布局。

**验收点：**编译、格式/静态检查、类型、架构依赖、安全、锁文件、覆盖率入口可重复运行；总体 line/branch ≥ 85%，auth/security/task/persistence ≥ 90%；不得通过降低门禁获得通过。

### 步骤 10：处置 P2/P3 并执行阶段出口校验

**目标与动作：**对 P2/P3 逐项决定立即整改、延期或淘汰；延期项记录负责人语义、风险、前置条件和重新晋升标准。汇总每个整改批次的证据，执行阶段出口命令与快照比对。

**依赖：**步骤 1-9 全部完成。

**验收点：**P0/P1 为零；P2/P3 全部有明确处置；import-linter 不再发现低层依赖高层；公共 API、配置键和迁移 head 无未声明变化；满足进入 Phase 2 的稳定契约条件。
