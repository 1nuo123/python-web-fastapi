## 阶段目标

- 直接问题:对照本次目标(可读/扩展/维护/稳定/安全/审计/监控告警/单机并发基建)复审 `src/`、`config/`、`noxfile.py`、Compose 与 CI,确认除已识别三缺口外是否存在新的 P0/P1。
- 中间结果:一份结构化发现清单(等级、触发条件、影响面、处置),冻结 Phase 2-4 的整改范围;上一轮 P3 遗留项(第三方弃用 warning、业务负载基准、REG-023)复核后维持 P3 跟踪,不纳入本轮阻断。

## 阶段契约

本阶段不改代码,仅固化审查口径中引用的既有契约事实:

| 英文名 | 中文名 | 中文说明 |
|---|---|---|

## 分步骤执行规划

1. 复审 core 契约层:判别联合、`extra="forbid"`、外内一致性校验是否全覆盖。
2. 复审 infrastructure 并发与资源边界:`RuntimeCapacityPolicy` 挂载点、线程池/连接池/队列有界性。
3. 复审安全链路:中间件顺序、fail-closed 行为、脱敏、token 绑定、SSRF/限流/封禁。
4. 复审审计链路:确认审计事件从产生到落库的全路径与丢失窗口。
5. 复审可观测链路:指标、日志缓冲、OTel 桥接的覆盖面。
6. 产出发现清单并给每项定级(P0/P1 阻断、P2 修复、P3 跟踪),固化进本文档修订(即原始方案文档 `docs/2026_7_20_2133_生产级完整性闭环审查与整改执行方案.md` 的修订)。

## 验收点

- 发现清单每项均有源码行级证据与复现入口。
- 三个已知缺口(审计丢失窗口、指标覆盖、告警基线)在清单中定级为 P1,范围与 Phase 2-4 一一对应;若出现新 P0/P1,先扩阶段再动码。

## 关联的全局验收标准

- 复审发现清单结构化状态为 `open=0`,P0/P1 全部 verified 或有根因修复加当前回归证据。
