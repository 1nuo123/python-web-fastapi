# 业务审计查询重做_分步骤执行方案

## 1. 阶段目标

新增业务审计查询，替代业务后台里的原始日志与安全事件页面。完成后，业务管理员只能看到业务操作审计，而不是底层系统日志、异常堆栈或安全事件细节。

## 2. 全局约束

- 若文档、图谱、源码冲突，以当前源码为准；旧管理员服务端方案中的后台暴露范围已可能过期，回归时必须同步修正。
- `/admin/*` 只表示业务管理后台；平台、运维、安全控制面后续如保留，必须迁移到默认关闭的 `/ops/*` 或 CLI。
- 默认 `config/app_base.toml` 不启用 `admin_task`、`admin_settings`、`admin_log`、`security_protection`、`system_overview` 作为业务后台模块。
- 通用任务派发、配置热重载、任意 scope CRUD、任意角色权限组合编辑、原始日志、安全事件、指标、IP 封禁、运行时资源不得暴露给业务管理员。
- 所有 list API 必须具备分页契约，过滤、排序、分页下推 SQL；禁止只在内存中过滤后截断。
- 契约必须使用“公共头字段 + 强类型扩展字段”：扩展字段使用 Pydantic 判别联合，扩展字段必须包含 `kind`、`schema_version`，必须启用 `extra="forbid"`。
- 禁止在契约中使用 `dict[str, Any]`、`metadata`、`extra_payload`；外层 `header.kind/schema_version` 必须与内层扩展类型一致。
- 日志、异常、注释和文档使用中文；响应、日志、审计不得泄漏密码、token、密钥、完整 IP、完整 user-agent 或底层任务 payload 原文。

## 3. 阶段依赖关系

- Phase 1 是业务后台与 ops 控制面的边界基础，后续阶段均依赖它。
- Phase 2 依赖 Phase 1，并依赖现有 `admin_identity` 用户、角色、scope 数据模型。
- Phase 3 依赖 Phase 1 和 Phase 2，并依赖现有安全事件、日志或新增业务审计总线的最终选择。
- 本阶段依赖现有日志/安全事件能力或新增业务审计总线。若审计文档、旧日志方案与源码冲突，以源码为准。

## 6. 契约

| 英文名 | 中文名 | 中文说明 |
|---|---|---|
| AdminAuditHeader | 业务审计公共头 | 承载 `kind`、`schema_version`、`operation_name`，与扩展字段一致 |
| AdminAuditEventPayload | 业务审计事件载荷 | 返回业务可读动作、操作者、目标对象、结果、发生时间，不返回原始日志详情 |
| AdminAuditEventListPayload | 业务审计列表载荷 | 带分页的审计事件集合 |
| AdminAuditAction | 业务审计动作枚举 | 如 `user_disabled`、`password_reset`、`role_assigned`、`business_object_changed`、`business_action_triggered` |
| AdminAuditQuery | 业务审计查询 | 支持操作者、目标类型、目标 ID、动作、时间范围、分页 |

## 7. 分步骤执行方案

### 步骤 1：新增业务审计 API 边界

- 新增 `endpoint_admin_audit` 模块。
- 新增 `contract_admin_audit.py`，定义业务审计 HTTP 契约。
- 新增 `route_admin_audit.py`，提供 `GET /admin/audit-events` 查询路由。
- 路由只返回业务审计事件，不返回 `SecurityEventEnvelope` 和 `LogEventEnvelope` 原始 detail。

### 步骤 2：新增应用用例与查询端口

- 新增 `AdminAuditQueryPort`。
- 新增 `application/admin/audit/list_admin_audit_events_usecase.py`。
- 在依赖上下文与 FastAPI 组装处按需注入业务审计查询用例。
- 若业务审计落库查询需要，新增 `admin_audit_repository_impl.py`；否则以现有日志表强类型映射输出业务审计视图。

### 步骤 3：接入身份管理业务审计写入

- 将用户停用、启用、密码重置、角色分配接入业务审计。
- 审计动作纳入白名单，如 `user_disabled`、`password_reset`、`role_assigned`、`business_object_changed`、`business_action_triggered`。
- 敏感字段只保留摘要或业务说明，不返回密码、token、密钥、完整 IP、完整 user-agent。

### 步骤 4：实现查询过滤与分页

- 审计查询支持分页、时间范围、动作、操作者、目标对象过滤。
- 过滤、排序、分页下推 SQL。
- 如需要新表或索引，新增 migration。

### 步骤 5：补充测试与验收

- 新增契约测试：覆盖 `AdminAuditEnvelope` 判别联合、分页响应、敏感字段不出现。
- 新增单元测试：覆盖查询对象边界、动作白名单、分页过滤顺序。
- 新增接口测试：覆盖 `/admin/audit-events` 权限、过滤、分页、脱敏。
- 回归默认 OpenAPI：原始 `/admin/logs`、`/admin/security-events` 不在默认业务后台 OpenAPI 中出现。

## 9. 校验 / 验收点

- `/admin/audit-events` 只返回业务审计事件。
- 原始 `/admin/logs`、`/admin/security-events` 不在默认业务后台 OpenAPI 中出现。
- 审计查询先过滤后分页。
- 审计响应不包含异常堆栈、原始安全事件 detail、任务 payload 原文和敏感值。
- 新增或改造后的 `/admin/audit-events` 只返回业务管理员可读的业务审计事件，并具备分页。
