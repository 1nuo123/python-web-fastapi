# Repository 事务边界与缓存策略规范执行方案

## 任务目标
交付一份后续真实改码与测试回归方案，解决两个直接问题：

- Repository 内部不得自行 `commit()` / `rollback()`，尤其是 `TaskExecutionRecordRepositoryImpl.upsert()` 不能在更大的 UoW 中回滚无关变更。
- 补齐缓存三类运行约定：key namespace 规范、TTL 默认策略、Redis 不可用时的 fail-open / fail-closed 策略。

完成判定是：源码、测试、文档都明确表达“事务边界由 UoW 控制，repository 只做读写并向上抛异常”；认证与限流类缓存 Redis 不可用时 fail-closed，普通查询缓存可 fail-open。

## 全局约束
- 以源码为准；若文档、图谱、历史执行方案与源码冲突，以源码执行，并说明旧文档可能过期。
- `src/core` 只放契约，`src/application` 只放用例和端口，`src/infrastructure` 放实现、装配、持久化。
- UoW 是唯一事务边界：只有 UoW 可以 `commit()`、`rollback()`、`dispose()`；repository 禁止调用 `commit()` / `rollback()`。
- Repository 允许 `flush()` 暴露数据库约束错误，但不得吞异常，不得通过回滚外层事务恢复状态。
- 若必须处理并发去重冲突，优先使用不污染外层事务的数据库原子语句；否则向上抛异常，由 UoW 调用方决定回滚。
- 契约采用“公共头字段 + 强类型扩展字段”规则。
- 扩展字段必须使用 Pydantic 判别联合，必须包含 `kind`、`schema_version`，必须启用 `extra="forbid"`。
- 禁止用 `dict[str, Any]`、`metadata`、`extra_payload` 承载稳定协议。
- 外层类型与内层扩展类型必须一致，至少校验 `detail_kind == detail.kind`、`schema_version` 一致。
- 缓存 key 统一形态为 `key_prefix:namespace:segment...`；片段不能为空，不能包含分隔符，不能直接包含令牌、密码等敏感原文。
- TTL 解析顺序为：请求显式 TTL > 命名空间策略默认 TTL > `runtime.cache.default_ttl_seconds`；所有 TTL 必须大于 0。
- Redis 不可用策略必须按功能分类：认证、鉴权、限流 fail-closed；普通查询缓存可 fail-open。
- 日志使用中文，记录必要上下文，但不得泄露密钥、令牌、密码、完整 Redis URL。

## 验收标准
- `src/infrastructure/persistence/repository_impl/` 下 repository 实现不直接调用 `commit()` / `rollback()`。
- `TaskExecutionRecordRepositoryImpl.upsert()` 遇到数据库约束异常时不回滚外层 session。
- 任务执行记录重复预占、异常预占、外层 UoW 组合写入场景都有测试覆盖。
- 缓存命名空间、key 片段、TTL、后端扩展字段都通过强类型契约校验。
- Redis 不可用时，认证与限流相关路径返回失败，不发放令牌、不放行请求。
- Redis 不可用时，标记为 fail-open 的普通查询缓存按未命中处理，不能影响主查询结果。
- 单元、路径、异常、初始化、集成回归测试全部通过。
- `docs/standard/编码规范.md` 与 `docs/design_docs/FastAPI统一Web基础设施实现规格.md` 已同步新规范。

## Phase 1
### 目标
收口 repository 与 UoW 的事务边界，消除 repository 内部 `rollback()` 回滚外部事务的风险。

当前阶段完成后，`TaskExecutionRecordRepositoryImpl.upsert()` 只负责读写与抛错；提交、回滚、释放全部由 UoW 调用方控制。

### 依赖
- 现有 `UnitOfWork`、`SqlAlchemyUnitOfWork`、`Repository` 抽象。
- 现有 `TaskExecutionRecordRepositoryImpl`、`TaskExecutionStore.reserve()`。
- 现有 `task_execution_record` 的唯一约束 `uq_task_execution_record_job_kind_deduplication_key`。

### 契约
| 英文名 | 中文名 | 中文说明 |
|---|---|---|
| `UnitOfWork` | 工作单元 | 唯一事务边界，负责 `commit()`、`rollback()`、`flush()`、`dispose()`。 |
| `Repository` | 仓储 | 只负责持久化读写，不直接提交或回滚事务；无法处理的数据库异常直接向上抛出。 |
| `TaskExecutionRecordRepositoryImpl.upsert` | 执行记录预占 | 已存在记录返回 `created=False`；新记录写入成功返回 `created=True`；约束冲突异常不自行回滚。 |
| `TaskExecutionRecordUpsertResult` | 执行记录写入结果 | 表达预占结果与是否新建，不承载事务状态。 |
| `IntegrityError` | 完整性异常 | 数据库约束冲突语义，由 UoW 调用方决定是否回滚当前工作单元。 |

### 任务清单
- [x] 修改 `repository_contract.py`，明确 repository 禁止 `commit()` / `rollback()`。
- [x] 修改 `unit_of_work_contract.py`，明确 UoW 是唯一事务边界。
- [x] 修改 `TaskExecutionRecordRepositoryImpl.upsert()`，移除 `self._session.rollback()`。
- [x] 保留“预查询命中则复用记录”的普通幂等路径。
- [x] 对 `IntegrityError` 只做必要上下文保留或直接抛出，不在 repository 内恢复 session。
- [x] 检查 `src/infrastructure/persistence/repository_impl/` 下其他 repository，确认没有新增事务控制。
- [x] 如后续必须实现并发冲突复用，单独设计数据库原子 upsert，不使用 catch + rollback + query。

### 关键代码片段
```python
def upsert(
    self,
    record: TaskExecutionRecordOrmModel,
) -> TaskExecutionRecordUpsertResult:
    existing_record = self.get_by_job_and_deduplication_key(
        job_kind=record.job_kind,
        deduplication_key=record.deduplication_key,
    )
    if existing_record is not None:
        return TaskExecutionRecordUpsertResult(record=existing_record, created=False)

    self._session.add(record)
    self._session.flush()
    return TaskExecutionRecordUpsertResult(record=record, created=True)
```

### 校验
- `rg -n "\.rollback\(|\.commit\(" src/infrastructure/persistence/repository_impl` 不能命中 repository 内部事务控制。
- 重复 `job_kind + deduplication_key` 的已存在记录仍返回 `created=False`。
- 模拟 `flush()` 抛出 `IntegrityError` 时，repository 不调用 `session.rollback()`。

### 契约
| 英文名 | 中文名 | 中文说明 |
|---|---|---|
| `CacheNamespace` | 缓存命名空间 | 统一枚举缓存用途，如 `auth_throttle`、`rate_limit`、`query_result`。 |
| `CachePolicyHeader` | 缓存策略公共头 | 包含 `kind`、`schema_version`、`detail_kind`、`namespace`，用于约束外层策略类型。 |
| `AuthThrottleCachePolicyDetail` | 鉴权节流缓存策略扩展 | 扩展字段包含 `kind`、`schema_version`、`default_ttl_seconds`，固定 fail-closed。 |
| `RateLimitCachePolicyDetail` | 限流缓存策略扩展 | 扩展字段包含 `kind`、`schema_version`、`default_ttl_seconds`，固定 fail-closed。 |
| `QueryResultCachePolicyDetail` | 查询缓存策略扩展 | 扩展字段包含 `kind`、`schema_version`、`default_ttl_seconds`，允许 fail-open。 |
| `CachePolicyDetailUnion` | 缓存策略扩展判别联合 | 使用 `Field(discriminator="kind")`，所有成员启用 `extra="forbid"`。 |
| `CachePolicyEnvelope` | 缓存策略信封 | 校验 `header.detail_kind == detail.kind`、`header.schema_version == detail.schema_version`、外层 namespace 与内层一致。 |
| `CacheKeyBuilder` | 缓存键构造器 | 统一生成 `key_prefix:namespace:segment...`，拒绝空片段和含分隔符片段。 |

## Phase 3
### 目标
实现 Redis 不可用时的可观察失败策略，确保认证、鉴权、限流 fail-closed，普通查询缓存可 fail-open。

当前阶段完成后，Redis 故障不再只有统一异常行为，而是按命名空间策略稳定处理。

### 依赖
- Phase 2 的 `CachePolicyEnvelope`、`CacheFailureMode`、`CachePolicyResolver`。
- 现有 `RedisCacheStore` 已将 Redis 异常转换为 `system.cache.unavailable`。
- 现有 FastAPI 异常呈现链路。

### 模拟用法
```python
read_result = cache_service.read_payload(
    CacheReadRequest(
        namespace=CacheNamespace.QUERY_RESULT,
        key_parts=["system_overview", "tenant-1"],
        payload_type=QueryResultCachePayload,
    )
)
```

### 契约
| 英文名 | 中文名 | 中文说明 |
|---|---|---|
| `CacheFailureMode.FAIL_CLOSED` | 失败关闭 | Redis 不可用时继续抛出 `system.cache.unavailable`，调用方不得放行关键流程。 |
| `CacheFailureMode.FAIL_OPEN` | 失败开放 | Redis 不可用时读操作按未命中处理，写入与删除记录告警后跳过。 |
| `CacheReadResult` | 缓存读取结果 | fail-open 读失败时返回 `hit=False, payload=None`。 |
| `CacheUnavailableHandling` | 缓存不可用处理 | `CacheService` 内部按 namespace 策略处理 Redis 不可用异常。 |
| `CoreErrorCode.CACHE_UNAVAILABLE` | 缓存不可用错误码 | fail-closed 路径继续使用现有错误码。 |

### 任务清单
- [x] 修改 `CacheService.read_payload()`，捕获 `system.cache.unavailable` 后按策略处理。
- [x] 修改 `CacheService.write_payload()`，fail-open 时记录告警并跳过写入，fail-closed 时继续抛出。
- [x] 修改 `CacheService.delete_payload()`，fail-open 时记录告警并跳过删除，fail-closed 时继续抛出。
- [x] 确认 `AuthFailureThrottle` 使用 `AUTH_THROTTLE` 策略，Redis 不可用时不放行签发与刷新路径。
- [x] 为后续普通查询缓存预留 `QUERY_RESULT` 策略，默认 fail-open。
- [x] 确保日志中只记录 namespace、key 摘要或已规范化 key，不输出敏感原文。
- [x] 保持 `RedisCacheStore.assert_available()` 的启动探活语义，生产 Redis 后端启动不可用仍可按现有策略失败。

### 关键代码片段
```python
try:
    raw_value = self._cache_store.get_value(cache_key)
except HttpFaultException as exc:
    policy = self._policy_resolver.resolve(request.namespace)
    if self._is_cache_unavailable(exc) and policy.failure_mode == CacheFailureMode.FAIL_OPEN:
        self._logger.warning("缓存不可用，已按未命中处理。命名空间：%s。", request.namespace)
        return CacheReadResult(hit=False, payload=None)
    raise
```

### 校验
- Redis 不可用且 namespace 为 `AUTH_THROTTLE` 时，读、写、删均继续抛出 `system.cache.unavailable`。
- Redis 不可用且 namespace 为 `QUERY_RESULT` 时，读返回未命中，写与删不抛异常。
- 认证失败计数依赖 Redis 时，Redis 不可用不能签发访问令牌。
