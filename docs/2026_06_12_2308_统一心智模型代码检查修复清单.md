# 2026_06_12_2308 统一心智模型代码检查修复清单

## 检查结论

本次检查重点不是找零散风格问题，而是找会破坏功能闭环、运行时事实源、权限模型和可维护边界的问题。已过滤开发态噪音，例如 PowerShell 中文显示乱码、缓存目录、日志文件、开发 compose 启动但未必使用的辅助服务。

已启动 6 个 `gpt-5.4 / reasoning_effort=xhigh` 子智能体做差异化检查；其中 Web 主链路、鉴权身份、任务运行时、部署入口 4 条线返回了有效结论，安全/日志线因并发限制中断，配置资源底座超时部分由本地交叉检查补足。源码通过 `python -m compileall -q src`。

## 全局最优方向

优先修 `P1`，再做 `P2` 的边界收口。当前最值得重构的是运行时事实源：`message runtime`、`task runtime`、后台管理可观测面和资源状态命名必须统一，否则后续补丁会继续糊墙。

建议把“声明的运行时配置”收口为唯一事实源，并让管理端接口表达真实生效状态：`task_backend`、`message_backend`、`worker_enabled`、注册项是否对当前后端生效。

## 修复清单

### 1. P1 内置授权 scope 可被禁用，可能把后台自锁死

- 定位：`src/infrastructure/persistence/repository_impl/admin_identity_repository_impl.py:153`，`src/infrastructure/persistence/repository_impl/auth_identity_repository_impl.py:186`，`src/api/admin_route_authorization.py:46`
- 根因：`update_scope()` 只禁止删除内置 scope，没有禁止把 `auth:read`、`auth:manage` 等内置 scope 改成 `enabled=false`；鉴权快照又会过滤 disabled scope。
- 前置条件：明确内置 scope 是系统保留能力，不应按普通业务 scope 管理。
- 修复方案：禁止后台接口禁用路由授权依赖的内置 scope；若仍允许编辑，只允许改名称/描述，不允许改 `enabled`。同时补 self-lock 校验，防止当前管理员移除自己继续管理所需权限。
- 验证：`PATCH /admin/scopes/auth:manage` 设置 `enabled=false` 应失败；自定义 scope 仍可禁用；操作后管理员仍能访问 `/admin/users`、`/admin/scopes`。

### 2. P1 生产环境缺少首个管理员的应用内闭环

- 定位：`src/infrastructure/settings/settings_security_validator.py:194`，`src/infrastructure/shared_resource_mount.py:1095`，`src/infrastructure/persistence/repository_impl/admin_identity_repository_impl.py:712`
- 根因：生产环境禁止 `bootstrap_admin.enabled=true`，普通后台身份管理又只允许分配业务角色，拒绝 `admin` 角色，导致生产首个管理员只能靠外部写库或临时改配置。
- 前置条件：定义生产首个管理员的标准建置方式。
- 修复方案：新增受控一次性 CLI 初始化入口，例如 `src.cli.create_initial_admin`；要求显式环境变量/交互确认，创建后幂等或拒绝重复执行。普通后台接口继续禁止把业务用户随意提升为 `admin`。
- 验证：生产配置下 CLI 可创建首个 `admin`；重复执行不会创建第二个超级管理员；普通后台接口仍不能分配 `admin` 角色。

### 3. P1 `message backend=rabbitmq` 但挂载对象仍是 `LocalMessageBus`

- 定位：`src/infrastructure/resource_mount/runtime_resource_bootstrapper.py:381`，`src/infrastructure/shared_resource_mount.py:1394`，`src/infrastructure/shared_resource_mount.py:1440`
- 根因：无论 `runtime.message.backend` 是 `local` 还是 `rabbitmq`，内部都创建 `LocalMessageBus()`；RabbitMQ 只承担探测和 Funboost broker 配置，但资源名仍叫 `shared_message_bus`，管理端也看不到真实后端组合。
- 前置条件：先定清 `message runtime` 是独立消息总线，还是 Funboost/RabbitMQ 的 broker 依赖。
- 修复方案：建议重构为“任务运行时后端组合”模型。若不实现独立 RabbitMQ message bus，就把 `shared_message_bus/get_message_bus` 改名为 local dispatcher channel 或 broker probe，避免伪抽象；同时后台 runtime payload 增加 `message_backend`、`task_backend`、`worker_enabled`、`effective_mode`。
- 验证：`runtime.message.backend=rabbitmq` 时管理端能明确显示 RabbitMQ 只是 broker/probe 或真实消息总线；初始化测试断言资源状态和对象语义一致。

### 4. P2 `security_protection` 路由绕过统一 `RequestExecutionBridge`

- 定位：`src/api/endpoint_security_protection/route_security_protection.py:149`，`:178`，`:219`，`:244`，`:279`
- 根因：该模块的 async 路由直接执行同步 UnitOfWork、仓储和 IP block guard；其他后台模块已统一通过 `read_request_execution_bridge(...).run_sync(...)` 卸载同步主干。
- 前置条件：确认继续采用“async 路由 + 同步用例 bridge”的 Web 主链路。
- 修复方案：把 IP 封禁查询、创建、读取、释放抽成同步 usecase/adapter；路由只负责鉴权、请求契约和 envelope，所有同步业务通过 `RequestExecutionBridge.run_sync` 执行。
- 验证：覆盖 `list/create/get/release` 四类接口，断言经过 `run_sync`；接口响应和状态码保持不变。

### 5. P2 admin 边界策略与授权事实源漂移

- 定位：`src/api/web_module_manifest.py:53`，`src/api/admin_route_authorization.py:61`，`src/api/endpoint_security_protection/route_security_protection.py:119`，`src/api/endpoint_system_overview/route_system_overview.py:81`
- 根因：manifest 标了 `AdminBoundaryPolicy.OPS_ONLY`，但运行时不消费该策略；`security_protection` 和 `system_overview` 的授权要求又内联在路由里，没有进入中心化 `OPS_ONLY_AUTHORIZATION_REQUIREMENTS`。
- 前置条件：确定后台边界唯一事实源是 manifest 还是中心化授权常量。
- 修复方案：把 `system_overview`、`security_protection` 的 requirement 提升到 `admin_route_authorization.py`，路由统一引用；新增 parity 测试，枚举所有非 PUBLIC manifest 项必须有中心化 requirement。若不打算运行时使用 `admin_boundary_policy`，删除这层伪元数据和对应测试。
- 验证：缺少 `security:manage` 时安全防护接口 403；有 scope 时通过；manifest 与中心授权集合一致。

### 6. P2 客户端 IP 读取分散，反向代理部署下安全链路会失真

- 定位：`src/api/endpoint_auth_access/route_auth_access.py:327`，`src/infrastructure/middleware_chain/authentication_binding_middleware.py:177`，`src/infrastructure/security/rate_limit_guard.py:180`，`src/infrastructure/security/security_protection_guard.py:137`，`src/infrastructure/security/ip_block_guard.py:233`
- 根因：token binding、refresh 节流、限流、IP 封禁、安全事件多处直接读 `request.client.host`；在 Nginx/Ingress/ELB 后通常得到代理地址。
- 前置条件：定义可信代理 CIDR 和可接受的转发头策略。
- 修复方案：抽统一 `ClientIpResolver`，只在来源属于可信代理时解析 `Forwarded` / `X-Forwarded-For`，否则回退 `request.client.host`；所有安全链路复用它。
- 验证：可信代理时首跳真实 IP 生效；非可信代理伪造头被忽略；token binding、refresh 节流、IP block 三条链路得到同一 IP。

### 7. P2 后台用户 `scope_codes` 展示与真实鉴权快照不一致

- 定位：`src/infrastructure/persistence/repository_impl/admin_identity_repository_impl.py:648`，对比 `src/infrastructure/persistence/repository_impl/auth_identity_repository_impl.py:186`
- 根因：鉴权快照过滤 disabled scope；后台用户详情/列表直接从角色关联拼 `scope_codes`，会把已禁用 scope 继续显示成用户权限。
- 前置条件：明确后台展示字段表达“绑定权限”还是“生效权限”。
- 修复方案：推荐拆字段：`bound_scope_codes` 表示角色绑定目录，`effective_scope_codes` 表示当前真正生效权限；如果只保留一个字段，应改为生效权限并过滤 disabled scope。
- 验证：禁用某 scope 后，用户详情/列表的生效权限不包含该 scope；合同测试覆盖两个字段的语义。

### 8. P2 任务注册列表只展示当前 task backend，配置巡检不闭环

- 定位：`src/infrastructure/shared_resource_mount.py:1440`，`src/infrastructure/task/task_registration_registry.py:269`，`src/api/endpoint_admin_task/contract_admin_task.py:260`
- 根因：`list_task_registration_snapshots()` 只返回当前 `task_backend` 的注册项；local/funboost 同时配置时，另一套注册对管理员不可见。
- 前置条件：确认管理端承担配置巡检，而不是只展示当前激活项。
- 修复方案：管理接口返回全部注册项，增加 `registration_backend`、`current_runtime_backend`、`active_for_current_runtime`；保留 query 参数用于过滤当前 backend。
- 验证：同时配置 local/funboost 时 `/admin/tasks/registrations` 可看到两套注册，并正确标记激活态。

### 9. P2 Funboost 失败回调缺少执行记录不存在时的兜底

- 定位：`src/infrastructure/task/funboost_task_bootstrapper.py:281`，`src/infrastructure/task/task_execution_store.py:322`
- 根因：消费失败回调直接 `mark_failed(job_kind, deduplication_key, ...)`；如果队列里有历史脏消息或记录已清理，`TaskExecutionStore._update_record()` 找不到记录会抛二次异常，覆盖原始失败。
- 前置条件：允许消费端优雅处理无本地执行记录的外部/历史消息。
- 修复方案：在 Funboost failure callback 中捕获记录缺失，至少写入 `FailedTaskRecorder` 和结构化日志；更稳妥是按消息内容补建一条 FAILED 执行记录。
- 验证：模拟不存在的 `deduplication_key`，断言不会二次抛错，失败仍进入 recorder/log。

### 10. P3 主 ASGI 入口的 task binding 过滤语义失活

- 定位：`src/api/asgi_entry.py:39`，`src/infrastructure/fastapi_app_assembler.py:306`，`src/infrastructure/fastapi_app_assembler.py:359`
- 根因：`create_app()` 未显式传入 `task_bindings` 时，先由 `ApplicationTaskBindingProvider.build()` 返回列表，再传给 assembler；assembler 只有在 `task_bindings is None` 时才过滤未声明 binding，因此真实主入口永远不会走声明过滤分支。
- 前置条件：明确 provider 返回的是默认候选 binding，还是必须原样注册的显式 binding。
- 修复方案：把 provider resolution 下沉到 assembler，或引入 binding source 类型区分“默认候选/显式覆盖”；真实 `create_app()` 应复用 declared-binding 过滤语义。
- 验证：fake provider 返回 declared + stale binding，断言主入口只注册已声明 binding；显式传入 `task_bindings` 时保持覆盖行为。

### 11. P2 生产 Web 运行时缺专用覆盖，默认继承开发 CORS

- 定位：`config/runtime/web_runtime/web_runtime_base.toml:8`，`config/runtime/web_runtime/web_runtime_production.toml` 缺失，`src/infrastructure/settings/settings_security_validator.py:196`
- 根因：base 配置默认启用 CORS，并允许 `http://localhost:3000`、`http://127.0.0.1:3000`；生产环境没有覆盖文件，加载器会跳过缺失文件，安全校验只禁止通配符，不禁止 localhost 来源。
- 前置条件：明确生产环境是否需要浏览器跨域访问及正式域名 allowlist。
- 修复方案：新增 `web_runtime_production.toml`，显式关闭 CORS 或只允许生产域名；把 localhost allowlist 下沉到 `web_runtime_development.toml`；生产校验禁止 localhost/127.0.0.1 示例来源。
- 验证：生产配置加载后不包含 localhost origins；带 `Origin: http://localhost:3000` 的接口烟测不返回允许跨域头。

### 12. P2 Docker、直启、dotenv 的开发数据库名漂移

- 定位：`.env.docker.example:4`，`.env.docker.example:7`，`compose.yml:67`，`config/runtime/database_runtime/database_runtime_development.toml:2`
- 根因：`.env.docker.example` 里 `POSTGRES_DB=fastapi_web_skeleton`，但 `DATABASE_URL` 指向 `fastapi_web_skeleton_dev`；Compose app/migration 又按 `POSTGRES_DB` 连接 `fastapi_web_skeleton`。Docker 开发、直启、配置默认可能落到不同库。
- 前置条件：决定 Docker 开发和本地直启是否共用同一个开发库。
- 修复方案：统一 `POSTGRES_DB`、根 `.env*.example` 的 `DATABASE_URL`、`database_runtime_development.toml` 数据库名；如果刻意分离，拆成两套明确样例和文档，不让 Docker 样例兼做直启 `.env`。
- 验证：`AppSettingsLoader().load_for_environment(DEVELOPMENT)` 与 `docker compose config` 渲染出的数据库名一致；本地直启和迁移任务命中同一库。

### 13. P1 测试夹具默认凭据与 Docker 基线脱节

- 定位：`test/conftest.py:31`，`test/conftest.py:152`，`.env.docker.example:5`，`docs/standard/测试规范.md:369`
- 根因：测试夹具默认 `POSTGRES_PASSWORD=postgres`，但 Docker 样例密码是 `local-dev-postgres-password`；pytest 进程不会自动读取 `.env.docker.example`，按文档启动依赖后直接跑测试容易连错库。
- 前置条件：确定本地测试基线以根 `.env` 为准，还是要求显式 `TEST_DATABASE_URL/POSTGRES_*`。
- 修复方案：让 `test/conftest.py` 与应用启动共用 dotenv/环境变量解析规则；缺省时从根 `.env` 推导测试库连接，不再硬编码 `postgres`；同步更新测试规范。
- 验证：干净 shell 中仅复制 `.env.docker.example` 为 `.env` 并启动 Docker 后，`pytest -q test/unit_test/test_test_database_isolation_unit.py test/integration_test/test_migration_job_integration.py` 可通过。

### 14. P3 过时的 `config/.env.example` 仍作为第二套启动样例残留

- 定位：`config/.env.example:1`，`src/infrastructure/settings/app_settings_loader.py:1999`，`docs/Docker启动运行指南.md:8`
- 根因：当前代码和文档都以仓库根目录 `.env`、`.env.docker.example`、`.env.production.example` 为入口，但 `config/.env.example` 仍保留旧最小样例，容易误导维护者使用失效入口。
- 前置条件：确认没有外部脚本依赖 `config/.env.example`。
- 修复方案：删除该文件，或把内容改成明确弃用提示并指向根目录样例；增加仓库检查，禁止再次出现第二套 env 样例。
- 验证：`rg -n "config/\\.env\\.example|\\.env\\.docker\\.example|\\.env\\.production\\.example" docs src test` 后引用面清晰；本地启动接口测试通过。

## 建议执行顺序

1. 先修 P1：内置 scope 保护、生产首个管理员入口、运行时事实源重构、测试夹具凭据闭环。

4. 最后补可观测与边界回归：任务注册列表、IP resolver、Funboost 失败兜底、scope 展示语义。
