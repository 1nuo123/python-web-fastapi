# Phase 2 鉴权与运行时底座

## 阶段目标
完成认证、数据库、缓存、消息/任务运行时与统一错误码体系，形成可扩展的业务底座。

当前阶段完成后的中间结果：
- `POST /auth/token`、`POST /auth/refresh`、`POST /auth/revoke`、`GET /auth/me` 可工作。
- ORM、缓存、消息/任务具备首版可替换实现。
- 统一错误码、事务、仓储、授权策略形成稳定契约。

## 依赖关系
- 依赖 Phase 1 的统一配置、统一响应、统一异常、依赖注入和测试应用工厂。
- 依赖 `docs/技术选型.md` 中对 ORM、缓存、消息、任务、鉴权的既定方向。
- 既定技术方向可直接对应为：ORM 使用 `sqlalchemy`，缓存使用 `redis` / `cachetools`，消息队列使用 `rabbitmq`，任务队列使用 `funboost`，鉴权方向按 `oauthlib` 既定选择执行。
- 源码现状说明：当前 `src` 仅有 `api`、`application`、`core`、`domain`、`infrastructure` 顶层包和空 `main.py`，`src/core`、`src/infrastructure` 下尚未出现本阶段要求的 contract/runtime 子目录与实现骨架。

## 执行约束提醒
- 命名遵循《命名规范》：具体动作优先，`dispatch` 用于分发，`execute` 用于流程/入口，阶段函数默认私有。
- 编码遵循《编码规范》：稳定结构优先使用 Pydantic，公共函数完整类型标注，使用 Python 3.11+ 现代类型语法，避免裸 `dict` 承载稳定契约。
- 测试遵循《测试规范》：新增功能至少补齐单元测试、路径测试、异常测试、边界条件测试；认证接口补接口测试；契约与错误码补契约测试；数据库、缓存、消息、任务联动补集成测试。

## 契约表
| 英文名 | 中文名 | 中文说明 |
|---|---|---|
| AuthenticatedPrincipal | 认证主体 | 认证成功后的主体信息，包含 `subject_id`、`roles`、`scopes` |
| TokenPayload | 令牌载荷 | `kind="token"`，承载 `sub`、`exp`、`scopes`、`token_use` |
| TokenIssuePayload | 令牌签发扩展体 | `kind="token_issue"`，响应 access/refresh token 信息 |
| AuthorizationPolicy | 授权策略 | 授权规则契约，定义所需 scope、role、资源约束 |
| ErrorCodeCatalog | 错误码目录 | 稳定错误码契约，格式固定为 `<domain>.<scenario>.<reason>` |
| UnitOfWork | 工作单元 | 事务边界契约，定义 `commit`、`rollback`、`dispose` |
| CacheRecordPayload | 缓存记录扩展体 | `kind="cache_record"`，承载 key、ttl、value 类型 |
| TaskMessagePayload | 任务消息扩展体 | `kind="task_message"`，承载任务类型、去重键、重试策略 |

## 分步骤规划

### 步骤 1：建立核心契约与错误码落点
- 覆盖任务：建立 `src/core/auth_contract`、`src/core/persistence_contract`、`src/core/cache_contract`、`src/core/task_contract`，并同步建立统一错误码目录和领域错误码落点。
- 依赖关系：直接承接 Phase 1 的统一异常、统一响应和依赖注入能力。
- 完成结果：认证主体、令牌、授权策略、工作单元、缓存记录、任务消息、错误码目录这些稳定契约固定下来，为后续运行时实现提供统一边界。
- 步骤验收点：统一错误码、事务、仓储、授权策略形成稳定契约。

### 步骤 2：落地认证运行时与认证接口最小闭环
- 覆盖任务：实现 OAuth2 Bearer 入口、JWT 签发/校验、授权评估与错误码映射，并完成认证访问接口。
- 依赖关系：依赖步骤 1 中的 `AuthenticatedPrincipal`、`TokenPayload`、`TokenIssuePayload`、`AuthorizationPolicy`、`ErrorCodeCatalog` 契约。
- 完成结果：`POST /auth/token`、`POST /auth/refresh`、`POST /auth/revoke`、`GET /auth/me` 可工作。
- 步骤验收点：认证接口可完成签发、刷新、吊销的最小闭环；错误码可在接口错误响应中稳定输出。

### 步骤 3：落地数据库运行时与事务仓储骨架
- 覆盖任务：实现 SQLAlchemy engine、session、unit of work、仓储实现骨架。
- 依赖关系：依赖步骤 1 中的 `UnitOfWork` 契约，并依赖 Phase 1 已有的统一配置与应用装配能力。
- 完成结果：数据库访问边界、事务边界、仓储边界先收口为首版可替换实现。
- 步骤验收点：ORM session 可创建并关闭。

### 步骤 4：落地缓存统一接口与首版实现
- 覆盖任务：实现内存缓存与 Redis 缓存统一接口，使缓存运行时具备首版可替换实现。
- 依赖关系：依赖步骤 1 中的 `CacheRecordPayload` 契约，以及 `docs/技术选型.md` 中的 `redis` / `cachetools` 既定方向。
- 完成结果：缓存运行时具备首版可替换实现。
- 步骤验收点：本地缓存可通过最小样例运行。

### 步骤 5：落地消息/任务运行时与任务派发用例
- 覆盖任务：实现本地消息总线、本地任务调度器与 `funboost` 扩展位，实现 RabbitMQ 适配边界，但首版默认不要求真实 broker 启动，并完成任务派发用例。
- 依赖关系：依赖步骤 1 中的 `TaskMessagePayload` 契约，以及 `docs/技术选型.md` 中的 `funboost`、`rabbitmq` 既定方向。
- 完成结果：本地可运行闭环与可替换扩展点分开，本地任务调度器可通过最小样例运行。
- 步骤验收点：任务派发用例能够对齐当前 Python 模拟用法。
