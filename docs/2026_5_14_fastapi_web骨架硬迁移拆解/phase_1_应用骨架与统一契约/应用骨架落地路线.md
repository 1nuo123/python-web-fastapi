# Phase 1 应用骨架与统一契约

## 阶段目标
完成首版可启动 Web 基础骨架，建立统一入口、统一契约、统一配置、统一异常、统一请求上下文与首批接口。

当前阶段完成后的中间结果：
- 应用可通过 `asgi_entry.py` 启动。
- 健康探针和系统概览接口可运行。
- 统一响应与统一错误结构落地。
- 配置、日志、请求上下文、中间件链具备首版实现。

## 依赖关系
- 依赖 [FastAPI统一Web基础设施实现规格](</e:/python_web_fastapi/work/docs/design_docs/FastAPI统一Web基础设施实现规格.md>)。
- 依赖三份标准文档中的命名、编码、测试约束。
- 依赖 `src` 当前空骨架目录作为实际落点。

源码现状说明：当前 `src` 已存在 `api`、`application`、`core`、`domain`、`infrastructure` 等包目录，`main.py` 为空文件，符合“当前空骨架目录作为实际落点”的描述。

## 执行约束
- Python 版本固定为 `3.11+`。
- Web 采用 `fastapi` + `uvicorn`，配置采用 `pydantic-settings` + `rtoml`，数据建模采用 `pydantic v2`，JSON 采用 `orjson`。
- 稳定协议必须采用“公共头字段 + 强类型扩展字段”规则；扩展字段必须包含 `kind`、`schema_version`，并启用 `extra="forbid"`。
- 禁止使用 `dict[str, Any]`、`metadata`、`extra_payload` 承载稳定协议；所有正式日志使用中文，不允许 `print` 代替日志；所有新增功能必须同步补测试。

## 契约表
| 英文名 | 中文名 | 中文说明 |
|---|---|---|
| ResponseHeader | 响应公共头 | 统一响应公共头，至少包含 `request_id`、`trace_id`、`code`、`message` |
| ResponseBodyKind | 响应体类型 | 统一响应扩展体的判别类型，必须与内层 `kind` 一致 |
| ResponseEnvelope[T] | 统一响应信封 | 外层响应模型，承载公共头字段与强类型扩展字段 |
| RequestScope | 请求上下文 | 请求期上下文，至少包含 `request_id`、`trace_id`、`request_time` |
| HealthProbePayload | 健康探针扩展体 | `kind="health_probe"`，`schema_version` 固定，`extra="forbid"` |
| SystemOverviewPayload | 系统概览扩展体 | `kind="system_overview"`，返回应用版本、环境、模块启用状态 |
| HttpFaultPayload | HTTP 故障扩展体 | `kind="http_fault"`，统一错误码、错误消息与可控细节 |

## 分步骤阶段规划

### 步骤 1：建立统一启动入口
- 覆盖任务：建立 `src/api/asgi_entry.py`、`src/main.py` 统一启动入口。
- 依赖关系：作为本阶段起点，无前置代码依赖；后续配置装配、路由装配、生命周期装配均挂到统一入口。
- 完成结果：应用可通过 `asgi_entry.py` 启动。
- 步骤验收点：`create_app()` 可成功构造应用对象。

### 步骤 2：建立 HTTP 与异常基础契约
- 覆盖任务：建立 `src/core/http_contract` 与 `src/core/exception_contract` 基础契约。
- 依赖关系：统一响应、统一异常、请求上下文、接口输出都依赖该层契约。
- 完成结果：`ResponseHeader`、`ResponseEnvelope[T]`、`RequestScope`、`HttpFaultPayload` 等稳定结构落地。
- 步骤验收点：统一响应中存在 `request_id`。

### 步骤 3：实现统一响应与统一异常输出
- 覆盖任务：实现统一响应信封与统一异常输出。
- 依赖关系：依赖步骤 2 的基础契约，并为健康探针、系统概览接口提供统一输出外壳。
- 完成结果：统一响应与统一错误结构落地。
- 步骤验收点：统一响应中存在 `request_id`；配置加载失败时可给出可识别异常。

### 步骤 4：实现配置加载链路
- 覆盖任务：实现 `app_* + modules/* + runtime/*` 配置加载链路。
- 依赖关系：统一入口、应用装配、生命周期装配、接口运行都依赖配置结果。
- 完成结果：配置按既定层次加载，开发环境可直接运行。
- 步骤验收点：配置加载失败时可给出可识别异常。

### 步骤 5：实现日志、请求上下文、中间件与生命周期装配
- 覆盖任务：实现日志工厂、请求上下文管理、中间件装配与生命周期装配。
- 依赖关系：依赖统一入口与配置加载；为统一响应、异常输出、请求链路透传提供基础设施支撑。
- 完成结果：配置、日志、请求上下文、中间件链具备首版实现。
- 步骤验收点：统一响应可带 `request_id`、`trace_id`。

### 步骤 6：实现健康探针与系统概览接口
- 覆盖任务：实现健康探针、系统概览接口与对应用例。
- 依赖关系：依赖统一响应、统一异常、请求上下文、路由装配。
- 完成结果：健康探针和系统概览接口可运行。
- 步骤验收点：`GET /health/live`、`GET /system/info` 可返回 200。

### 步骤 7：实现模块清单与路由组合装配
- 覆盖任务：实现 `web_bundle_catalog.py` 与路由组合装配。
- 依赖关系：依赖统一入口、接口契约、接口实现；负责把首批接口挂载到应用。
- 完成结果：健康探针、系统概览等首批接口通过统一装配方式接入。
- 步骤验收点：`GET /health/live`、`GET /system/info` 可返回 200。

### 步骤 8：预留后续依赖注入位点
- 覆盖任务：为后续鉴权、持久化、缓存、任务保留依赖注入位点。
- 依赖关系：依赖统一入口、应用装配、配置装配、生命周期装配的稳定落点。
- 完成结果：不破坏当前阶段启动与接口可用性的前提下，为后续能力接入预留边界。
- 步骤验收点：`create_app()` 可成功构造应用对象，且现有接口保持可用。

## 关键代码片段
```python
from pydantic import BaseModel, ConfigDict, Field


class HealthProbePayload(BaseModel):
    model_config = ConfigDict(extra="forbid")

    kind: str = Field(default="health_probe")
    schema_version: str = Field(default="1.0")
    status: str


class ResponseEnvelope(BaseModel):
    model_config = ConfigDict(extra="forbid")

    code: str
    message: str
    request_id: str
    trace_id: str | None
    data: HealthProbePayload | SystemOverviewPayload | HttpFaultPayload
```
