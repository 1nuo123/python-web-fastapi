# 生产级完整性闭环审查与整改执行方案

## 任务目标

- 交付物：在现有单机生产级基线（2026_7_13 审查已收口 `open=0`）之上，完成一轮全量复审，并补齐三个已确认的完整性缺口——审计事件持久化闭环、监控指标覆盖、告警规则基线，使可读性、扩展性、维护性、稳定性、安全性与审计/监控告警形成最终闭环。
- 完成判定：复审发现清单中无未关闭 P0/P1；审计关键事件具备崩溃安全的落库路径与可查询动作全覆盖；`/metrics` 暴露安全、日志缓冲、任务、容量四类新增低基数指标；告警规则基线文件可被测试反序列化校验；全部质量门禁（`nox -s static/offline/regression`）通过且文档与源码一致。
- 边界：单机部署规格，不引入分布式组件、不内置 Prometheus/Alertmanager 部署栈、不做无基准的异步重写；深度到位即止，不无限堆叠。

## 全局约束

- 编码：Python 3.11，同步主干 + 有界线程池隔离；分层依赖遵守 import-linter 四条既有契约（core 不反向依赖、domain/application/infrastructure 边界不破坏）。
- 契约：一律「公共头字段 + 强类型扩展字段」。扩展字段使用 Pydantic 判别联合（`Field(discriminator="kind")`），必须携带 `kind`、`schema_version`，启用 `extra="forbid"`；外层信封 `header.mode/detail_kind` 必须与内层 `detail.kind` 一致并由 `model_validator` 强制；禁止 `dict[str, Any]`、`metadata`、`extra_payload` 类弱类型字段。
- 日志：沿用脱敏约束——指标标签与日志只允许低基数值（方法、路由模板、状态码、reason_code、digest），禁止完整 URL、请求体、token、password、secret。
- 文档：docs 与源码冲突时以源码为准，并在文档标注可能过期；`docs/observability_grafana_prometheus接入说明.md` 中「日志缓冲指标缺失」段落即为本次要消除的已知过期点。
- 测试：静态门禁零容忍（Ruff/Mypy/import-linter/Bandit 中高危/pip-audit/detect-secrets/uv lock）；全量回归禁止 skip/xfail；总覆盖率 ≥85%，auth/security/task/persistence 四域 ≥90%。
- 变更纪律：硬迁移，不保留旧路径兼容层；不因新增指标扩大静态检查忽略。

## 验收标准

- 复审发现清单结构化状态为 `open=0`，P0/P1 全部 verified 或有根因修复加当前回归证据。

- 质量门禁：`nox -s static`、`nox -s offline`、`nox -s regression` 全部通过，覆盖率不低于既有基线（总体 90.8%、四域 ≥90%）。

## Phase 2 审计事件持久化闭环

### 目标

- 直接问题：审计/安全关键事件当前与普通日志共用 lazy-flush 缓冲（`LogBufferDispatcher.emit` 仅在容量或间隔触发刷盘），进程崩溃时窗口内审计事件丢失；且 `AdminAuditAction` 未覆盖 scope/role/settings 变更，审计查询维度不完整。
- 中间结果：关键事件带持久化优先级标记，走即时落库路径；审计写失败产生结构化失败计数（供 Phase 3 转指标）；审计动作枚举全覆盖管理员变更面。

### 依赖

- Phase 1 固化的审计缺口清单。
- 既有契约：`LogEventEnvelope`、`LogWriteRequest/LogWriteReason/LogWriteResult`、`SecurityEventEnvelope`、`AdminAuditQueryPort`。
- 既有文件：`log_buffer_dispatcher.py`、`logging_resource_facade.py`、`log_record_repository_impl.py`。

### 模拟用法

```python
# 安全门面记录管理员身份变更：审计关键事件即时落库，不等缓冲窗口
envelope = security_event_builder.build_admin_identity_changed_event(...)
logging_facade.record_security_event(
    envelope,
    persistence_priority=LogPersistencePriority.AUDIT_CRITICAL,
)
# 崩溃安全：record 返回前该事件已进入数据库事务提交路径
```

### 契约

| 英文名 | 中文名 | 中文说明 |
|---|---|---|
| LogPersistencePriority | 日志持久化优先级 | 新增 StrEnum：`standard`（走缓冲）/ `audit_critical`（即时落库），挂在 `LogEventEnvelope` 公共头，默认 `standard` |
| LogWriteReason.AUDIT_CRITICAL | 审计关键写入原因 | `LogWriteReason` 新增成员，标识即时落库批次，用于失败归因与指标标签 |
| AuditWriteFailureCounter | 审计写失败计数 | `LogBufferDispatcher` 暴露的强类型只读快照（dataclass，含 `failed_count`、`pending_items`），供指标桥接读取，禁止裸 dict |
| AdminAuditAction | 业务审计动作枚举 | 扩展成员：`SCOPE_CHANGED`、`ROLE_CREATED`、`ROLE_UPDATED`、`ROLE_DELETED`、`ROLE_ROLES_REPLACED`、`SETTINGS_RELOADED`；查询契约同步支持 |

扩展字段规则：`LogEventEnvelope` 为既有「header + 判别联合 detail」结构，本次只在公共头新增 `persistence_priority` 字段并升 `schema_version`；不新增弱类型字段。

### 关键代码片段

```python
class LogPersistencePriority(StrEnum):
    STANDARD = "standard"
    AUDIT_CRITICAL = "audit_critical"

def emit(self, event: LogEventEnvelope) -> None:
    if event.header.persistence_priority is LogPersistencePriority.AUDIT_CRITICAL:
        self._submit_critical(LogWriteRequest(
            events=(event,), reason=LogWriteReason.AUDIT_CRITICAL,
        ))
        return
    ...  # 既有缓冲路径不变
```

## Phase 3 监控指标补齐

### 目标

- 直接问题：`PrometheusMetricsRegistry` 仅有 HTTP 请求数、耗时、ready 三个指标；安全事件、日志缓冲失败/积压、任务执行结果、运行时容量饱和度均不可观测，文档已自认缺口。
- 中间结果：四类新增低基数指标接入 `/metrics`；指标开关进入配置契约；Phase 2 的审计写失败快照转为可抓取指标。

### 依赖

- Phase 2 的 `AuditWriteFailureCounter` 快照接口。
- 既有契约：`MetricsRuntimeEnvelope`（1.0）、`RuntimeCapacityPolicy`、任务执行记录链。
- 既有文件：`prometheus_metrics_registry.py`、`shared_resource_lifecycle.py`、metrics_runtime TOML。

### 模拟用法

```python
registry.record_security_event(SecurityEventMetric(
```

### 契约

| 英文名 | 中文名 | 中文说明 |
|---|---|---|
