# 配置资源装配硬拆分分步骤执行方案

## 阶段范围
本文件只拆解原方案中的 `## Phase 3 配置加载器与资源挂载热点拆分`。

本阶段按硬迁移口径执行：一次性迁移至最终最佳实践状态，不采用新旧实现并存、不做渐进式双轨兼容设计。若文档、图谱、历史方案与源码冲突，以源码为准，并在后续文档回归中说明历史文档可能过期。

## 阶段目标
降低 `app_settings_loader.py` 与 `shared_resource_mount.py` 的持续膨胀风险。

阶段完成后，配置读取、合并、安全校验、资源启动、资源释放、访问器刷新都有清晰落点：
- `AppSettingsLoader` 保留为配置加载门面，只负责编排读取、覆盖、合并、校验流程。
- `SharedResourceMount` 保留为资源挂载门面，对外方法签名稳定。
- 配置递归合并、生产安全校验、资源启动、资源释放、访问器刷新全部下沉到独立模块。
- 拆分后行为与拆分前一致，现有配置模型与资源生命周期测试不需要大量重写。

## 依赖关系
| 依赖项 | 中文说明 |
|---|---|

| Phase 2 日志脱敏链路 | Phase 2 不依赖本阶段，但本阶段不得破坏异常日志脱敏链路。 |

| 当前资源生命周期测试 | 以现有资源启动、关闭、热更新路径测试作为行为保持依据。 |
| 源码优先原则 | 若历史文档与源码冲突，以源码为准。 |

## 分步骤执行方案
### Step 1 固定门面边界
先确认 `AppSettingsLoader` 与 `SharedResourceMount` 的现有公开入口、调用方和测试覆盖范围。

本步骤只做边界确认，不引入双轨实现：
- 固定 `AppSettingsLoader().load_for_environment(...)` 的外部行为。
- 固定 `SharedResourceMount` 对外方法签名。
- 明确拆分后门面仍负责流程编排，不继续承载具体实现细节。
- 明确拆出的模块必须由门面统一调用，外部调用方不直接依赖拆分细节。

### Step 2 硬拆配置递归合并
新增 `src/infrastructure/settings/settings_mapping_merger.py`。

将 `app_settings_loader.py` 中的 `_merge_mapping()` 迁移到该模块：
- 迁移普通字典递归合并逻辑。
- 保留判别联合切换时整段替换规则。
- 保持配置合并顺序和冲突处理行为不变。
- 禁止用 `dict[str, Any]`、`metadata`、`extra_payload` 承载稳定协议字段。

### Step 3 硬拆生产安全校验
新增 `src/infrastructure/settings/settings_security_validator.py`。

将生产 JWT、Redis、RabbitMQ、安全运行时校验迁移到该模块：
- 生产 JWT 安全校验迁移到独立 validator。
- Redis 生产安全校验迁移到独立 validator。
- RabbitMQ 生产安全校验迁移到独立 validator。
- 安全运行时校验迁移到独立 validator。
- 保持原有失败异常、失败语义和校验顺序一致。

### Step 4 收缩 `AppSettingsLoader`
修改 `src/infrastructure/settings/app_settings_loader.py`。

`AppSettingsLoader` 硬收缩为门面：
- 继续负责编排配置读取。
- 继续负责编排环境变量覆盖。
- 调用 `settings_mapping_merger.py` 完成递归合并。
- 调用 `settings_security_validator.py` 完成生产安全校验。
- 不再内联承载递归 merge 和生产安全校验实现细节。

### Step 5 硬拆资源启动装配
新增 `src/infrastructure/resource_mount/runtime_resource_bootstrapper.py`。

将 `shared_resource_mount.py` 中资源启动装配细节迁移到该模块：
- 迁移数据库、缓存、日志、任务、鉴权等资源启动装配细节。
- 保持资源启动顺序不变。
- 保持资源就绪状态写入语义不变。
- 启动失败时保持原有异常传播和清理策略。

### Step 6 硬拆资源释放逻辑
新增 `src/infrastructure/resource_mount/runtime_resource_releaser.py`。

将 `shared_resource_mount.py` 中资源释放细节迁移到该模块：
- 迁移资源关闭、释放、清理逻辑。
- 保持释放顺序不变。
- 保持失败处理策略不变。
- 保证关闭路径、异常路径、重复释放路径与拆分前行为一致。

### Step 7 硬拆访问器刷新逻辑
新增 `src/infrastructure/resource_mount/runtime_accessor_refresher.py`。

将鉴权、日志访问器刷新逻辑迁移到该模块：
- 迁移鉴权访问器刷新逻辑。
- 迁移日志访问器刷新逻辑。
- 保持热更新路径行为不变。
- 保持访问器快照刷新后的对外可见行为不变。

### Step 8 收缩 `SharedResourceMount`
修改 `src/infrastructure/shared_resource_mount.py`。

`SharedResourceMount` 硬收缩为资源门面：
- 对外方法签名保持稳定。
- 资源启动委托给 `runtime_resource_bootstrapper.py`。
- 资源释放委托给 `runtime_resource_releaser.py`。
- 访问器刷新委托给 `runtime_accessor_refresher.py`。
- 不再继续承载启动、释放、刷新全部实现细节。

## 契约
### 契约设计硬约束
| 英文名 | 中文名 | 中文说明 |
|---|---|---|
| PublicHeaderPlusTypedDetail | 公共头字段加强类型扩展字段 | 外层公共头承载稳定字段，内层扩展字段使用 Pydantic 判别联合。 |
| DiscriminatedUnionDetail | 判别联合扩展字段 | 扩展字段必须包含 `kind`、`schema_version`，并通过判别字段区分具体扩展模型。 |
| ForbidExtraFields | 禁止额外字段 | 扩展模型必须启用 `extra="forbid"`，禁止接收未声明字段。 |
| NoAnyPayload | 禁止弱类型载荷 | 禁止使用 `dict[str, Any]`、`metadata`、`extra_payload` 承载稳定协议字段。 |
| KindConsistency | 外层内层类型一致 | 外层公共头类型必须与内层扩展类型语义一致。 |

### 本阶段契约
| 英文名 | 中文名 | 中文说明 |
|---|---|---|
| `SettingsMergeHeader` | 配置合并公共头 | 承载 `kind`、`schema_version`、`merge_name`。 |
| `RecursiveMappingMergeDetail` | 递归映射合并扩展 | `kind="recursive_mapping_merge"`，定义普通字典递归合并和判别联合切换整段替换规则；扩展模型必须包含 `schema_version` 且启用 `extra="forbid"`。 |
| `RuntimeResourceOperationHeader` | 运行时资源操作公共头 | 承载 `kind`、`schema_version`、`operation_name`、`target_resource`。 |
| `ResourceBootstrapDetail` | 资源启动扩展 | `kind="resource_bootstrap"`，描述资源启动顺序和就绪状态写入；扩展模型必须包含 `schema_version` 且启用 `extra="forbid"`。 |
| `ResourceReleaseDetail` | 资源释放扩展 | `kind="resource_release"`，描述资源释放顺序和失败处理策略；扩展模型必须包含 `schema_version` 且启用 `extra="forbid"`。 |

## 校验与验收点
### 阶段校验
- `AppSettingsLoader().load_for_environment(...)` 行为与拆分前一致。
- `TestAppFactory().create()` 能正常装配全部路由。
- 资源启动、关闭、热更新路径现有测试不需要大量重写。

### 阶段验收
- `app_settings_loader.py` 不再承载递归 merge、生产安全校验全部实现细节。
- `shared_resource_mount.py` 至少完成资源启动、资源释放、访问器刷新逻辑的独立模块提取。
- `SharedResourceMount` 对外方法签名稳定。
- 配置合并、生产安全校验、资源启动、资源释放、访问器刷新行为与拆分前一致。
- 本阶段不得破坏 Phase 2 的日志脱敏链路。
