# 本地直启环境加载分步骤执行方案

## 1. 阶段目标
解决本地 `uvicorn src.main:app` 因缺失进程环境变量而启动失败的问题。

阶段完成后：开发环境可读取本地 `.env`，生产环境仍必须依赖外部环境变量。

本阶段按硬迁移口径执行：一次性迁移到最终配置来源模型与加载顺序，不设计旧逻辑并存、不保留渐进式开关。

## 2. 依赖关系
| 依赖项 | 说明 |
|---|---|
| `AppSettingsLoader` | 当前配置加载入口，需收口 `.env` 与进程环境变量合并顺序。 |
| `.env` | 本地开发/测试环境可读取的变量来源。 |
| `.env.docker.example` | 需补充本地直启变量说明。 |
| `.env.production.example` | 需明确生产环境不读取仓库 `.env`。 |
| `config/runtime/auth_runtime/auth_runtime_base.toml` | 继续保持不提供默认 `jwt_secret` 的安全基线。 |
| `AppEnvironment` | 当前包含 `development`、`test`、`production`，生产环境规则必须保持强约束。 |

## 3. 模拟用法
```powershell
$env:APP_ENV="development"
uvicorn src.main:app --reload
```

## 4. 契约
本阶段契约采用“公共头字段 + 强类型扩展字段”规则：

- 外层信封使用公共头字段。
- 扩展字段使用 Pydantic 判别联合。
- 扩展字段必须包含 `kind`、`schema_version`。
- 扩展模型必须启用 `extra="forbid"`。
- 禁止使用 `dict[str, Any]`、`metadata`、`extra_payload` 承载扩展内容。
- 外层类型与内层扩展类型的 `kind`、`schema_version` 必须一致。

| 英文名 | 中文名 | 中文说明 |
|---|---|---|
| `SettingsSourceHeader` | 配置来源公共头 | 承载 `kind`、`schema_version`、`environment`、`source_name`。 |
| `ProcessEnvironmentSourceDetail` | 进程环境变量来源扩展 | `kind="process_environment"`，描述从 `os.environ` 读取的配置来源。 |
| `DotenvSourceDetail` | 本地 dotenv 来源扩展 | `kind="dotenv_file"`，描述开发/测试环境允许读取的 `.env` 文件路径与启用状态。 |
| `SettingsSourceEnvelope` | 配置来源信封 | 外层公共头 + 判别联合扩展；扩展含 `kind`、`schema_version`，`extra="forbid"`。 |
| `LocalStartupPolicy` | 本地启动策略 | 声明开发/测试允许 `.env` 补齐，生产禁止 `.env` 补齐。 |

## 5. 分步骤执行方案
### Step 1：新增 dotenv 配置来源模型与解析器
新增 `dotenv_settings_loader.py`，只解析简单 `KEY=VALUE` 形式。

执行要求：
- 只使用标准库解析。
- 不记录、打印、返回日志中的变量值。
- 支持跳过空行和注释行。
- 解析结果作为配置覆盖来源参与合并。
- 对 `.env` 不存在的情况返回空配置，不视为异常。

验收点：
- `.env` 存在时可解析 `JWT_SECRET`、`AUTH_BOOTSTRAP_ADMIN_PASSWORD`。
- `.env` 不存在时不影响配置加载主流程。
- 日志不包含 `.env` 中的具体值。

### Step 2：固定配置来源优先级
调整 `AppSettingsLoader.load()` 与相关内部流程，先解析有效环境，再按以下优先级合并：

```text
process env > local .env > TOML
```

执行要求：
- 先通过 `APP_ENV` 确定 `AppEnvironment`。
- 生产环境跳过仓库 `.env`。
- 开发/测试环境允许读取仓库 `.env`。
- 进程环境变量始终最后覆盖，用于容器部署时替换敏感信息和连接地址。
- 不改变现有 TOML 配置文件层级收集逻辑。

验收点：
- 开发环境缺失进程级 `JWT_SECRET` 时，可由 `.env` 补齐。
- 进程级 `JWT_SECRET` 存在时，必须覆盖 `.env`。
- TOML 仍作为基础配置来源。

### Step 3：保持生产环境强安全约束
生产环境显式跳过仓库 `.env`，缺失 `JWT_SECRET` 继续失败。

执行要求：
- `APP_ENV=production` 时不读取仓库 `.env`。
- `JWT_SECRET` 必须来自进程环境变量。
- 保留生产环境弱密钥校验。
- 保留生产外部运行时密钥校验，包括数据库、Redis、RabbitMQ 等现有规则。

验收点：
- `APP_ENV=production` 且缺失进程级 `JWT_SECRET` 时仍启动失败。
- 生产环境不会从仓库 `.env` 补齐 `JWT_SECRET`。
- 原有生产安全失败信息语义不变。

### Step 4：补齐开发环境本地直启变量
开发环境缺失 `JWT_SECRET`、`AUTH_BOOTSTRAP_ADMIN_PASSWORD` 时可由 `.env` 补齐。

执行要求：
- `.env` 可补齐认证运行时 `jwt_secret`。
- `.env` 可补齐 bootstrap admin 的 `password_plain`。
- 不向基础 TOML 写入默认密钥。
- 不降低 `config/runtime/auth_runtime/auth_runtime_base.toml` 的安全基线。

验收点：
- 清空进程级 `JWT_SECRET` 后，开发环境能从 `.env` 构建 `ApplicationSettings`。
- 开发环境 bootstrap admin 启用时，可通过 `.env` 获得密码。
- 本地 `uvicorn src.main:app --reload` 不因缺少进程变量直接失败。

### Step 5：更新 env 示例文档
调整 `.env.docker.example` 与 `.env.production.example`。

执行要求：
- `.env.docker.example` 补充本地直启变量说明。
- `.env.production.example` 明确生产不读取仓库 `.env`。
- 示例文件不得引导生产使用示例密钥。
- 文档口径必须与源码实际加载顺序一致。

验收点：
- 开发/测试、本地直启、Docker Compose、生产部署的变量来源边界清晰。
- 文档、示例、源码三者对 `.env` 的使用规则一致。

## 6. 关键代码片段
原始关键代码片段保留如下：

```python
SettingsSourceDetail = Annotated[
    ProcessEnvironmentSourceDetail | DotenvSourceDetail,
    Field(discriminator="kind"),
]

class SettingsSourceEnvelope(BaseModel):
    model_config = ConfigDict(extra="forbid")
    header: SettingsSourceHeader
    detail: SettingsSourceDetail
```

## 7. 校验与验收点
- 清空进程级 `JWT_SECRET` 后，开发环境能从 `.env` 构建 `ApplicationSettings`。
- `APP_ENV=production` 且缺失进程级 `JWT_SECRET` 时仍启动失败。
- 日志不输出 `.env` 中的具体值。
- 本地 `uvicorn src.main:app --reload` 可在开发环境通过 `.env` 完成启动所需配置补齐。
- 生产环境仍必须通过外部环境变量注入敏感配置。
