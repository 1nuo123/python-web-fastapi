# 单机版任务队列执行方案

## 任务目标
在当前源码基础上，完成单机任务队列的可追踪、可去重、可重试、可回溯闭环；保留现有任务入口，不引入复杂分布式编排、控制台或额外 outbox。

完成判定：
- 任务可通过 `request_id` / `trace_id` 关联到日志与执行记录。
- 重复 `job_kind + deduplication_key` 不再产生重复副作用。
- 失败状态、失败原因、重试次数、下一次重试时间可查询。
- 新增/修改测试、真实测试、文档回归全部通过。

## 全局约束
- 以源码为准；若文档、图谱、源码冲突，以源码为准，旧文档可能过期。
- 保持现有 `TaskMessageEnvelope`、`TaskDispatcher`、`DispatchBackgroundJobUsecase` 外部入口兼容。
- 所有新增外部契约必须使用 Pydantic，且满足 `kind`、`schema_version`、`extra="forbid"`。
- 扩展字段必须使用 Pydantic 判别联合；外层类型与内层扩展类型必须一致。
- 禁止使用 `dict[str, Any]`、`metadata`、`extra_payload` 承载稳定协议。
- 日志必须中文输出，禁止 `print` 作为正式日志。
- 重试仅覆盖可恢复异常；Funboost 仍优先依赖自身重试，项目侧只负责状态落库与可观测性补齐。

## 验收标准
- 任务执行记录表、仓储、状态机、去重逻辑全部落地。
- `TaskMessageHeader` 与任务日志补齐链路关联字段。
- 本地任务具备简单指数退避，且失败可定位、可复跑。
- 真实测试命令全部通过，且文档与源码一致。

## Phase 1
### 目标
补齐任务执行记录契约、状态模型与持久化底座，为去重、失败回溯和状态查询提供唯一数据源。

### 依赖
- 现有 `TaskMessageEnvelope`、`TaskDispatchResultPayload`、SQLAlchemy 基座。
- `docs/standard` 的命名、编码、测试规范。

### 模拟用法
```python
record = TaskExecutionRecordEnvelope(...)
repository.upsert(record)
```

### 契约
| 英文名 | 中文名 | 中文说明 |
|---|---|---|
| `TaskExecutionRecordHeader` | 任务执行记录公共头 | 承载 `record_id`、`task_id`、`job_kind`、`deduplication_key`、`request_id`、`trace_id`、`created_at_epoch` 等公共字段。 |
| `TaskExecutionPendingDetail` | 等待态扩展 | 表示已接收未执行，记录 `status=PENDING`、`attempt_count`、`schema_version`、`kind`。 |
| `TaskExecutionRunningDetail` | 执行中扩展 | 表示正在执行，记录 `status=RUNNING`、`attempt_count`、`started_at_epoch`。 |
| `TaskExecutionRetryingDetail` | 重试中扩展 | 表示等待重试，记录 `status=RETRYING`、`attempt_count`、`next_retry_at_epoch`、`last_error_type`。 |
| `TaskExecutionSuccessDetail` | 成功态扩展 | 表示最终成功，记录 `status=SUCCESS`、`attempt_count`、`finished_at_epoch`。 |
| `TaskExecutionFailedDetail` | 失败态扩展 | 表示最终失败，记录 `status=FAILED`、`attempt_count`、`failed_at_epoch`、`last_error_message`、`stage`。 |
| `TaskExecutionRecordEnvelope` | 任务执行记录信封 | 外层 `header + detail`，`detail` 使用 Pydantic 判别联合，外层/内层 `kind` 与 `schema_version` 保持一致。 |

### 任务清单
- [x] 新增执行记录契约与判别联合。
- [x] 新增执行记录 ORM 与唯一约束 `job_kind + deduplication_key`。
- [x] 新增执行记录仓储读写接口。
- [x] 补齐状态机字段与时间戳字段。
- [x] 明确失败信息写入执行记录，不再依赖独立失败表。

## Phase 2
### 目标
把执行记录接入真实分发/消费链路，完成去重、退避重试、失败落库与日志关联。

### 依赖
- Phase 1 的执行记录契约与仓储。
- 现有本地/Funboost 调度器、日志构造器、设置加载器。

### 模拟用法
```python
result = dispatch_background_job_usecase.execute(
    TaskDispatchCommand(payload=demo_payload, job_kind="demo_task")
)
```

### 契约
| 英文名 | 中文名 | 中文说明 |
|---|---|---|
| `TaskMessageHeader` | 任务消息公共头 | 增加 `request_id`、`trace_id` 等关联字段，用于跨链路排查。 |
| `TaskExecutionStatus` | 任务执行状态 | 表示 `PENDING`、`RUNNING`、`RETRYING`、`SUCCESS`、`FAILED`。 |
| `TaskFailureRecord` | 任务失败记录 | 扩展 `request_id`、`trace_id`、`deduplication_key`、`attempt_count`，供日志与回归修复使用。 |
| `TaskRetryPolicy` | 任务重试策略 | 表示 `retry_limit`、`retry_delay_seconds`、`retry_backoff_multiplier`、`retry_max_delay_seconds`。 |
| `TaskDispatchResultPayload` | 任务分发结果 | 需要能回传任务是否复用既有记录、最终状态与任务标识。 |

### 任务清单
- [x] 在 `DispatchBackgroundJobUsecase` 中注入 `request_id`、`trace_id` 与显式去重键。
- [x] 在本地调度器中先抢占/查询执行记录，再决定是否实际执行。
- [x] 在 Funboost 分发与消费路径补齐状态回写与失败记录。
- [x] 在日志构造器中补齐 `task_id`、`job_kind`、`deduplication_key`、`request_id`、`trace_id`、`attempt_count`、`status`、`stage`。
- [x] 为本地任务加入指数退避与可恢复异常分支。
- [x] 保持现有对外入口不变，只收紧内部行为。

### 关键代码片段
```python
message = TaskMessageEnvelope(
    header=TaskMessageHeader(..., request_id=request_id, trace_id=trace_id),
    payload=TaskMessagePayload(...),
)
store.reserve_or_get(message)
```

### 校验
- 重复 `job_kind + deduplication_key` 不再重复执行。
- 失败状态、重试次数、下一次重试时间可查询。
- 任务日志能串起 HTTP 与任务链路。
- 本地/Funboost 路径的回归测试可稳定通过。
