Codex E2EE 威胁模型
====================

信任边界
--------

设备私钥只在当前 Windows 用户 DPAPI 范围内生成和使用。服务端保存设备公钥、指纹、
operation 摘要和加密 outbox，不把 outbox 的 AES-GCM 设计宣称为服务端不可读的端到端
加密。浏览器用户身份与 Agent 设备身份分离。

冲突与泄露面
------------

* 审批、审计和搜索需要服务端可验证的摘要；因此不能把“不可搜索”误写成隐私保证。
* 多设备同时在线时，服务端仍需验证租户 owner、host、workspace、thread 和 approval
  的归属，重放保护由 command id、设备 key 和一次性 ticket 共同完成。
* 元数据（时间、容量、状态、设备数量）即使不含正文也可能泄露使用模式，指标和日志
  只允许低基数维度。

恢复与轮换
----------

设备 key 撤销和轮换必须先完成服务端 CAS，再让旧 key 进入 revoked 状态；丢失 Redis
后不恢复旧 ticket。若未来引入真正 E2EE，需要额外设计多设备密钥同步、恢复密钥、审批
确认和可搜索索引，并在独立 ADR 评审通过前禁止实施。

验收结论
--------

当前实现满足 WSS、设备公钥认证、最小化留存和敏感载荷加密的产品目标；不满足“服务端
无法读取 Codex 内容”的 E2EE 目标，后者明确列为后续评审项。
