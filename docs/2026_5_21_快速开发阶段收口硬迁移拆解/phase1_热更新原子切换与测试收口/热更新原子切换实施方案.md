# 热更新原子切换实施方案

## 阶段目标与硬约束
- 编码遵循 `docs/standard`。
- 修复热更新“先改现态、后重建资源”的半生效风险。
- 收口测试入口，使本地与 CI 都能一键收集并执行测试。
- 本阶段为硬迁移方案，目标是一次性把热更新链路与测试入口收口到目标状态，不采用任何渐进式迁移设计。
- 若文档、图谱、源码冲突，以源码为准，并在文档回归中标注旧文档可能过期。
- 不允许以放宽断言、跳过测试、保留死代码替代真实修复。
- 新增或修改契约统一采用“公共头字段 + 强类型扩展字段”。
- 外层结构固定为 `header + detail`。
- `detail` 必须使用 Pydantic 判别联合。
- 每个扩展模型必须包含 `kind`、`schema_version`。
- 每个扩展模型必须 `extra="forbid"`。
- 禁止 `dict[str, Any]`、`metadata`、`extra_payload`。
- 外层类型与内层扩展类型必须一致。
- 保持现有统一错误码、统一日志结构、统一响应外壳不变。
- 不新增新的中心化超大文件；拆分后入口文件只负责装配与转发。
- 测试必须覆盖单测、路径/边界回归、至少一条真实集成链路。

## 依赖关系与范围
- 阶段依赖：Phase 1 无前置，先收口热更新原子性与测试入口。
- 前置文件：`src/infrastructure/shared_resource_mount.py`、`src/infrastructure/settings/settings_reload_coordinator.py`、`pyproject.toml`
- 前置环境：本地 `uv` 可用，测试依赖已安装
- 源码锚点：`src/infrastructure/fastapi_app_assembler.py` 当前通过 `on_settings_applied=resource_mount.apply_settings` 连接重载协调器与资源挂载点，并在装配时执行 `reload_coordinator.initialize_snapshot()` 建立首个成功快照。
- 本文只覆盖 Phase 1，不扩写 Phase 2、Phase 3。

## 阶段契约
| 英文名 | 中文名 | 中文说明 |
| --- | --- | --- |
| `SettingsApplyOperationHeader` | 配置应用公共头 | 描述操作名、目标资源、候选版本，禁止裸字符串驱动切换流程 |
| `HttpResourceSwitchDetail` | HTTP 资源切换扩展 | `kind/schema_version/extra="forbid"`，描述候选构建、切换、回滚策略 |
| `TaskRegistryReloadDetail` | 任务注册切换扩展 | `kind/schema_version/extra="forbid"`，描述注册替换与恢复策略 |
| `SettingsApplyOperationEnvelope` | 配置应用操作信封 | 外层 `header + detail`，`detail` 使用 Pydantic 判别联合 |
| `SettingsApplyResultPayload` | 配置应用结果载荷 | 返回 `success`、`rolled_back`、`active_snapshot_id`、`restored_resources` |

## 源码补充锚点
当前 `SharedResourceMount.apply_settings` 的风险入口是先写入现态，再重建资源与注册表；Phase 1 的改造点必须落在这里。

```python
self._settings_holder.current_settings = settings
self._rebuild_http_resources(settings)
self._password_hasher = self._build_password_hasher(settings)
self._jwt_token_service = self._build_jwt_token_service(settings)
self._bootstrap_admin_synchronizer = BootstrapAdminSynchronizer(
    password_hasher=self._password_hasher
)
self._task_registration_registry.replace_registrations(
    settings.modules.task.registrations
)
self._sync_task_bindings_to_bootstrapper()
if self._cache_service is not None:
    self._auth_failure_throttle = AuthFailureThrottle(
        cache_service=self._cache_service,
        settings=settings.runtime.auth,
    )
self._logger_factory.update_level(
    self._logger,
    settings.runtime.logging.level.value,
)
if self._log_buffer_dispatcher is not None:
    self._flush_logs(reason=LogWriteReason.MANUAL)
```

当前 `SettingsReloadCoordinator._apply_candidate` 已经保留了本阶段必须延续的校验与快照语义，相关注释与语义不得丢失。

```python
# 热更新先做“绝对禁止”校验，再做“允许但需重启”校验，避免配置进入半生效状态。
unsafe_changes = self._collect_unsafe_changes(
    current_settings=current_settings,
    candidate_settings=candidate_settings,
)
...
# 只有资源挂载点确认应用成功后，才推进快照版本，保证回滚基线可靠。

self._snapshot_store.save(
    SettingsSnapshot(
        version_id=candidate_digest[:CANDIDATE_VERSION_LENGTH],
        digest=candidate_digest,
        settings=candidate_settings.model_copy(deep=True),
    )
)
...
# 失败时用最近一次成功快照恢复内存态，避免部分组件继续持有候选配置。
self._settings_holder.current_settings = latest_snapshot.settings.model_copy(
    deep=True
)
```

## 代码现状、目标形态与修改路径
- 代码现状：`src/infrastructure/shared_resource_mount.py` 当前在 `apply_settings` 内先写入 `current_settings`，再重建 HTTP 资源，并继续更新密码哈希器、JWT 服务、管理员同步器、任务注册、认证节流、日志级别与日志刷新。
- 代码现状：`src/infrastructure/settings/settings_reload_coordinator.py` 当前在 `_apply_candidate` 内保留了“绝对禁止”优先于“允许但需重启”的校验顺序，并在 `self._on_settings_applied(candidate_settings)` 成功后才保存快照。
- 代码现状：`test/conftest.py` 已通过 `APP_ENV=test` 装配测试环境；`pyproject.toml` 仍是本阶段收口 pytest 入口、`pythonpath`、`testpaths` 的修改落点。
- 目标形态：候选资源先完成构建，再统一切换运行时引用；仅在切换成功后推进快照；失败时恢复到同一成功版本对应的配置、资源与任务注册状态；测试入口由本地与 CI 共用同一套收口配置。
- 修改路径：`src/infrastructure/settings/settings_apply_contract.py`、`src/infrastructure/settings/settings_apply_transaction.py`、`src/infrastructure/shared_resource_mount.py`、`src/infrastructure/settings/settings_reload_coordinator.py`、`pyproject.toml`、`test/conftest.py`。

## 分步骤执行方案
### 步骤 1：固化热更新事务契约与候选资源切换
- 阶段目标：新增热更新事务契约与原子切换执行器，先构建候选资源，再执行引用切换。
- 依赖关系：`src/infrastructure/settings/settings_apply_contract.py`、`src/infrastructure/settings/settings_apply_transaction.py`、`src/infrastructure/shared_resource_mount.py`、`src/infrastructure/settings/settings_reload_coordinator.py`
- 执行内容：保留 `header + detail`、Pydantic 判别联合、`kind`、`schema_version`、`extra="forbid"` 这些强约束；禁止回退到裸字典或弱类型切换。
- 执行内容：事务执行器需要显式表达候选资源构建、引用切换、失败恢复、结果回传，不能继续把切换副作用散落在挂载点内部。
- 验收点：候选资源先于现态切换完成；切换动作可以回传 `success`、`rolled_back`、`active_snapshot_id`、`restored_resources` 所需信息。

### 步骤 2：改写 `SharedResourceMount.apply_settings`
- 阶段目标：重写 `SharedResourceMount.apply_settings`，禁止“先覆盖 current_settings 再销毁旧资源”。
- 依赖关系：`src/infrastructure/shared_resource_mount.py`
- 执行内容：以候选资源对象承接 HTTP client、async client、request bridge、task registry 的新版本构建，切换成功后再统一替换挂载引用。
- 执行内容：当前 `apply_settings` 还会同步更新密码哈希器、JWT 服务、管理员同步器、认证节流、日志级别与日志刷新；修改路径仍落在 `src/infrastructure/shared_resource_mount.py`，这些运行时依赖需要与候选资源切换保持同一成功版本。
- 验收点：热更新成功时，新配置与新资源同时生效。

### 步骤 3：收口协调器快照推进与失败回滚
- 阶段目标：调整 `SettingsReloadCoordinator`，仅在资源切换成功后推进快照。
- 依赖关系：`src/infrastructure/settings/settings_reload_coordinator.py`、`SettingsSnapshotStore`、`SettingsStateHolder`
- 执行内容：保留“绝对禁止”校验优先于“允许但需重启”校验的顺序，避免候选配置进入半生效状态。
- 执行内容：为失败回滚补齐旧资源恢复逻辑，至少覆盖 HTTP client、async client、request bridge、task registry。
- 执行内容：失败时不仅恢复 `current_settings`，还要恢复到同一成功版本对应的运行资源与注册状态。
- 验收点：热更新失败时，旧配置与旧资源同时保留。
- 验收点：热更新失败后，配置快照、HTTP 资源、请求执行桥、任务注册状态保持同一成功版本，无半生效状态。

### 步骤 4：收口 pytest 入口与测试环境
- 阶段目标：在 `pyproject.toml` 收口 pytest 入口、`pythonpath`、`testpaths`，在 `test/conftest.py` 明确测试环境装配，消除 `src` 导入漂移。
- 依赖关系：`pyproject.toml`、`test/conftest.py`
- 执行内容：本地与 CI 使用同一测试入口，不再依赖临时环境变量、IDE 私有路径或手工拼接路径启动。
- 执行内容：测试环境继续以 `APP_ENV=test`、测试数据库预备、JWT 测试密钥等现有约束装配，避免因为入口收口引入新漂移。
- 验收点：`uv run python -m pytest -q test/unit_test test/path_test -x` 可正常收集。
- 验收点：`uv run python -m pytest` 可稳定收集测试，无 `ModuleNotFoundError: src`。

### 步骤 5：Phase 1 核验与文档回归
- 阶段目标：让源码、测试、Phase 1 文档三者一致。
- 依赖关系：Phase 1 所有修改项完成后统一回归。
- 执行顺序：执行修改 -> 新增或修改测试 -> 真实测试 -> 回归修复 -> 文档回归。
- 执行内容：测试覆盖单测、路径/边界回归、至少一条真实集成链路；不允许以放宽断言、跳过测试、保留死代码替代真实修复。
- 执行内容：若文档与源码冲突，以源码为准，并在文档回归中标注旧文档可能过期。
- 验收点：设计文档、测试规范、执行方案文档与源码行为一致。

- 热更新失败后，配置快照、HTTP 资源、请求执行桥、任务注册状态保持同一成功版本，无半生效状态。
- 保持现有统一错误码、统一日志结构、统一响应外壳不变。
