# 任务强类型校验与注册收口实施方案

## 阶段目标
- 让 `payload_model` 从“占位字段”变成真实运行时约束。
- 清理任务注册与装配链中的死代码、重复定义与弱校验。

## 相关约束
- 依赖 Phase 1 的稳定测试入口。
- 编码遵循 `docs/standard`。
- 若文档、图谱、源码冲突，以源码为准，并在文档回归中标注旧文档可能过期。
- 不允许以放宽断言、跳过测试、保留死代码替代真实修复。
- 新增或修改契约统一采用“公共头字段 + 强类型扩展字段”：
  - 外层结构固定为 `header + detail`
  - `detail` 必须使用 Pydantic 判别联合
  - 每个扩展模型必须包含 `kind`、`schema_version`
  - 每个扩展模型必须 `extra="forbid"`
  - 禁止 `dict[str, Any]`、`metadata`、`extra_payload`
  - 外层类型与内层扩展类型必须一致
- 保持现有统一错误码、统一日志结构、统一响应外壳不变。
- 测试必须覆盖单测、路径/边界回归、至少一条真实集成链路。
- 本阶段按硬迁移一次性收口，不采用任何渐进式迁移设计，不保留 `BaseModel` 占位兼容路径。

## 依赖与范围


## 阶段契约
| 英文名                           | 中文名                | 中文说明                                                     |
| -------------------------------- | --------------------- | ------------------------------------------------------------ |
| `TaskRegistrationHeader`         | 任务注册公共头        | 保留现有 `job_kind/backend/enabled` 主语义，继续作为任务注册唯一入口 |
| `LocalTaskRegistrationDetail`    | 本地任务注册扩展      | `kind/schema_version/extra="forbid"`，定义本地重试与执行约束 |
| `FunboostTaskRegistrationDetail` | Funboost 任务注册扩展 | `kind/schema_version/extra="forbid"`，定义队列、路由、消费约束 |
| `RegisteredTaskBinding`          | 已注册任务绑定        | `payload_model` 必须是具体 Pydantic 模型类，禁止 `BaseModel` 占位 |
| `TaskMessageEnvelope`            | 任务消息信封          | `payload_kind` 必须与 `payload_model` 对应，分发前先做 `model_validate_json` |

## 分步骤实施方案
### 步骤 1：收口注册入口与绑定约束
- 目标：修改 `register_task_handler` / `register_handler`，不再默认注入 `BaseModel`，并把注册阶段的弱校验收紧为硬约束。
- 代码现状：`src/infrastructure/shared_resource_mount.py` 的 `register_task_handler` 与 `src/infrastructure/task/task_worker_supervisor.py` 的 `register_handler` 仍默认把 `payload_model=BaseModel` 注入 `RegisteredTaskBinding`；`TaskRegistrationRegistry.register_binding` 当前仅校验 `payload_model` 是否为 `BaseModel` 子类，因此 `BaseModel` 占位仍会穿过注册入口。
- 目标形态：任务注册入口只接受具体 Pydantic 模型类，`BaseModel` 占位在注册阶段直接失败；`TaskRegistrationEnvelope + detail` 判别联合口径保持不变。
- 修改路径：`src/infrastructure/shared_resource_mount.py`、`src/infrastructure/task/task_worker_supervisor.py`、`src/infrastructure/task/task_registration_registry.py`、`src/core/task_contract/task_registration_contract.py`
- 动作：
  - 修改 `src/infrastructure/shared_resource_mount.py` 中 `register_task_handler`，不再以 `BaseModel` 作为默认 `payload_model` 注入。
  - 修改 `src/infrastructure/task/task_worker_supervisor.py` 中 `register_handler`，不再以 `BaseModel` 作为默认 `payload_model` 注入。
  - 在 `TaskRegistrationRegistry` 注册阶段拒绝无效 `payload_model`、重复 `job_kind`、缺失注册项绑定。
  - 保持现有 `TaskRegistrationEnvelope + detail 判别联合` 规则，不引入 `dict[str, Any]` 扩展字段。
- 依赖：依赖 Phase 1 的稳定测试入口；前置文件为 `src/infrastructure/task/*.py`、`src/core/task_contract/task_registration_contract.py`。
- 源码落点补充：
```python
self.register_binding(
    RegisteredTaskBinding(
        job_kind=job_kind,
        payload_model=BaseModel,
        handler=handler,
    )
)
```
- 验收：
  - `BaseModel` 占位注册必须失败。
  - 在注册阶段拒绝无效 `payload_model`、重复 `job_kind`、缺失注册项绑定。
  - `TaskRegistrationRegistry` 无重复方法与静默覆盖死代码。

### 步骤 2：收口本地分发前的强类型校验
- 目标：让 `LocalTaskDispatcher` 在执行处理器前按 `payload_model` 解析消息载荷。
- 代码现状：`src/infrastructure/task/local_task_dispatcher.py` 的 `_execute_handler` 当前在拿到 `resolved_binding` 后直接执行 `handler.handle(message)`，本地分发侧没有在处理前执行 `payload_model.model_validate_json(...)`。
- 目标形态：本地分发必须先用 `resolved_binding.binding.payload_model` 对 `message.payload.payload_json` 做真实校验，校验通过后才进入处理器。
- 修改路径：`src/infrastructure/task/local_task_dispatcher.py`
- 动作：
  - 在 `src/infrastructure/task/local_task_dispatcher.py` 中，先解析 `resolved_binding.binding.payload_model`，再对 `message.payload.payload_json` 执行真实校验。
  - 校验通过后才允许 `handler.handle(message)` 继续执行；不允许“先处理、后报错”。
- 依赖：步骤 1 已完成，注册中心能够返回可信的 `payload_model`。
- 关键代码片段：
```python
payload_model = resolved_binding.binding.payload_model
payload_model.model_validate_json(message.payload.payload_json)
resolved_binding.binding.handler.handle(message)
```
- 验收：
  - 非法 payload 在本地分发侧必须早失败。
  - 保持现有统一错误码、统一日志结构、统一响应外壳不变。

### 步骤 3：收口 Funboost 消费侧的强类型校验
- 目标：让 `FunboostTaskBootstrapper` 在消费侧执行同样的强类型校验。
- 代码现状：`src/infrastructure/task/funboost_task_bootstrapper.py` 的 `consume_funboost_message` 当前仅执行 `TaskMessageEnvelope.model_validate(...)`，随后直接调用 `resolved_binding.binding.handler.handle(task_message)`，未在消费侧补做 `payload_model` 校验。
- 目标形态：Funboost 消费函数保留“只负责消息收发，真正的任务处理仍回到项目统一的处理器绑定上”的原始注释语义，但在进入处理器前补齐与本地分发一致的强类型校验。
- 修改路径：`src/infrastructure/task/funboost_task_bootstrapper.py`
- 动作：
  - 在 `src/infrastructure/task/funboost_task_bootstrapper.py` 的消费函数中，在 `TaskMessageEnvelope.model_validate(...)` 之后、`handler.handle(...)` 之前补上 `payload_model` 校验。
  - 保持 Funboost 仅负责消息收发，真正的任务处理仍回到项目统一的处理器绑定上。
- 依赖：步骤 1 已完成，注册中心可以提供 `ResolvedTaskBinding`；步骤 2 的本地分发口径同步用于消费侧。
- 源码落点补充：
```python
def consume_funboost_message(message_payload: dict[str, object]) -> None:
    # Funboost 只负责消息收发，真正的任务处理仍回到项目统一的处理器绑定上。
    task_message = TaskMessageEnvelope.model_validate(
        message_payload["task_message"]
    )
    resolved_binding.binding.handler.handle(task_message)
```
- 验收：
  - 非法 payload 在 Funboost 消费侧都必须早失败。
  - 至少一条真实集成链路覆盖消费校验。

### 步骤 4：清理注册中心重复定义与弱校验
- 目标：删除 `TaskRegistrationRegistry` 中重复的 `build_bootstrap_snapshot`，保证注册、绑定、装配快照逻辑单一。
- 代码现状：`src/infrastructure/task/task_registration_registry.py` 中存在两份 `build_bootstrap_snapshot` 定义，后定义会覆盖前定义，形成静默覆盖死代码。
- 目标形态：`TaskRegistrationRegistry` 仅保留一份装配快照构建逻辑，本地任务与 Funboost 任务的注册/装配入口保持唯一。
- 修改路径：`src/infrastructure/task/task_registration_registry.py`
- 动作：
  - 删除 `src/infrastructure/task/task_registration_registry.py` 中重复的 `build_bootstrap_snapshot`。
  - 保留现有本地/Funboost 注册项约束，继续校验重复 `queue_name` 与缺失绑定。
  - 避免以保留死代码或静默覆盖方式维持兼容。
- 依赖：步骤 1 完成后再收口重复定义，避免重复调整同一注册校验链路。
- 验收：
  - `TaskRegistrationRegistry` 无重复方法与静默覆盖死代码。
  - 本地任务与 Funboost 任务的注册/装配入口保持唯一。

- 修改路径：`test/unit_test/test_task_registration_registry_unit.py`、`test/integration_test/test_funboost_rabbitmq_integration.py`、本阶段拆解文档
