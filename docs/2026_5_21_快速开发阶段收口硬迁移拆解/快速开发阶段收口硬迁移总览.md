# 快速开发阶段收口硬迁移总览

## 任务概览与基本约束

### 任务来源
- 原始大型任务文档：`docs/2026_5_21_1140_快速开发阶段收口执行方案.md`

### 任务目标
- 交付一套可进入后续快速开发阶段的代码底座：热更新无半生效、测试可一键执行、任务 `payload_model` 强类型生效、核心热点完成首轮拆分。
- 完成判定：源码、测试、文档三者一致；若文档与源码冲突，已按“源码为准”完成文档回归说明。
- 本方案为硬迁移方案，目标是一次性将整个模块重构至最佳实践状态，不采用任何渐进式迁移设计。

### 基本约束
- 编码遵循 `docs/standard`。
- 若文档、图谱、源码冲突，以源码为准，并在文档回归中标注旧文档可能过期。
- 不允许以放宽断言、跳过测试、保留死代码替代真实修复。
- 新增或修改契约统一采用“公共头字段 + 强类型扩展字段”：
  - 外层结构固定为 `header + detail`
  - `detail` 必须使用 Pydantic 判别联合
  - 每个扩展模型必须包含 `kind`、`schema_version`
  - 每个扩展模型必须 `extra="forbid"`
  - 禁止 `dict[str, Any]`、`metadata`、`extra_payload`
  - 外层类型与内层扩展类型必须一致
- 保持现有统一错误码、统一日志结构、统一响应外壳不变。
- 不新增新的中心化超大文件；拆分后入口文件只负责装配与转发。
- 测试必须覆盖单测、路径/边界回归、至少一条真实集成链路。

### 全局验收标准
- 热更新失败后，配置快照、HTTP 资源、请求执行桥、任务注册状态保持同一成功版本，无半生效状态。
- `uv run python -m pytest` 可稳定收集测试，无 `ModuleNotFoundError: src`。
- 本地任务与 Funboost 任务在分发/消费前都按 `payload_model` 完成真实校验，禁止 `BaseModel` 占位注册。
- `TaskRegistrationRegistry` 无重复方法与静默覆盖死代码。
- `SharedResourceMount`、`AppSettingsLoader` 完成首轮职责拆分，新增功能不再继续堆入单文件。
- 设计文档、测试规范、执行方案文档与源码行为一致。

### 生命周期
1. 执行修改
2. 新增或修改测试
3. 真实测试
4. 回归修复
5. 文档回归

## 跨阶段依赖
- Phase 1 无前置，先收口热更新原子性与测试入口。
- Phase 2 依赖 Phase 1 的测试基线与回滚机制。
- Phase 3 依赖 Phase 1、Phase 2，基于稳定行为做热点拆分与扩展入口降耦。
