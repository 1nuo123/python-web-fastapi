# 热点拆分与装配降耦实施方案

## 阶段目标与执行边界
- 对 `SharedResourceMount` 与 `AppSettingsLoader` 做首轮职责拆分。
- 降低 Web 模块接入与依赖访问的中心化程度，减少后续并行开发冲突。
- 本阶段按硬迁移执行：一次性完成目标结构重组，不采用任何渐进式迁移设计。
- 本文只覆盖 Phase 3 涉及的 Web 装配、配置分节、依赖访问降耦，不扩写其他阶段任务。

## 本阶段适用的全局约束
- 若文档、图谱、源码冲突，以源码为准，并在文档回归中标注文档可能过期。
- 不允许以放宽断言、跳过测试、保留废代码替代真实修复。
- 新增或修改契约统一采用“公共头字段 + 强类型扩展字段”。
- 外层结构固定为 `header + detail`。
- `detail` 必须使用 Pydantic 判别联合。
- 每个扩展模型必须包含 `kind`、`schema_version`，且 `extra="forbid"`。
- 禁止 `dict[str, Any]`、`metadata`、`extra_payload`。
- 外层类型与内层扩展类型必须一致。
- 保持现有统一错误码、统一日志结构、统一响应外壳不变。
- 不新增新的中心化超大文件；拆分后入口文件只负责装配与转发。
- 测试必须覆盖单测、路径/边界回归、至少一条真实集成链路。

## 依赖
- 依赖 Phase 1 的原子切换能力。
- 依赖 Phase 2 的任务契约稳定行为。
- 当前直接落点：
  - `src/infrastructure/shared_resource_mount.py`
  - `src/infrastructure/fastapi_app_assembler.py`
  - `src/infrastructure/settings/app_settings_loader.py`
  - `src/api/web_bundle_catalog.py`
  - `src/api/dependency_context_accessor.py`

## 阶段契约
| 英文名 | 中文名 | 中文说明 |
| --- | --- | --- |
| `SettingsSectionHeader` | 配置节公共头 | 描述配置节名称、来源、版本，用于替代单大文件内联分支 |
| `ModuleSettingsSectionDetail` | 模块配置节扩展 | `kind/schema_version/extra="forbid"`，负责模块区段解析 |
| `RuntimeSettingsSectionDetail` | 运行时配置节扩展 | `kind/schema_version/extra="forbid"`，负责运行时区段解析 |
| `SettingsSectionEnvelope` | 配置节信封 | 外层 `header + detail`，`detail` 使用 Pydantic 判别联合 |
| `WebBundleProviderEnvelope` | Web 模块提供者信封 | 外层 `header + detail`，用于去中心化装配路由提供者 |

## 分步骤实施方案
### 步骤 1：拆分 `SharedResourceMount` 热点职责
- 原始任务口径：从 `SharedResourceMount` 抽离 HTTP 资源管理、任务运行时管理、鉴权/日志访问器。
- 代码现状：
  - `SharedResourceMount` 当前同时承接 HTTP、缓存、消息、任务、鉴权、日志初始化与热更新重建，热点集中。
- 目标形态：
  - `SharedResourceMount` 退回为生命周期协调与稳定门面，具体资源分别落到独立 manager/accessor。
- 实施方案：
  - 将 HTTP 客户端、异步 HTTP 客户端、`RequestExecutionBridge` 的初始化、重建、读取收口到独立 manager。
  - 将消息总线、任务分发器、Funboost bootstrap、任务绑定同步、任务快照收口到独立 manager。
  - 将鉴权、日志读取接口拆为专用 accessor/provider；`SharedResourceMount` 只保留生命周期协调、稳定门面与兼容转发。
  - 拆分后不得形成新的中心化超大文件。
- 修改路径：
  - 修改 `src/infrastructure/shared_resource_mount.py`，抽出 HTTP、任务、鉴权/日志相关 manager/accessor，并保留原有热更新切换语义。
- 依赖关系：
  - 必须复用 Phase 1 的原子切换能力，不改变热更新后的统一应用语义。
- 验收点：
  - `SharedResourceMount` 不再继续增长为单点热点。
  - 现有路由与配置加载行为回归通过。

### 步骤 2：让 `FastApiAppAssembler` 面向 manager/provider 装配
- 原始任务口径：让 `FastApiAppAssembler` 面向拆分后的 manager/provider 装配，而不是继续直接堆字段。
- 代码现状：
  - `FastApiAppAssembler` 当前直接创建 `AppSettingsLoader`、`SharedResourceMount`、`ApplicationContainer`，并直接消费 `WebBundleCatalog().build()`。
- 目标形态：
  - 装配器仅负责配置加载、容器拼装、生命周期绑定、路由装配四类职责。
- 实施方案：
  - `ApplicationContainer` 的对外语义保持稳定，内部改为注入拆分后的 manager/provider。
  - `FastApiAppAssembler` 只保留配置加载、容器拼装、生命周期绑定、路由装配四类职责。
  - 禁止继续把新字段直接堆入 assembler、container、resource mount。
- 修改路径：
  - 修改 `src/infrastructure/fastapi_app_assembler.py`，把直接拼接的资源创建与 Web provider 装配改为面向拆分后的 manager/provider。
- 依赖关系：
  - 依赖步骤 1 的拆分产物。
- 验收点：
  - 应用装配入口仍保持单入口调用方式。
  - 对外接口、错误码与响应结构不变。

### 步骤 3：拆分 `AppSettingsLoader` 为根入口与分节解析器
- 原始任务口径：将 `AppSettingsLoader` 拆为根入口 + 模块/运行时分节解析器，保留对外加载 API。
- 代码现状：
  - `AppSettingsLoader` 当前集中承担文件收集、路径分节路由、环境覆盖与整体校验。
- 目标形态：
  - 维持现有对外加载 API，不再把新增配置节继续堆入单个超大加载器。
- 实施方案：
  - 保留 `load`、`load_for_environment`、`load_from_mapping` 对外加载 API。
  - 将文件收集、模块分节解析、运行时分节解析、环境变量覆盖、整体校验拆开。
  - 用 `SettingsSectionHeader`、`ModuleSettingsSectionDetail`、`RuntimeSettingsSectionDetail`、`SettingsSectionEnvelope` 承接分节契约。
  - 继续保持 `header + detail`、Pydantic 判别联合、`kind/schema_version/extra="forbid"`。
- 修改路径：
  - 修改 `src/infrastructure/settings/app_settings_loader.py`，拆出根入口与模块/运行时分节解析职责，同时保持原有加载入口不变。
- 依赖关系：
  - 依赖 Phase 1 的原子切换能力继续消费稳定配置快照。
- 验收点：
  - 新增配置节时，不再继续把分支堆入单个超大加载器。
  - 现有配置加载 API 与行为不变。

### 步骤 4：改造 `WebBundleCatalog` 为 provider/registry
- 原始任务口径：改造 `WebBundleCatalog` 为 provider/registry 形式，降低手工集中登记成本。
- 代码现状：
  - `WebBundleCatalog.build()` 当前通过集中列表手工登记 `HealthProbe`、`SystemOverview`、`AuthAccess` 三个 bundle。
- 目标形态：
  - Web 模块侧自带 provider/registry 注册，中心入口只做装配与转发。
- 实施方案：
  - 从静态 `build()` 列表改为 provider/registry 形式。
  - 使用 `WebBundleProviderEnvelope` 承接 provider 的 `header + detail` 契约。
  - 新增 Web 模块时，只在模块侧新增 provider/registry 注册，不再回到中心化清单逐处登记。
- 修改路径：
  - 修改 `src/api/web_bundle_catalog.py` 及对应 Web 模块注册落点，把集中列表改为 provider/registry 装配。
- 依赖关系：
  - 依赖步骤 2 的装配入口已转向 provider。
- 验收点：
  - 新增 Web 模块时，不再必须修改多处中心化清单。
  - 现有路由路径、错误码与响应结构不变。

### 步骤 5：收缩 `DependencyContextAccessor`
- 原始任务口径：收缩 `DependencyContextAccessor`，仅保留路由直接需要的依赖读取接口。
- 代码现状：
  - `DependencyContextAccessor` 当前集中封装 `request.state` 与 `request.app.state.container` 的读取逻辑，并向路由暴露 `response_factory`、`resource_mount`、`request_execution_bridge` 等入口。
- 目标形态：
  - 路由层只保留直接需要的稳定读取路径，非路由直接依赖回收到更小的 provider/accessor。
- 实施方案：
  - 仅保留路由直接需要的读取接口，减少路由层对 `app.state.container` 结构的感知。
  - 将非路由直接依赖的读取逻辑回收到更小的 provider/accessor 中。
  - 保留路由直接依赖的鉴权、请求执行桥接、响应工厂等稳定读取路径。
- 修改路径：
  - 修改 `src/api/dependency_context_accessor.py`，删除非路由直接依赖读取项，保留鉴权、请求执行桥接、响应工厂等稳定读取路径。
- 依赖关系：
  - 依赖步骤 1 和步骤 2 的容器与 provider 拆分完成。
- 验收点：
  - Web 依赖访问不再继续中心化膨胀。
  - 现有路由与鉴权行为回归通过。

### 步骤 6：保持外部稳定并完成回归
- 原始任务口径：保证对外接口、现有路由路径、错误码与响应结构不变。
- 实施方案：
  - 回归对外接口、现有路由路径、错误码、响应结构。
  - 同步回归配置加载行为、应用级装配行为、热更新后的 Web 装配行为。
  - 若回归触发文档偏差，同步做文档回归，不留口头约定。
- 本阶段必须保留的原始校验：
  - 新增 Web 模块时，不再必须修改多处中心化清单。
  - `SharedResourceMount` 与 `AppSettingsLoader` 不再继续增长为单点热点。
  - 现有路由与配置加载行为回归通过。
- 与本阶段直接相关的测试与回归动作：
  - 修改 `test/path_test/test_runtime_path.py`，覆盖热更新成功/失败两条路径。
  - 修改 `test/integration_test/test_app_integration.py`，覆盖应用级热更新与任务注册真实链路。
  - 执行 `uv run python -m pytest -q test/unit_test test/contract_test test/path_test test/initialization_test`。
  - 执行 `uv run python -m pytest -q test/boundary_test test/interface_test test/exception_test test/convention_usage_test`。
  - 执行 `uv run python -m pytest -q test/integration_test/test_app_integration.py`。

  - 最终执行 `uv run python -m pytest -q`。
  - 真实测试失败时，优先修源码与契约，不以放宽断言代替修复。
  - 若失败由测试夹具或环境装配引起，同步修 `conftest.py` 与 `pyproject.toml`。
  - 每次修复后先回跑最小失败集，再回跑阶段测试集，最后回跑全量。
  - 若回归触发文档偏差，同步加入文档回归清单，不留口头约定。
- 阶段完成标志：
  - `SharedResourceMount`、`AppSettingsLoader` 完成首轮职责拆分，新增功能不再继续堆入单文件。
  - 设计文档、测试规范、执行方案文档与源码行为一致。
