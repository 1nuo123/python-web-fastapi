# FastAPI 工作区生产级代码全量审查与整改执行方案

## 任务目标

对 `src/`、`config/`、`test/`、容器与依赖配置、部署入口和项目手册执行源码级审查及整改，交付可持续快速开发的生产级基建：边界清晰、契约强类型、测试可分层独立运行、生产配置默认安全，并具备可验证的横向扩容、背压、超时、幂等、可观测与故障恢复能力。

当前只能判定“基础能力较完整，但尚未达到可证明的生产就绪状态”：历史 P0/P1 整改已有较好基础，语法编译、锁文件及两套 Compose 配置校验通过；但全量 `pytest -q` 因会话级自动数据库夹具在 PostgreSQL 不可用时产生 `698 errors, 4 skipped`，所有单元测试也被外部数据库阻断；同时缺少静态检查、类型、覆盖率、依赖漏洞、架构依赖和持续集成门禁。源码还存在 `shared_resource_mount.py`（约 3322 行）、`app_settings_loader.py`（约 2478 行）、管理员身份路由与仓储等高复杂度热点，以及 infrastructure 反向依赖 api、测试依赖 `portalocker` 未直接声明、少量乱码文档字符串等问题。因此现阶段不得声明“不存在 P0/P1”。

完成判定：全量审查发现均有证据和处置结论；P0/P1 为零；已批准范围内的整改、测试、真实环境回归和文档回归全部通过；关键路径不存在未解释的跨层依赖；生产镜像、迁移、配置、安全和并发基建具备可重复验证结果。

## 全局约束

- 事实优先级固定为：当前源码与迁移 > 可执行配置与测试 > 当前项目手册 > 历史方案；冲突时按源码整改并标注文档可能过期。
- 先建立可回滚基线。当前目录没有可用 `.git` 元数据，二级模块重构前必须接入原仓库或建立本地版本基线，不覆盖未知历史。
- 审查覆盖正确性、可读性、扩展性、维护性、稳定性、安全性、性能基建、数据一致性、部署和供应链；发现按 P0/P1/P2/P3 分级，P0/P1 先于结构优化处理。
- 不改变既有 HTTP 路径、状态码、响应语义、配置键、数据库兼容性和任务消息语义；确需变更时使用显式版本、迁移和兼容窗口，不做静默破坏。
- 公共契约统一使用“公共头字段 + 强类型扩展字段”。扩展字段必须是 Pydantic 判别联合，具有 `kind`、`schema_version`，所有模型启用 `ConfigDict(extra="forbid")`；禁止 `dict[str, Any]`、`metadata`、`extra_payload`；外层类型、判别值与内层扩展类型必须一致。
- 已触发二级模块重构阈值：组合根、配置加载、管理员身份路由/仓储按职责拆分；仅在引用分析、契约测试和关键路径验证齐备后实施。同步数据库访问继续通过有界线程池隔离，除非基准证明异步数据库迁移收益足够，不为“异步化”本身重写持久层。
- 单元、契约和边界测试不得依赖 PostgreSQL、Redis、RabbitMQ 或网络；集成测试通过显式 marker/fixture 启动真实依赖，失败必须报告缺失前置条件，不能把全部测试连带变为 error。
- 质量门禁采用成熟工具并固化在 `pyproject.toml`/`noxfile.py`：Ruff、Mypy、pytest-cov、import-linter、Bandit、pip-audit；不得通过扩大 ignore、降低阈值或删除断言获得通过。
- 覆盖率验收为总体 line/branch 不低于 85%，auth/security/task/persistence 关键路径不低于 90%；新增和变更分支必须覆盖成功、拒绝、超时、回滚、幂等与资源释放。
- 生产安全默认 fail closed：密钥不入库、不入日志；鉴权、RBAC、SSRF、代理头、CORS、限流、请求体、迁移和初始管理员入口执行负向测试；镜像保持非 root，补齐最小权限、只读文件系统、资源限制和优雅停机验证。
- 高并发工作以“可扩展基建”而非虚高单机数字为目标：有界连接池/线程池/队列、超时、背压、熔断或降级、幂等、横向扩容与低基数指标必须可配置、可观测、可测试。
- 若进入参数调整，在 `test/performance/autotuner/` 使用自动搜索，不盲调；逐轮记录配置、吞吐、p50/p95/p99、错误率、资源峰值和结论，输出最优/失败配置对比及是否值得继续。只有多轮、不同种子/负载均稳定的结果可晋升。
- 清理 `__pycache__`、`tmp_pycache`、空数据库、日志等工作区产物，但不把产物清理冒充业务整改；依赖必须直接声明，锁文件保持可复现。

## 验收标准

- P0/P1 未关闭项为零；P2/P3 均有负责人语义、风险说明、处置或明确延期依据，不存在“未审查即通过”。
- `src/` 编译、格式/静态检查、类型检查、架构依赖检查、单元/契约/边界/接口/异常/初始化/路径/集成测试和全量回归全部通过。
- 无外部服务时单元、契约、边界测试可独立通过；真实 PostgreSQL、Redis、RabbitMQ 环境中的迁移、事务、缓存、消息、密钥、日志和安全集成测试通过。
- 公共契约满足公共头、判别联合、`kind`、`schema_version`、`extra="forbid"` 和外内类型一致性规则，无禁用的开放字典扩展字段。
- `core`、`domain`、`application` 不依赖 `api`/`infrastructure`；`infrastructure` 不再依赖 API 路由常量，组合根与业务模块职责可独立测试。
- 生产 Compose/镜像构建、启动、健康检查、迁移门禁、非 root、最小权限、资源与停机检查通过；依赖漏洞扫描无未豁免的高危/严重项。
- 并发基准无未处理 5xx、死锁、连接泄漏和无界增长；p95 相对已冻结基线不劣化超过 20%，过载时按契约背压/拒绝而非雪崩；自动调参报告可复现。
- 项目手册、API/OpenAPI、配置样例、迁移说明、安全与运维说明和最终审查报告与源码及真实测试结果一致。

### 契约

| 英文名 | 中文名 | 中文说明 |
|---|---|---|
| `ContractHeader` | 公共契约头 | 统一承载契约标识、业务主键/追踪字段和外层类型；不得承载可变扩展字典。 |
| `ContractDetailUnion` | 强类型扩展联合 | 使用 `Annotated[Union[...], Field(discriminator="kind")]` 表达扩展模型，只包含业务允许的具体类型。 |
| `kind` | 扩展类型 | 每个扩展模型使用唯一 `Literal` 判别值；外层声明必须与内层实际类型一致。 |
| `schema_version` | 契约版本 | 每个扩展模型必须显式提供 `Literal` 版本，用于兼容和迁移判断。 |
| `model_config` | 模型约束 | 公共头、扩展模型和外层 envelope 全部使用 `ConfigDict(extra="forbid")`。 |
| `RuntimeCapacityPolicy` | 运行时容量策略 | 强类型描述数据库池、线程池、HTTP 池、任务 worker、队列上限、超时和过载行为；环境覆盖必须校验一致性。 |

### 校验

- 断开所有外部服务后，unit/contract/boundary 能独立运行且不触发数据库夹具。
- 测试收集无 marker 警告，新增失败用例可在旧实现复现、在新实现通过。
- autotuner dry-run 能产生合法轮次记录、最优/失败对比与“是否继续”结论。

## Phase 3：真实测试

### 目标

在可复现的本地与容器环境中执行完整质量、安全、集成、迁移、镜像和并发验证，产出可作为生产就绪判断依据的真实结果，而非只依赖 mock 或历史报告。

### 依赖

- Phase 1、Phase 2 完成。
- Docker/Compose 可用；测试专用 PostgreSQL、Redis、RabbitMQ 健康；测试密钥与生产样例隔离。
- 冻结基准机器、Python/依赖版本、数据规模、并发模型和基线提交/快照。

### 契约

| 英文名 | 中文名 | 中文说明 |
|---|---|---|
| `TestRunHeader` | 测试运行公共头 | 记录运行 ID、代码基线、环境、开始时间和命令入口。 |
| `TestRunDetailUnion` | 测试运行扩展联合 | 以 `kind` 判别 static、unit、integration、security、migration、image、load 结果；均含 `schema_version` 并禁止额外字段。 |
| `TestRunStatus` | 测试状态 | 固定为 `passed/failed/blocked`；blocked 必须给出可复现的外部前置条件，不能记为 passed。 |
| `BenchmarkPromotion` | 基准晋升结论 | 固定为 `promoted/rejected/candidate`，同时记录相对基线、稳定性和过拟合/偶然性判断。 |

### 任务清单

- [x] 顺序执行编译、Ruff、Mypy、import-linter、Bandit、pip-audit、锁文件和敏感信息扫描。
- [x] 在无外部服务环境执行 unit → contract → boundary → interface/exception/path/initialization 快速层。
- [x] 启动真实依赖，执行 Alembic 空库升级、旧版本升级、重复升级、失败回滚与 migration job 测试。
- [x] 执行 PostgreSQL、Redis、RabbitMQ、Funboost、密钥、分布式锁、日志、任务 Outbox 和生产安全集成测试。
- [x] 执行全量 pytest 与覆盖率门禁；任何 skip/xfail 必须有明确、仍有效的原因。
- [x] 构建生产镜像，执行容器启动、存活/就绪、非 root、最小权限、只读写边界、SIGTERM 优雅停机和重启恢复测试。
- [x] 执行稳定负载、突发、过载、依赖降级与多实例场景，观察 p50/p95/p99、错误率、池等待、队列深度、内存/线程/连接和恢复时间。

- [x] 汇总所有运行结果、失败日志摘要、最优/失败参数对比和生产就绪结论。

### 校验

- 所有命令返回码、测试计数、覆盖率、安全扫描和镜像摘要均写入回归报告。
- P0/P1 为零，真实测试无未解释 error；负载期间无死锁、泄漏、无界增长和敏感信息暴露。
- 性能结论至少复跑一次；单轮偶然最优不得晋升。

## Phase 4：回归修复

### 目标

对 Phase 3 暴露的问题做根因修复，保持测试可信度和外部兼容性，直至阻断项清零并形成稳定回归结果。

### 依赖

- Phase 3 的失败命令、结构化结果、日志、环境快照和性能轮次记录。

### 契约

- [x] 禁止删除有效断言、扩大忽略、吞异常、降低覆盖率或性能阈值来“修复”失败。

- 无通过降低门禁、隐藏异常或改变未声明外部行为产生的伪修复。
