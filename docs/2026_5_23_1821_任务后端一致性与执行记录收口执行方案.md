# 任务后端一致性与执行记录收口执行方案

## 任务目标
交付任务后端一致性强约束、执行记录语义补齐、默认 demo 任务绑定隔离三项整改方案，供后续真实改码、测试回归与文档回归执行。

完成判定是：
- `runtime.task.backend` 与任务注册 `header.backend` 不一致时，不能分发或执行任务。
- 执行记录明确保存 `backend`、`queue_name`、`stage`，本地与 Funboost 状态语义不混淆。
- 生产启动不再隐式绑定 `demo/noop` 默认任务，测试与开发示例被显式隔离。

## 全局约束
- 以源码为准；若文档、图谱、历史执行方案与源码冲突，以源码执行，并标注旧文档可能过期。
- 保持分层边界：`src/core` 放契约，`src/application` 放用例和端口，`src/infrastructure` 放实现、装配、持久化。
- 契约采用“公共头字段 + 强类型扩展字段”规则。
- 扩展字段必须使用 Pydantic 判别联合，必须包含 `kind`、`schema_version`，必须启用 `extra="forbid"`。
- 禁止使用 `dict[str, Any]`、`metadata`、`extra_payload` 承载稳定协议。
- 外层类型与内层扩展类型必须一致，新增校验必须在模型或注册中心入口完成。
- 后端一致性校验必须做双层防护：用例分发前校验，dispatcher 执行前再次校验。
- 日志和异常信息使用中文，错误码沿用现有 `CoreErrorCode.CONFIG_INVALID` / `TASK_FAILED` 体系。
- 数据库迁移必须兼容历史执行记录；历史记录无法可靠反推 backend 时，在文档回归中说明旧记录语义可能不完整。

## 验收标准
- 本地运行时不能分发或执行 Funboost 注册任务，Funboost 运行时不能分发或执行本地注册任务。
- `TaskExecutionRecordEnvelope`、ORM、仓储、store、dispatcher 返回结果中的 `backend`、`queue_name`、`stage` 一致。
- `mark_running()`、`mark_success()` 不再默认写入 `LOCAL_EXECUTION`，Funboost 消费侧写入 `CONSUME_EXECUTION`。
- `FastApiAppAssembler` 不再在未显式传入任务绑定时自动使用 demo/noop 绑定。
- 测试、真实回归、文档回归全部通过。

## Phase 1
### 目标
建立 runtime backend 与任务注册 backend 的强一致性校验，阻断本地 dispatcher 执行 Funboost 注册任务的风险。

当前阶段完成后，任务分发入口、注册中心、local/funboost dispatcher 都只能处理与当前运行时 backend 匹配的启用注册项。

### 依赖
- 现有 `TaskRegistrationEnvelope.header.backend` 与 `detail.kind` 一致性校验。
- 现有 `TaskRuntimeSettingsContract.backend`。
- 现有 `DispatchBackgroundJobUsecase`、`TaskRuntimePort`、`TaskRegistrationRegistry`、两个 dispatcher。

### 模拟用法
```python
registration = task_runtime_port.get_enabled_task_registration_for_backend(
    job_kind="demo_task_funboost",
    backend=TaskBackend.FUNBOOST,
)
```

### 契约
| 英文名 | 中文名 | 中文说明 |
|---|---|---|
| `TaskBackend` | 任务后端枚举 | 继续作为 `local`、`funboost` 唯一后端类型来源。 |
| `TaskRegistrationHeader.backend` | 注册后端 | 声明单个任务注册项允许使用的目标后端。 |
| `TaskRuntimeBackendContext` | 任务运行时后端上下文 | 新增端口级读取结果，表达当前 `runtime.task.backend`。 |
| `get_enabled_registration_for_backend` | 按后端读取启用注册项 | 注册中心方法，要求 `job_kind` 存在、启用且 `registration.header.backend == backend`。 |
| `TaskBackendMismatchFault` | 后端不匹配错误 | 后端不一致时统一抛出的配置错误语义。 |

### 任务清单
- [x] 在 `TaskRuntimePort` 增加读取当前 backend 或按 backend 读取注册项的方法。
- [x] 在 `SharedResourceMount` 实现当前 `runtime.task.backend` 暴露能力。
- [x] 在 `TaskRegistrationRegistry` 增加 `get_enabled_registration_for_backend()`。
- [x] 在 `DispatchBackgroundJobUsecase.execute()` 构建 descriptor 前校验 backend 一致性。
- [x] 在 `LocalTaskDispatcher.dispatch()` 中只接受 `TaskBackend.LOCAL` 注册项。
- [x] 在 `FunboostTaskDispatcher.dispatch()` 中只接受 `TaskBackend.FUNBOOST` 注册项。
- [x] 清理本地 dispatcher 中对 Funboost detail 的队列名兼容逻辑，避免语义混用。

### 关键代码片段
```python
runtime_backend = self._task_runtime_port.get_current_task_backend()
registration = self._task_runtime_port.get_enabled_task_registration_for_backend(
    resolved_job_kind,
    backend=runtime_backend,
)
```

### 校验
- 构造 `runtime.task.backend=local`、`job_kind=demo_task_funboost` 时应快速失败。
- 构造 `runtime.task.backend=funboost`、`job_kind=demo_task` 时应快速失败。
- 已启用且 backend 匹配的任务仍能按原入口分发。

## Phase 2
### 目标
补齐执行记录契约、ORM、仓储、store 和 dispatcher 写入语义，使 `backend`、`queue_name`、`stage` 在本地与 Funboost 场景下都准确。

当前阶段完成后，执行记录不再默认偏向本地阶段，Funboost 发布、消费、失败回写都有明确状态语义。

### 依赖
- Phase 1 的 backend 一致性保障。
- 现有 `TaskExecutionRecordEnvelope`、`TaskExecutionRecordOrmModel`、`TaskExecutionStore`、两个 dispatcher。
- 现有 Alembic 迁移链路。

### 模拟用法
```python
store.mark_running(
    job_kind="demo_task_funboost",
    deduplication_key="dedupe-1",
    attempt_count=1,
    backend=TaskBackend.FUNBOOST,
    queue_name="demo_task_funboost_queue",
    stage=TaskExecutionStage.CONSUME_EXECUTION,
)
```

### 契约
| 英文名 | 中文名 | 中文说明 |
|---|---|---|
| `TaskExecutionRecordHeader` | 执行记录公共头 | 增加 `backend`、`queue_name`，继续承载 `record_id`、`task_id`、`job_kind`、`deduplication_key`、`request_id`、`trace_id`。 |
| `TaskExecutionRecordDetailKind` | 执行记录扩展类型 | 新增状态明细类型枚举，如 `task_execution_pending_detail`、`task_execution_running_detail`。 |
| `TaskExecutionRecordDetailUnion` | 执行记录扩展判别联合 | 使用 `Field(discriminator="kind")`，每个扩展模型都有 `kind`、`schema_version`、`extra="forbid"`。 |
| `TaskExecutionPendingDetail` | 等待态扩展 | 明确 `status=PENDING`、`stage=DISPATCH`、`attempt_count`。 |
| `TaskExecutionRunningDetail` | 运行态扩展 | 明确 `status=RUNNING`、`stage`、`started_at_epoch`，stage 可为 local 或 consume。 |
| `TaskExecutionSuccessDetail` | 成功态扩展 | 明确 `status=SUCCESS`、`stage`、`finished_at_epoch`。 |
| `TaskExecutionRetryingDetail` | 重试态扩展 | 明确 `status=RETRYING`、`stage`、`next_retry_at_epoch` 与最后错误。 |
| `TaskExecutionFailedDetail` | 失败态扩展 | 明确 `status=FAILED`、`stage`、`failed_at_epoch` 与最后错误。 |
| `TaskExecutionRecordUpdatePayload` | 执行记录更新载荷 | 增加 `backend`、`queue_name` 或保证更新时显式保留这两个字段。 |

### 任务清单
- [x] 修改执行记录契约，补齐 `backend`、`queue_name`、强类型 detail kind。
- [x] 增加 header 与 detail 的 `schema_version`、`kind/detail_kind` 一致性校验。
- [x] 修改 ORM，新增 `backend` 字段与索引，保留 `queue_name`、`stage`。
- [x] 新增 Alembic 迁移，兼容历史记录并标注旧记录 backend 可能无法精确反推。
- [x] 修改仓储更新 payload，支持状态更新时保留或写入后端、队列、阶段。
- [x] 修改 `TaskExecutionStore.mark_running()`、`mark_success()`，移除本地 stage 默认值，改为显式传参。
- [x] 修改 local dispatcher，创建与更新记录时写入 `backend=local`、`queue_name=job_kind`、`stage=local_execution`。
- [x] 修改 Funboost dispatcher，发布记录写入 `backend=funboost`、注册队列、`stage=dispatch`。
- [x] 修改 Funboost bootstrapper，消费运行/成功/失败写入 `stage=consume_execution`。
- [x] 修改 `build_envelope()`，从 ORM 构造新契约并保持外层与内层一致。

### 关键代码片段
```python
TaskExecutionRecordDetailUnion = Annotated[
    TaskExecutionPendingDetail
    | TaskExecutionRunningDetail
    | TaskExecutionRetryingDetail
    | TaskExecutionSuccessDetail
    | TaskExecutionFailedDetail,
    Field(discriminator="kind"),
]
```

### 校验
- 新建本地任务记录时 `backend=local`、`queue_name=job_kind`、`stage=dispatch/local_execution`。
- 新建 Funboost 任务记录时 `backend=funboost`、`queue_name=registration.detail.queue_name`。
- Funboost 消费成功后最终记录为 `SUCCESS + consume_execution`。
- `TaskExecutionRecordEnvelope` 对额外字段和外内层不一致能快速失败。

## Phase 3
### 目标
移除或隔离 `FastApiAppAssembler` 的隐式默认 demo/noop 任务绑定，避免生产启动在未传入业务 task binding 时悄悄启用 demo 处理器。

当前阶段完成后，生产任务绑定必须由应用入口、配置或专用 provider 显式提供；测试和开发示例只能通过测试工厂或 demo 工厂显式启用。

### 依赖
- Phase 1 的 backend 强约束。
- 现有 `FastApiAppAssembler._resolve_task_bindings()`、`DefaultTaskBindingFactory`、`TestAppFactory`。
- 现有 `config/modules/task_module/*` 注册配置。

### 模拟用法
```python
app = FastApiAppAssembler()(
    environment=AppEnvironment.PRODUCTION,
    task_bindings=build_production_task_bindings(),
)
```

### 契约
| 英文名 | 中文名 | 中文说明 |
|---|---|---|
| `TaskBindingProvider` | 任务绑定提供器 | 应用层显式提供业务任务绑定列表，不再由 assembler 隐式兜底。 |
| `DemoTaskBindingFactory` | 示例任务绑定工厂 | 仅供测试或开发演示显式调用，不能作为生产默认值。 |
| `TaskBindingStartupPolicy` | 任务绑定启动策略 | 定义生产环境缺少启用任务绑定时的失败规则。 |
| `TaskBindingStartupFault` | 任务绑定启动错误 | 生产或严格模式下缺少任务绑定时的配置错误语义。 |

### 任务清单
