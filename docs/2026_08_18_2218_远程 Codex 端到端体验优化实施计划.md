# 远程 Codex 端到端体验优化实施计划

本计划是可直接交给开发人员执行、回写任务状态和进行验收的版本。当前不执行任何代码修改，也不保存文件。

## 一、真实结论与最终目标

当前问题不是单一的滚动条样式问题，而是以下几个系统问题共同造成的：

- 流式事件在 Agent、FastAPI gateway、browser hub、Pinia reducer 和 Vue 渲染层被重复逐条处理。
- 时间线测量、虚拟列表、ResizeObserver、用户滚动和自动跟随同时竞争 `scrollTop`。
- 当前跟随逻辑不能识别“用户真实上滑”，会把布局测量误判为滚动状态变化。
- Markdown 每个 delta 从头解析，长回复越往后越容易造成主线程卡顿。
- 乐观消息在 HTTP `202` 后才插入，且通过正文匹配服务端消息，连续相同文本可能错配。
- 快照没有 `stream_epoch` 和 `snapshot_cursor`，恢复时存在覆盖新事件的竞态。
- 历史分页不是稳定的向前分页，前端追加位置错误，游标不具备线程和版本绑定。
- 停滞判断依赖浏览器全局 WebSocket 时间，不代表实际 Codex turn 是否仍在运行。
- 审批嵌套滚动区域改变时间线高度，并且当前产品决策没有完整覆盖 App Server 官方审批语义。
- 认证终态、WebSocket 生命周期和 Pinia store 没有统一 generation 控制。
- PWA Service Worker 和 Workbox 缓存会让生产远程页面继续运行旧版本。
- Windows Agent 的生产和开发身份、状态目录、计划任务和锁不隔离，无法安全共存。

最终目标：

- Android Chrome 为第一优先级，桌面端保持完整功能。
- 流式输出贴底时持续跟随，用户真实上滑后稳定暂停。
- 网络切换、后台恢复、弱网重连、认证过期和服务端断档都可以恢复。
- 用户消息立即显示，发送失败可以安全重试，绝不重复执行。
- 历史可以稳定向前分页，动态高度变化不破坏用户阅读位置。
- 任务状态、停滞、审批和中断均由服务端权威状态驱动。
- 不保存会话正文、命令输出或 Diff 到 PostgreSQL、localStorage 或 IndexedDB。
- 主力手机流式期间目标为约 55+ FPS，常用交互反馈 p95 小于 100ms。
- 所有改动遵守 `E:\python_web_fastapi\work\docs\standard` 中的类型、UoW、幂等、测试和日志规范。

## 二、不可改变的架构约束

- Codex App Server 协议冻结为 `0.145.0`，不得根据前端需求自创官方不存在的决策或信任层。
- 稳定数据结构必须使用 Pydantic、dataclass、TypedDict 或 TypeScript interface/union。
- 禁止在新增代码中扩散裸 `dict[str, Any]`、`Record<string, any>` 或无约束 JSON。
- 数据库的 commit、rollback、flush、dispose 只能由现有 UoW 负责。
- 所有可重试写操作必须有明确幂等键、状态转换和冲突语义。
- 所有后台任务、Timer、WebSocket listener、ResizeObserver 和全局事件监听都必须具备显式销毁逻辑。
- 诊断日志默认脱敏，不能上传正文、标题、命令、Diff、access token、cookie 或完整敏感路径。
- 不使用 Service Worker 作为离线发送队列；离线状态下不自动发送消息。
- 不把滚动位置、草稿或会话正文通过 BroadcastChannel 在标签页之间共享。
- 所有新功能必须先在隔离开发环境验证，再进入生产环境。

## 三、公共接口和数据模型变更

### 3.1 消息操作模型

沿用现有发送接口，增加：

```text
client_operation_id: UUID
```

固定语义：

- 前端生成一次 UUID，并在整个操作生命周期内复用。
- HTTP `Idempotency-Key` 必须等于 `client_operation_id`。
- FastAPI、Agent、App Server `TurnStartParams.clientUserMessageId` 均携带该 ID。
- 实时事件、HTTP 响应、错误和恢复快照都必须携带该 ID。
- 相同用户、相同 ID、相同负载：返回原操作结果。
- 相同用户、相同 ID、不同负载：返回 `409 idempotency_conflict`。
- 数据库唯一约束必须至少覆盖 `owner_id + client_operation_id`。
- 操作状态与 turn phase 分离，不能用正文或 WebSocket 到达时间推断状态。

### 3.2 实时事件批次

新增类型化批次：

```text
CodexRealtimeBatch {
  protocol_version: integer
  stream_epoch: string
  first_cursor: string | null
  last_cursor: string | null
  barrier: boolean
  events: CodexRealtimeEvent[]
}
```

固定规则：

- 普通事件最多等待 40ms。
- 达到 64 个事件或 64KiB 时立即 flush。
- Agent 上游批处理最长 25ms 或 16KiB。
- `barrier=true` 只能用于终态、审批打开、审批解决、错误和必要的同步屏障。
- 屏障发送前必须先提交全部前序 delta。
- `events` 必须按 cursor 顺序排列。
- 浏览器一次批次只触发一次 reducer commit 和一次视图刷新。

### 3.3 权威快照

新增：

```text
CodexAuthoritySnapshot {
  stream_epoch: string
  snapshot_cursor: string
  projection_revision: string
  thread: CodexThread
  timeline_items: CodexTimelineItem[]
  turns: CodexTurnRuntime[]
  approvals: CodexApproval[]
}
```

固定规则：

- Agent 通过与事件相同的有序控制通道建立 snapshot barrier。
- FastAPI 必须返回快照生成前捕获的 cursor 水位。
- 浏览器快照请求期间继续接收事件，但暂存到恢复缓冲区。
- 应用快照后只重放 `snapshot_cursor` 之后的事件。
- `stream_epoch` 变化时，旧 cursor 立即失效，必须完整重同步。
- 快照不允许把正文持久化到 PostgreSQL。

### 3.4 历史分页

新增请求参数：

```text
before_cursor: opaque string | null
limit: integer, default 50, maximum 100
```

响应：

```text
CodexHistoryPage {
  items: CodexTimelineItem[]
  before_cursor: string | null
  has_more: boolean
  history_revision: string
}
```

固定规则：

- 游标必须绑定用户、主机、线程、历史版本和边界 item ID。
- 游标必须签名或使用服务端短期句柄，禁止裸 offset。
- 游标失效时返回明确的 `history_cursor_stale`，前端按稳定 item ID 重建窗口。
- Agent 可以在短生命周期内存中缓存上游完整历史，但禁止写入数据库和磁盘。

### 3.5 Turn Runtime

```text
TurnRuntime {
  phase:
    submitted | starting | running | awaiting_approval |
    stalled | completed | failed | interrupted
  last_activity_at: datetime
  stalled_reason: string | null
}
```

内部 lease 额外使用：

```text
lease_generation: integer
lease_expires_at: datetime
```

浏览器不得获得可直接续租的 lease token。

### 3.6 工作区执行偏好

```text
CodexWorkspaceExecutionPreferences {
  model: string | null
  reasoning_effort: string | null
  sandbox_mode: CodexSandboxMode
  approval_policy: CodexApprovalPolicy
  capabilities_revision: string
}
```

服务端返回：

```text
effective_preferences
adjusted_fields
```

固定校验：

- model 和 reasoning 不再支持时回退主机当前默认。
- sandbox 和 approval 不再支持时回退到用户当前可用的最严格选项。
- `danger-full-access` 仍必须经过现有权限 scope 校验。
- 能力版本变化后重新验证，不允许继续使用旧权限配置。

## 四、工作包与详细任务清单

## WP-00：基线、测试夹具与功能开关

### 当前根因

现在没有足够稳定的流式回放、网络故障和动态高度测试夹具，直接修改会难以判断问题来自渲染、事件顺序、连接恢复还是 Agent 行为。

### 最佳实践方案

先建立可重复的本地事件回放和故障注入能力，再实施行为变更。所有新路径由独立开关控制，避免多个高风险变更同时无法定位。

## WP-02：事件批量、Reducer 和 Markdown 增量渲染

### 当前根因

### 最佳实践方案

批量边界必须贯穿 Agent、FastAPI 和浏览器。浏览器每帧只执行一次结构化提交，稳定 Markdown 块不可重复解析。

- [x] Agent 将 flush 上限调整为 25ms 或 16KiB，终态、审批、错误立即 flush。
- [x] FastAPI observer 接收批次并以批接口传递，不在内部重新逐条 publish。
- [x] browser hub 以 `CodexRealtimeBatch` 向每个标签页广播。
- [x] 批次达到 64 事件或 64KiB 时提前发送。
- [x] 浏览器将普通批次放入 queue，以 40ms RAF/Timer 合帧。
- [x] 屏障事件先强制提交 queue，再单独提交屏障。
- [x] Reducer 使用稳定有序 ID 列表和按 item 定点更新。
- [x] 使用 `shallowRef` 或等效结构避免大对象深层响应式代理。
- [x] Getter 不再每次从 `itemsById` 重建完整时间线数组。
- [x] 增加事件 cursor 连续性检查、重复 cursor 检查和 epoch 检查。
- [x] Markdown 将稳定块解析结果缓存为不可变结构。
- [x] 活跃尾部只重新解析当前未完成块。
- [x] 未闭合代码块、列表或引用结构无法安全分块时回退当前消息解析。

## WP-04：历史分页、快照边界、内存预算和上下文页面

### 当前根因

## WP-05：服务端 phase、Agent lease、watchdog 和会话排序

### 当前根因

当前停滞判断使用前端固定 90 秒和全局 socket 活动时间，不能代表某个 turn 的真实运行状态。
