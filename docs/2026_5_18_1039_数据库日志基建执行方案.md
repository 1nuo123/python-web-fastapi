# 数据库日志基建升级执行方案

## 任务目标
最终交付一套符合当前 FastAPI 分层架构与 `docs/standard` 规范的日志基建，覆盖统一日志契约、结构化采集、数据库持久化、主链路接入、测试与文档回归。  
完成判定是：访问日志、异常日志、关键资源状态日志能够按统一契约落库，配置与契约强类型化，数据库不可用时具备可观测降级，源码、测试、文档三者一致。

## 全局约束
- 严格遵循 `docs/standard` 现有规范；若规范文档、设计图谱、历史方案与当前源码冲突，以当前源码事实为准，并明确标注旧文档可能过期。
- 保持现有架构边界：`src/core` 只定义契约，`src/infrastructure` 只落地实现，配置继续通过 `app_settings_loader.py` 收口，资源继续通过 `shared_resource_mount.py` 装配。
- 日志契约统一采用“公共头字段 + 强类型扩展字段”模式；扩展字段必须使用 Pydantic 判别联合，必须包含 `kind`、`schema_version`，并启用 `extra="forbid"`。
- 禁止在日志契约、配置契约、落库扩展体中使用 `dict[str, Any]`、`metadata`、`extra_payload`；外层类型与内层扩展类型必须一致。
- 日志实现必须是结构化日志，禁止业务层继续散落拼接字符串或直接自行写库；正式日志禁止使用 `print`。
- 数据库日志写入必须优先采用缓冲/批量/解耦方式，避免主请求线程同步重度写库；数据库不可用时必须保留 stdout/stderr 保底输出与健康状态告警。
- 首版落地范围限定为 `access`、`exception`、`resource_lifecycle` 三类日志；审计类日志只预留扩展位，不在本轮提前扩 scope。
- 文档、注释、日志消息统一使用中文；注释只补充重要流程、关键分支、状态流转、配置读取与异常处理，不做逐行废话注释。
- 测试必须覆盖配置校验、契约判别联合、数据库写入、降级路径、资源装配、访问日志、异常日志与主链路回归。

## 验收标准
- `logging_runtime` 配置完成强类型收口，非法配置在加载阶段直接失败，且错误可定位到具体字段。
- 日志事件统一为 `header + detail` 结构，`kind`、`schema_version`、请求链路字段、来源字段、级别字段可稳定落库并可查询。
- `access`、`exception`、`resource_lifecycle` 三类日志接入统一基建，能够按 `request_id`、`trace_id`、时间范围、级别、类型追溯。
- 数据库日志写入具备批量 flush、失败降级、健康状态暴露能力，日志失败不会改变既有 HTTP 语义，也不会反向打爆主链路。
- Alembic 迁移、ORM 模型、资源装配、运行时配置、测试断言与文档说明保持一致。
- 受影响测试与全量回归通过，文档已回写到与最终源码一致的状态。

## Phase 1
### 目标
先收口日志契约与日志运行时配置，解决当前“只有普通 `logging.Logger` 文本输出，没有统一事件模型、没有数据库 sink 契约、没有强类型配置”的直接问题。  
本阶段完成后的中间结果是：日志事件、日志配置、日志类型边界稳定，后续实现可以围绕清晰契约编码，而不是边写边补字段。

### 依赖
依赖当前 `app_settings_loader.py`、`shared_resource_mount.py`、`app_logger_factory.py`、`access_log_middleware.py`、`fastapi_exception_presenter.py` 的真实实现。  
若历史设计文档与现状冲突，以当前源码为准，并在文档回归时标注历史描述可能过期。

### 模拟用法
```toml
[runtime.logging]
enabled = true
level = "INFO"
sink = "database"
buffer_max_items = 1000

[runtime.logging.sink_detail]
kind = "database"
schema_version = "1.0"
table_name = "app_log_record"
flush_interval_seconds = 2
max_batch_size = 100
fallback_to_stdout = true
```

### 契约
| 英文名 | 中文名 | 中文说明 |
|---|---|---|
| LoggingRuntimeSettings | 日志运行时配置 | 日志公共配置，承载 `enabled`、`level`、`sink`、缓冲策略与 `sink_detail` 扩展字段，并校验外层 `sink` 与内层 `kind` 一致。 |
| DatabaseLogSinkDetail | 数据库日志落库扩展配置 | 数据库日志独有配置，包含 `kind`、`schema_version`、表名、批量大小、刷新间隔与降级开关，启用 `extra="forbid"`。 |
| LogEventEnvelope | 日志事件信封 | 统一日志输入模型，固定为 `header + detail` 结构，并校验外层与内层的 `kind`、`schema_version` 一致。 |
| LogEventHeader | 日志公共头字段 | 记录 `event_id`、`occurred_at`、`level`、`kind`、`schema_version`、`request_id`、`trace_id`、`source`、`message` 等公共字段。 |
| LogDetailUnion | 日志扩展体判别联合 | 通过 Pydantic 判别联合承载 `AccessLogDetail`、`ExceptionLogDetail`、`ResourceLifecycleLogDetail`。 |
| AccessLogDetail | 访问日志扩展体 | 描述请求方法、路径、状态码、耗时、客户端地址等访问维度字段。 |
| ExceptionLogDetail | 异常日志扩展体 | 描述异常类型、异常码、处理结果、traceback 摘要等异常维度字段。 |
| ResourceLifecycleLogDetail | 资源生命周期日志扩展体 | 描述资源名称、动作、状态、失败原因等资源状态字段。 |

### 任务清单
- [x] 新增 `src/core/logging_contract`，补齐日志公共头、扩展体、判别联合、枚举与校验规则。
- [x] 新增 `config/runtime/logging_runtime`，并在 `app_settings_loader.py` 中接入强类型加载与早失败校验。
- [x] 明确首版日志类型范围为 `access`、`exception`、`resource_lifecycle`，保留审计扩展位但不提前实现。
- [x] 校验外层 `sink/kind/schema_version` 与内层扩展体一致，禁止 `dict[str, Any]`、`metadata`、`extra_payload`。
- [x] 为日志公共字段、默认值、取值语义、错误语义补齐中文文档，避免继续依赖散落的隐式约定。

### 关键代码片段
```python
LogDetailUnion = Annotated[
    AccessLogDetail | ExceptionLogDetail | ResourceLifecycleLogDetail,
    Field(discriminator="kind"),
]


class LogEventEnvelope(BaseModel):
    header: LogEventHeader
    detail: LogDetailUnion
```

### 校验
- 合法 `logging_runtime` 配置能够通过加载，非法 `sink/detail` 组合在加载阶段直接失败。
- `LogEventEnvelope` 能稳定校验 `header + detail`，未知 `kind`、多余字段、版本不一致都会失败。
- 契约输出 JSON 后仍能稳定反序列化，且公共头与扩展体边界清晰。

## Phase 2
### 目标
落地数据库日志持久化基建与资源装配，解决当前“没有日志表、没有统一写入器、没有缓冲 flush、没有资源生命周期管理”的直接问题。  
本阶段完成后的中间结果是：应用能够通过统一日志处理器将结构化日志批量写入数据库，并在失败时执行明确降级。

### 依赖
依赖 Phase 1 的日志配置契约与日志事件契约。  
依赖现有 SQLAlchemy、Alembic、`sqlalchemy_session_factory.py`、`sqlalchemy_metadata_registry.py` 与 `shared_resource_mount.py` 的真实装配方式。

### 契约
| 英文名 | 中文名 | 中文说明 |
|---|---|---|
| AppLogRecordOrmModel | 应用日志 ORM 模型 | 对应数据库日志表，固化公共查询列与扩展体存储列，用于日志持久化与检索。 |
| LogWriteRequest | 日志写入请求 | 承载待落库的 `LogEventEnvelope` 集合、flush 原因与批量边界信息。 |
| LogWriteResult | 日志写入结果 | 返回写入条数、失败条数、降级状态与异常摘要，用于健康检查与回归诊断。 |
| DatabaseLogWriter | 数据库日志写入器 | 负责批量入库、事务边界、异常收口与降级信号生成。 |
| LogBufferDispatcher | 日志缓冲派发器 | 负责接收日志事件、定时或定量 flush，并避免主链路同步重度写库。 |

### 任务清单
- [x] 新增日志表 ORM、仓储实现与 Alembic 迁移，落地 `app_log_record` 持久化结构。
- [x] 新增结构化日志处理器、事件构造器、缓冲派发器、数据库日志写入器。
- [x] 在 `shared_resource_mount.py` 中装配日志 writer、dispatcher、logger，并补齐启动、关闭、flush 生命周期。
- [x] 为数据库不可用、队列满、批量写入失败定义统一降级策略：保底 stdout/stderr、记录健康状态、不中断主链路。
- [x] 为日志表补齐必要索引、保留期与清理策略接口，首版至少支持按时间、级别、类型、链路字段查询。

### 关键代码片段
```python
class DatabaseLogWriter:
    def write_batch(self, request: LogWriteRequest) -> LogWriteResult: ...


class LogBufferDispatcher:
    def emit(self, event: LogEventEnvelope) -> None: ...

    def flush(self, reason: str) -> LogWriteResult: ...
```

### 校验
- 迁移后日志表、索引与 ORM 模型一致，能够完成最小一批日志的插入与查询。
- 数据库不可用或 flush 失败时，应用主请求链路不因日志写入失败而改变语义。
- 资源关闭时能够触发最后一次 flush，并释放 dispatcher、session 等相关资源。

## Phase 3
### 目标
把访问日志、异常日志、资源生命周期日志接入统一基建，解决当前“主链路日志分散在 middleware、exception presenter、资源装配点，字段不统一且无法稳定追溯”的直接问题。  
本阶段完成后的中间结果是：主链路关键日志全部统一建模、统一装配、统一落库，查询时能够按请求链路完整回放。

### 依赖
依赖 Phase 1 的日志契约与 Phase 2 的数据库日志基建。  
依赖当前 `request_scope_middleware.py`、`access_log_middleware.py`、`fastapi_exception_presenter.py`、`shared_resource_mount.py` 的真实链路。

### 契约
| 英文名 | 中文名 | 中文说明 |
|---|---|---|
| RequestLogContext | 请求日志上下文 | 封装 `request_id`、`trace_id`、`user_id`、`client_ip`、`user_agent` 等链路字段。 |
| AccessLogDetail | 访问日志扩展体 | 记录请求方法、请求路径、状态码、耗时、路由名称与客户端来源。 |
| ExceptionLogDetail | 异常日志扩展体 | 记录异常类型、异常级别、错误码、处理结果、traceback 摘要与映射后的响应状态。 |
| ResourceLifecycleLogDetail | 资源生命周期日志扩展体 | 记录资源名称、生命周期动作、状态、耗时与失败原因，用于启动/关闭与资源故障追踪。 |

event = log_event_builder.build_access_event(
