## 修复清单

### 1. P0 最后一个管理员可被其他管理员停用或剥权

- 定位：`src/infrastructure/persistence/repository_impl/admin_identity_repository_impl.py:464`、`:501`、`:521`
- 根因：`update_user()`、`replace_user_roles()`、`disable_user()` 只拦截 self-lock，没有校验变更后系统里仍至少存在一个 active `admin` 且具备 `auth:manage` 能力的管理员。
- 触发条件：系统只有一个真正可管理后台的管理员，另一个有操作权限的主体停用它、或移除它的管理角色。
- 影响：后台身份管理会进入不可恢复的 403/锁死状态，只能靠外部写库或临时入口恢复。
- 修复方案：在三条写路径里引入全局剩余管理员能力校验；对涉及 admin 能力变化的操作加行级锁或事务内一致性查询。建议抽成 `AdminAccessInvariant`，统一判断“至少一个 active admin + auth:manage”。
- 验证：最后一个管理员被停用、禁用、剥离 admin/auth:manage 时返回 409；存在第二个有效管理员时允许操作。

### 2. P0 `security:manage` 未进入受保护 scope 集合

- 定位：`src/api/admin_route_authorization.py:77`、`src/api/endpoint_security_protection/route_security_protection.py:128`、`src/infrastructure/persistence/repository_impl/admin_identity_repository_impl.py:193`
- 根因：受保护 scope 只从 `ADMIN_ROUTE_AUTHORIZATION_REQUIREMENTS` 汇总；安全防护路由在路由内部临时创建 `security:manage` requirement，没有进入中心化授权注册表。
- 触发条件：拥有 `auth:manage` 的管理员通过 scope 管理接口把 `security:manage` 置为 disabled。
- 影响：`/security/ip-blocks` 等安全管理入口会被管理面自己关闭，安全控制面失去恢复闭环。
- 修复方案：把 `SECURITY_PROTECTION_AUTHORIZATION_REQUIREMENT` 提升到 `admin_route_authorization.py`，或更彻底地建立全站受保护 scope registry，所有非 PUBLIC 管理路由都从同一 registry 派生 protected scopes。
- 验证：禁用 `security:manage` 返回 409；安全防护路由的授权 requirement 与 protected scope registry parity 测试通过。

### 3. P1 `worker_enabled` 被实现成禁止派发，破坏 producer-only 部署

- 定位：`src/infrastructure/task/local_task_dispatcher.py:86`、`src/infrastructure/task/funboost_task_dispatcher.py:74`、`test/unit_test/test_local_task_dispatcher_unit.py:175`、`test/unit_test/test_funboost_task_dispatcher_unit.py:177`
- 根因：`worker_enabled=false` 在 dispatcher 入口直接拒绝任务提交，而不是仅表示当前节点不启动 consumer/worker；现有测试也固化了这条语义。
- 触发条件：API 节点只负责派发任务，消费者在其他节点运行，生产者节点配置 `runtime.task.worker_enabled=false`。
- 影响：RabbitMQ/Funboost 的 producer/consumer 分离部署无法使用，API 节点不能提交任务。
- 修复方案：把 `worker_enabled` 收敛为“当前节点是否消费/执行任务”。Funboost 派发应继续 publish；consumer 启停受 `worker_enabled` 控制。本地后端若必须同进程执行，单独引入 `dispatch_enabled` 或 `inline_execute_enabled`，不要复用 worker 开关。
- 验证：`worker_enabled=false` 时 API/admin 仍可 dispatch，Funboost 消息进入队列；当前节点不启动 consumer。本地后端的 inline 行为由新开关覆盖。

### 4. P1 启动时强制所有启用任务绑定本节点 handler

- 定位：`src/infrastructure/task/task_runtime_manager.py:92`、`src/infrastructure/task/task_registration_registry.py:253`
- 根因：`TaskRuntimeManager.build_runtime()` 无条件调用 `assert_all_enabled_tasks_bound()`，把“消费节点必须有 handler”的校验推广到所有节点。
- 触发条件：启用了任务注册，但当前进程只做 producer，不装配对应 handler。
- 影响：producer-only 节点启动或热更新失败，任务部署拓扑被迫退回单体同进程模型。
- 修复方案：把 handler 完整性校验下沉到 `worker_enabled=true` 且当前节点实际会消费/本地执行的路径；producer-only 只校验注册合法、后端匹配和消息总线可用。
- 验证：无 handler + `worker_enabled=false` 可启动并可派发；无 handler + `worker_enabled=true` 仍快速失败。

### 5. P1 RabbitMQ 未路由消息可能被当成发布成功

- 定位：`src/infrastructure/task/rabbitmq_message_bus.py:28`、`:62`
- 根因：`RabbitMqMessageBus.publish()` 使用 `mandatory=False`，且只处理 publisher confirm 返回 `False` 的情况；exchange 存在但 routing key 无队列绑定时，broker 可丢弃消息而调用侧仍认为成功。
- 触发条件：RabbitMQ backend 启用，队列未声明、routing/binding 漂移或 job_kind 配错。
- 影响：任务执行记录停留在 pending/dispatch，实际消息已丢失，排障会误判为 worker 问题。
- 修复方案：关键任务发布开启 `mandatory=True` 并处理 returned message；或发布前声明并校验目标 binding/queue 可达。保留静默丢弃只应限于明确的非关键事件通道。
- 验证：exchange 存在但无匹配 binding 时，dispatch 失败并记录发布失败，不返回成功。

### 6. P1 本地任务后端配外部 message bus 会产生重复执行风险

- 定位：`src/infrastructure/task/local_task_dispatcher.py:117`、`:122`、`src/infrastructure/resource_mount/runtime_resource_bootstrapper.py:506`
- 根因：本地 dispatcher 在 reserve 后先 `_execute_handler()`，随后仍发布到 `message_bus`；资源装配又会按 `runtime.message.backend` 创建 RabbitMQ bus。
- 触发条件：配置成 `runtime.task.backend=local` 且 `runtime.message.backend=rabbitmq`。
- 影响：同一任务可能本地执行一次，又被外部消费者处理一次；有副作用任务会出现重复写入、重复通知或状态漂移。
- 修复方案：配置校验直接禁止 `task=local + message=rabbitmq`，或把“本地执行任务”和“发布事件/观测消息”拆成两条明确链路。若要支持混合模式，必须有幂等与消费归属契约。
- 验证：该组合启动即拒绝，或新增测试证明不会二次执行。

### 7. P1 IP 封禁命中被记录成 rate limit 事件

- 定位：`src/infrastructure/security/security_protection_guard.py:87`、`src/infrastructure/security/security_event_builder.py:224`
- 根因：`ip_block_guard.evaluate()` 命中 active block 后，返回事件仍调用 `build_rate_limit_event()`，没有使用已有的 `build_ip_block_event()`。
- 触发条件：请求来自已封禁 IP。
- 影响：安全事件类型、统计和后台检索都会把“封禁命中”误归类为“限流命中”，安全运营判断失真。
- 修复方案：active IP block 分支改用 `build_ip_block_event()`，并补齐事件 payload 中封禁原因、ip_digest、blocked 状态与 retry_after。
- 验证：已封禁 IP 请求返回 429 时，安全事件类型为 ip_block；限流超限后首次封禁仍保留 rate_limit 事件语义。

### 8. P1 IP 封禁缓存命中的 `Retry-After` 不准确

- 定位：`src/infrastructure/security/ip_block_guard.py:90`、`:94`、`:206`
- 根因：DB 命中时缓存 TTL 会取 `min(cache_ttl_seconds, remaining_seconds)`，但缓存值只保存 `"active"`，下一次缓存命中直接返回配置的 `cache_ttl_seconds`，丢失真实剩余时间。
- 触发条件：封禁剩余时间小于配置 TTL，且后续请求命中缓存。
- 影响：客户端收到的 `Retry-After` 可能大于真实解封时间，封禁体验和自动重试策略不可信。
- 修复方案：缓存值保存 blocked_until_epoch 或 remaining_seconds；命中缓存时根据当前时间重新计算 retry_after。也可以把 Redis TTL 读取能力纳入 cache contract。
- 验证：封禁剩余 5 秒、缓存 TTL 60 秒时，连续命中返回的 retry_after 不超过真实剩余时间。

### 9. P2 默认 task binding 过滤分支在主入口失活

- 定位：`src/api/asgi_entry.py:42`、`src/infrastructure/fastapi_app_assembler.py:359`、`:369`
- 根因：ASGI 主入口在 `task_bindings is None` 时先调用 provider 生成列表，再传给 assembler；assembler 只有在收到 `None` 时才过滤未声明 binding，因此真实主入口永远走不到默认过滤分支。
- 触发条件：`ApplicationTaskBindingProvider` 返回某个配置未声明的 binding。
- 影响：要么未声明任务在注册阶段 fail-fast，要么注释承诺的“过滤默认 binding”不生效，入口心智不统一。
- 修复方案：推荐按严格配置模型处理：删除过滤分支和误导性注释，所有未声明 binding 都 fail-fast；
- 验证：provider 返回 declared + stale binding 时，行为与选定模型一致；显式传入 stale binding 的测试单独覆盖。

### 10. P2 日志 `flush_interval_seconds` 不是后台定时刷盘

- 定位：`src/infrastructure/logging/log_buffer_dispatcher.py:38`、`:84`、`test/unit_test/test_log_writer_unit.py:125`
- 根因：interval 只在下一条 `emit()` 到来时判断，没有后台 timer；测试已把“下一条日志触发刷盘”固化为当前语义。
- 触发条件：低流量服务写入一条日志后长时间没有下一条日志。
- 影响：数据库日志可见性延迟不受配置秒数约束，只能等下一条日志或 shutdown flush。
- 修复方案：若配置承诺近实时刷盘，则引入后台 flush loop，并纳入资源生命周期关闭；
- 验证：写入单条日志后不再 emit，超过 interval 后仍能落库；或契约测试明确当前懒刷盘语义。

### 11. P2 admin audit 查询契约暴露未实现的业务审计枚举

- 定位：`src/application/ports/admin_audit_query_port.py:29`、`:30`、`src/infrastructure/persistence/repository_impl/log_record_repository_impl.py:231`、`src/infrastructure/shared_resource_mount.py:284`
- 根因：查询 port 暴露 `business_object_changed`、`business_action_triggered`，但当前实现只把 admin identity security event 映射成固定操作集合。
- 触发条件：调用方按契约查询业务对象变化或业务动作审计。
- 影响：API 契约看起来支持业务审计，实际数据源和映射不闭环，后续调用方会误接入。
- 修复方案：长期重构成统一 audit event registry，由业务模块注册 event kind、operation、object_type，再由查询仓储按 registry 构建过滤条件。
- 验证：所有公开 operation kind 都有仓储实现和接口测试；不存在“枚举可选但永远无数据”的查询路径。

### 12. P2 分布式锁 `failure_mode` 是误导性能力

- 定位：`src/core/concurrency_contract/distributed_lock_contract.py:34`、`:71`、`src/infrastructure/concurrency/distributed_lock_provider.py:40`、`:179`
- 根因：契约和配置暴露 `failure_mode`，但枚举只有 `FAIL_CLOSED`，provider 没有 fail-open/fail-soft 分支，只把该值放进错误 detail。
- 触发条件：运维或后续开发试图依赖 `distributed_lock_runtime.failure_mode` 调整故障策略。
- 影响：配置项制造不存在的能力，与 cache failure mode 的真实分支形成心智不一致。
- 修复方案：当前更优是收缩契约：删除运行时可配置的 `failure_mode`，保留固定 fail-closed 文档；
- 验证：旧配置被迁移或拒绝；契约测试证明锁故障策略只有一个明确行为。

## 建议执行顺序

1. 先修 P0：管理员存活不变量、`security:manage` 受保护 scope。
2. 再修任务运行时 P1：`worker_enabled` 语义、handler 绑定校验、RabbitMQ mandatory、local+rabbitmq 组合禁用。
