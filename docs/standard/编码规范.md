请使用 Python 3.11+ 生成高质量工程化代码，并严格遵守以下规范：

【总体目标】
- 规范的核心定位是一个可快速执行的函数与代码设计决策体系，而不是知识说明书
- 在面对“要写一个函数”时，必须依次判断：
  - 这个函数该不该存在
  - 它是什么角色
  - 它该公开还是私有
  - 它该不该拆
  - 它是不是编排函数
  - 它的输入输出怎么定
  - 它有没有副作用风险
  - 它未来会不会演化成坏抽象
  - 它的名字该怎么取
- 生成代码时，优先满足以下目标：
  1. 类型安全
  2. 数据结构清晰
  3. 可维护性
  4. 可测试性
  5. 工程可扩展性

【类型标注】
- 必须使用现代类型标注语法：list[T]、dict[K, V]、X | Y、T | None
- 禁止使用 typing.List、typing.Dict、typing.Optional、typing.Union 等旧式写法
- 尽量避免 Any；如使用 Any，必须有明确理由
- 公共函数、类属性、返回值必须完整标注类型

【数据建模】
- 禁止将稳定结构的数据建模为裸 dict
- 外部输入、配置、API 请求/响应、反序列化数据：优先使用 Pydantic 模型
- 内部轻量数据对象：优先使用 dataclass
- 必须保持 dict 形态的数据协议：使用 TypedDict
- 除非确有必要，不要使用 dict[str, Any]、list[dict[str, Any]]

【函数设计总流程】
- 写函数时按顺序执行以下判断：
  - 先判断：是否值得成为独立函数
  - 再判断：函数角色
  - 再判断：是否公共暴露
  - 再判断：是否需要拆分
  - 再判断：是否需要编排层
  - 再判断：输入输出边界
  - 再判断：副作用与错误处理
  - 最后判断：命名

【函数存在性】
- 只有在以下条件成立时才应创建独立函数：
  - 逻辑有独立语义
  - 具有明确输入输出
  - 能被一个稳定名字概括
  - 拆出来后能让主流程更清晰
  - 不是单纯为了减少代码行数
- 若以上条件不成立，则不要创建函数，保留在原地
- 禁止为了“看起来更短”而机械拆函数

【函数角色】
- 每个函数必须优先归类到一个主角色；若无法归类，说明抽象未想清楚，应停止生成
- 允许的主角色：
  - 基础动作函数：执行单一、稳定动作，如 `create` / `get` / `update` / `delete` / `validate` / `parse` / `build`
  - 过程函数：表达流程阶段，如 `pre_` / `post_` / `prepare_` / `finalize_`
  - 组合函数：封装多个基础动作提升便利性，如 `get_or_create` / `init_and_validate`
  - 编排函数：组织多个步骤调用，自身少做细节逻辑，如 `orchestrate` / `run` / `process` / `execute`
  - 分发器函数：根据条件选择处理路径，如 `dispatch` / `route` / `select` / `resolve`
  - 入口函数：对外统一接入点，如 `handle` / `process` / `execute` / `serve`
  - 转换函数：结构化转换，如 `to_` / `from_` / `convert_` / `serialize_` / `deserialize_`
  - 校验函数：检查约束或合法性，如 `validate` / `check` / `verify` / `assert` / `can`
  - 清理函数：清理状态、资源或中间物，如 `clean` / `cleanup` / `release` / `clear` / `dispose`
  - 持久化函数：落地、读取、装载状态，如 `save` / `load` / `read` / `write` / `store` / `persist`

【可见性与复用边界】
- 若函数仅服务于当前流程、强依赖上下文、阶段性强，则应为私有函数
- 若函数语义独立、输入输出稳定、存在真实复用价值，则可为公共函数
- 若阶段函数中包含可复用逻辑，应提炼为公共基础函数，阶段函数自身保留私有
- 默认不要因为“未来可能复用”而过早公开
- 若只有看起来相似、未来演化不明、抽象后名称会变差，应先复制、后观察
- 仅在已有真实第二个调用场景且共性稳定明确时，才进行抽象复用
- 可以同时保留原子函数与便捷函数：
  - 需要一步完成时使用便捷函数
  - 需要精细控制时使用原子函数

【拆分与编排】
- 函数必须职责单一，避免一个函数同时做解析、校验、转换、业务处理、持久化、日志等多件事
- 是否拆分函数，应基于语义清晰，而不是仅为了变短
- 当函数同时承担多个清晰可命名步骤，并且拆分后主函数更像业务剧本时，应拆分
- 若子函数没有独立语义、上下文过于紧密、拆分后导致频繁跳转，则不应拆分
- 若函数主要职责是组织多个步骤执行顺序，则应定义为编排函数
- 编排函数自身不应承载大量实现细节
- 基础动作函数不得逐渐承担编排职责
- 编排函数也不得下沉承担所有具体细节，避免演化为上帝函数

【阶段函数规范】
- `pre_` / `post_` / `prepare_` / `finalize_` 仅用于明确表达主流程阶段的内部过程函数
- 阶段函数默认应为私有
- 不得用 `pre_` / `post_` 替代真实具体动作词
- 不得将阶段函数直接作为公共 API 暴露
- 若阶段中的某部分具有独立复用价值，应抽出公共基础动作函数，不要直接公开阶段函数

【输入边界】
- 参数必须保持最小、清晰、显式，只传函数真正依赖的输入
- 禁止传入过大的对象只为取少数字段
- 禁止将业务参数、配置参数、技术依赖混杂在同一层参数中
- 参数过多时使用对象封装，不要堆积布尔参数和大量位置参数
- 尽量避免多个布尔参数、过多 `mode` / `type` / `flag` / `options`
- 仅在共享流程状态明确时使用 `context` 或参数对象：
  - 适用于编排流程共享状态、跨步骤传递 trace/request/auth/runtime 信息、逐步 enrich 同一上下文
  - 不适用于基础动作函数、纯工具函数、仅为掩盖参数过多的情况
- 输入若可能被函数修改，必须显式设计，避免隐式修改传入对象
- 在必要时先做归一化，再进入后续处理

【输出边界】
- 返回值必须语义稳定
- 输出必须与函数职责匹配，避免返回过弱、过重或泄漏内部实现细节
- 只返回 `bool`、`None` 时，必须确保其语义足够明确；否则应改为更明确的结果表达
- 当返回的是“语义结果”而不是“单一值”时，应使用结果对象而不是裸值
- 以下场景适合使用结果对象：
  - 需要表达 success/failure
  - 需要附带错误原因、警告、元信息
  - 存在部分成功语义
  - 返回值未来会扩展
  - 返回的本质是一个结果语义，而非单值
- 以下场景可直接返回裸值：
  - 纯简单函数
  - 返回值极明确
  - 内部辅助函数，额外包装收益不大

【副作用控制】
- 将纯逻辑与副作用分离
- 尽量减少共享可变状态
- 查询函数尽量无副作用，禁止查询函数偷偷写状态
- 校验函数不得偷偷修复数据
- 命令函数若存在副作用，必须在语义上显式承认
- 关键副作用应尽量放在外层编排函数中
- 若核心逻辑本质上是决策，而副作用只是提交，应拆为“决策/准备 + 提交”
- 在以下场景优先考虑将副作用推迟到更外层：
  - 需要 dry-run
  - 需要事务控制
  - 需要批处理、延迟提交、异步提交
  - 当前副作用让函数难测、难复用、难回滚
- 若逻辑与副作用天然不可分，可以保持一体，但边界必须清晰
- 禁止在保存函数中顺手发消息、清缓存、建索引等未显式声明的混合副作用

【异常处理】
- 禁止无意义的 `except Exception`
- 禁止吞异常
- 仅捕获可处理的具体异常
- 需要时定义明确的业务异常类型，并保持异常语义清晰
- 错误处理策略必须区分以下情况：
  - 意外错误、契约破坏、系统错误：抛异常
  - 正常业务失败、调用方需要显式分支处理：返回错误对象或结果对象
- 若存在部分成功 / 部分失败语义，应避免仅靠异常或简单布尔值表达

【命名】
- 命名必须清晰表达业务意图，避免模糊命名
- 名字应表达“做什么”，而不是“怎么实现”
- 优先使用具体动作词，避免低信息量动词作为主动作
- 禁止或避免使用模糊命名：
  - `do`
  - `manage`
  - `helper`
  - `common`
  - `misc`
- `handle` 仅用于入口函数
- `process` / `execute` 仅用于流程或入口函数，不能给普通 CRUD 或基础动作乱用
- `dispatch` / `route` / `select` / `resolve` 仅用于分发器函数
- `pre_` / `post_` 仅用于阶段函数
- 允许的标准动作词：
  - 创建：`create` / `build` / `make` / `init`
  - 获取：`get` / `find` / `fetch` / `read` / `load` / `list`
  - 更新：`update` / `set` / `patch` / `save` / `write` / `store` / `persist`
  - 删除：`delete` / `remove` / `clear` / `destroy` / `dispose`
  - 校验：`validate` / `check` / `verify` / `assert` / `can`
  - 转换：`convert` / `to` / `from` / `parse` / `format` / `serialize` / `deserialize` / `encode` / `decode` / `normalize`
  - 比较：`compare` / `match` / `matches` / `diff`
  - 入口：`handle` / `process` / `execute` / `serve`
  - 编排：`orchestrate` / `run` / `execute` / `process`
  - 分发：`dispatch` / `route` / `select` / `resolve`
  - 清理：`clean` / `cleanup` / `release` / `close` / `flush`
  - 并发：`lock` / `unlock` / `wait_for` / `signal` / `notify` / `retry` / `cancel`
- 允许的组合命名仅限：
  - `A_and_B`
  - `A_or_B`
  - `A_if_xxx`
- 组合命名仅在稳定高频组合下使用，如：
  - `get_or_create`
  - `init_and_validate`
  - `create_if_absent`
- 若组合链条很长、条件很多、流程复杂，应改为编排函数，不要堆叠命名
- 不建议将以下语义写入函数名：
  - `safe`
  - `pure`
  - `impure`
  - `do`
  - `undo`
- 幂等性、纯度、生命周期、并发级别、风险等级等应进入文档、元数据或规范属性，而不是函数名
- `unsafe_` 可作为强语义前缀例外保留

【结构演进】
- 无状态、单动作、边界清晰时，优先使用函数
- 当复杂性来自以下因素时，应考虑升级为对象或类：
  - 存在内部状态
  - 存在多种可替换策略
  - 参数越来越多
  - 需要生命周期管理
  - 有一组总是一起出现的相关函数
  - 已明显表现出角色感
- 当复杂性来自多种实现算法、运行时策略选择、不断膨胀的 `if mode/type/...` 分支时，应升级为策略对象
- 当复杂性来自稳定多阶段流程、阶段接口稳定、需要插拔/配置/监控/重试/阶段复用时，应升级为 pipeline / workflow
- 简单顺序调用仍以编排函数为主，不必过早引入 workflow
- 在以下场景应考虑拆为两阶段：
  - 不可逆副作用、需要 dry-run / 预览 / 二次确认 / 批量合并提交：拆为 `prepare` / `plan` + `commit` / `apply`
  - 调用方有时只需要知道能不能做、校验逻辑值得复用：拆为 `can_` / `validate_` + `execute` / `create` / `update`
  - 解析错误与业务校验错误需要区分，或存在“可解析但不合法”的中间态：拆为 `parse_` + `validate_`
  - 调用方有时只想构造对象而不想立即持久化：拆为 `build_` + `save_`
  - 选择策略与执行策略复杂度都在上升：拆为 `resolve` / `select` + `execute`

【日志】
- 禁止使用 `print` 作为正式日志手段
- 记录错误时保留必要上下文；需要时记录 traceback
- 使用中文进行记录
- 日志不应承担业务语义本身，业务结果仍应通过返回值或异常清晰表达

【结构与可维护性】
- 保持接口层、业务层、数据访问层、模型层分离
- 不要生成臃肿的 `utils.py` / `common.py` / `helpers.py`
- 代码应便于后续重构与测试
- 注释、文档等应当使用中文
- 优先选择简单、直接、清晰的实现
- 避免炫技、过度抽象、无意义封装
- 生成的代码应默认可用于中大型项目，而不是一次性脚本风格

【测试友好】
- 尽量减少共享可变状态
- 将纯逻辑与副作用分离
- 让代码天然易于 pytest 测试
- 若函数难测，应优先检查是否混入了不必要副作用、隐藏依赖、过大的输入边界或不清晰的职责边界

【并发、幂等、资源与事务】
- 对可能被重试、重放、重复消费、网络重发的操作，必须考虑幂等性
- 对创建、扣费、发消息、状态流转等具有重复副作用风险的函数，必须显式考虑幂等设计
- 纯读取、纯计算一般无需额外幂等设计
- 对长时间运行、用户可中止、多阶段流程的操作，应考虑取消语义及取消后的补偿/清理
- 对文件、连接、锁、事务、会话等资源，必须设计清晰的资源边界与释放责任
- 资源显著时，应显式使用 `open/close`、`acquire/release` 或上下文管理
- 多个写操作需要一致成功/失败时，必须明确事务边界
- UoW 是持久化链路唯一事务边界，只有 UoW 可以执行 `commit()`、`rollback()`、`flush()` 与 `dispose()`
- Repository 只负责读写和抛出无法处理的数据库异常，禁止在仓储实现中调用 `commit()`、`rollback()` 或释放外层会话
- Repository 可以使用 `flush()` 暴露数据库约束错误，但不得吞异常，也不得通过回滚外层事务恢复状态
- 若允许最终一致性，应设计补偿、outbox 或异步机制
- 当调用方经常循环调用单条函数且存在明显批量优化空间时，应提供批处理接口

【缓存策略】
- 缓存契约必须采用“公共头字段 + 强类型扩展字段”模式，扩展字段使用 Pydantic 判别联合并启用 `extra="forbid"`
- 缓存命名空间必须收敛到 `CacheNamespace` 等封闭枚举；稳定公共取值不得散落为业务代码中的魔法字符串
- 缓存 key 统一格式为 `key_prefix:namespace:segment...`，前缀与片段均不能为空，片段不得包含 `:` 分隔符
- 调用方不得把令牌、密码、密钥等敏感原文直接作为缓存 key 片段；需要参与键构造时必须先摘要化
- TTL 解析顺序固定为：请求显式 TTL > 命名空间策略默认 TTL > `runtime.cache.default_ttl_seconds`，所有 TTL 必须大于 0
- Redis 不可用策略必须按命名空间分类：认证、鉴权、限流类缓存使用 fail-closed，普通查询缓存可使用 fail-open
- fail-closed 必须继续抛出 `system.cache.unavailable`，不得放行认证、鉴权或限流关键流程
- fail-open 仅读取时按未命中处理，写入与删除可记录中文告警后跳过；告警只记录命名空间与键摘要，不输出敏感原文

【质量警报】
- 出现以下信号时，必须立即回到“角色判定”和“职责边界”重新审视设计：
  - 命名警报：
    - `do_` / `manage_` / `helper_` / `common_` / `misc_`
    - `handle_` 但其实不是入口
    - `process_` 但其实只是 CRUD
  - 参数警报：
    - 参数过多
    - 多个 bool 参数
    - 大量可选参数
    - `mode` / `type` / `flag` / `options` 过多
    - 技术依赖与业务数据混杂
  - 结构警报：
    - 基础动作函数开始承担编排
    - 编排函数开始承担所有实现细节
    - 阶段函数被当作公共 API 使用
    - 分发器函数开始做大量实际处理
    - 入口函数下沉到领域细节
  - 复用警报：
    - 因“未来可能复用”而过早公开
    - 公共函数被越来越多场景参数污染
    - 抽象后名字越来越模糊
    - 相似代码被错误强行统一
  - 副作用警报：
    - 查询函数偷偷写状态
    - 校验函数偷偷修复数据
    - 保存函数顺手执行多个额外副作用
    - 函数行为需要靠注释才知道

【给 LLM / 自动化工具的标准执行协议】
- Step A：函数存在性判断
  - 判断目标逻辑是否具有独立语义
  - 判断是否具有明确输入输出
  - 判断是否可用稳定名称概括
  - 若以上任一为否，则不建议创建独立函数
- Step B：函数角色判定
  - 将函数判定为以下一种主角色：`primitive`、`process`、`composite`、`orchestrator`、`dispatcher`、`entry`、`transformer`、`validator`、`cleaner`、`persistence`
  - 若无法归类，则说明抽象不稳定，不应继续生成
- Step C：可见性判定
  - 若函数仅服务特定主流程、依赖隐式上下文、阶段性强，则设为 `private/internal`
  - 若函数语义独立、输入输出稳定、存在真实复用，则设为 `public/shared`
  - 若阶段函数中含公共逻辑，则生成“公共基础函数 + 私有阶段包装”
- Step D：拆分判定
  - 若函数同时承担多个清晰可命名步骤，且拆分后主函数更清晰，则拆分，否则保持一体
- Step E：编排判定
  - 若函数主要职责是组织多个步骤执行顺序，则判定为 `orchestrator`
  - 编排函数自身不应承载大量具体业务细节
- Step F：输入边界判定
  - 仅保留真正依赖的参数，避免大对象滥传，避免多 bool 参数
  - 避免业务数据与技术依赖混杂
  - 仅在共享流程状态明确时使用 `context`
- Step G：输出与错误判定
  - 查询结果单一明确时返回裸值
  - 结果包含状态、错误、警告、元信息时返回 `Result` 对象
  - 失败为意外时抛异常
  - 失败为正常业务分支时返回错误对象或结果对象
- Step H：副作用判定
  - 标记函数是否有外部副作用
  - 若核心为决策且副作用可后置，则拆为“决策/准备 + 提交”
  - 查询函数默认不得隐藏副作用
- Step I：命名判定
  - 优先具体动作词，禁止使用低信息量动词作为主动作：`do` / `manage`
  - `handle` / `process` 仅用于入口或流程
  - `dispatch` / `route` / `select` / `resolve` 仅用于分发
  - `pre` / `post` 仅用于阶段函数
  - 组合命名仅允许：`and` / `or` / `if_xxx`
  - 不将 `pure` / `impure` / `safe` / `do` / `undo` 写入函数名，`unsafe_` 可作为例外保留
- Step J：结构演进判定
  - 若复杂性来自状态、策略、生命周期，则升级为对象/类
  - 若复杂性来自稳定多阶段流程，则升级为 `pipeline/workflow`
  - 若复杂性来自多策略分支，则升级为 `strategy`

【一页式快速决策卡】
- 先问是否值得成为函数：
  - 有独立语义吗
  - 有明确输入输出吗
  - 有稳定名字吗
  - 拆出来会更清晰吗
- 先定角色：
  - 它是基础动作、过程阶段、组合便捷、编排、分发、入口、转换、校验、清理还是持久化
- 再定可见性：
  - 只服务当前流程则私有
  - 语义独立且稳定复用则公共
  - 阶段中有公共逻辑则抽公共基础函数
- 再定是否拆：
  - 多阶段且可命名则拆
  - 只是变短但不更清晰则不拆
- 再看副作用：
  - 是否修改外部状态
  - 查询是否偷偷写
  - 是否应把副作用外提
- 再看输入输出：
  - 参数是否最小、显式、透明
  - 返回值是否清晰表达结果
  - 失败应作为异常还是业务分支
- 最后命名：
  - 用具体动词
  - 阶段用 `pre_` / `post_`
  - 分发用 `dispatch` / `route` / `select` / `resolve`
  - 编排用 `orchestrate` / `run`
  - 入口用 `handle` / `process` / `execute`
  - 组合仅用 `and` / `or` / `if_xxx`
- 出现以下信号立刻重审：
  - `do` / `manage` / `helper` / `common`
  - 多个 bool 参数 / 参数爆炸
  - 阶段函数被公共复用
  - 查询函数有副作用
  - 名字越来越长
  - 编排函数越来越像上帝函数
