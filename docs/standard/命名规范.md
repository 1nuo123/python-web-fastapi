# 函数命名

## 函数设计

### 一、总目标

- **核心定位**：这份检查表不是知识说明书，而是一个可快速执行的决策体系。
- **目标**：让你或 LLM 在面对“我要写一个函数”时，能快速回答这些问题：
  - 这个函数该不该存在？
  - 它是什么角色？
  - 它该公开还是私有？
  - 它该不该拆？
  - 它是不是编排函数？
  - 它的名字该怎么取？
  - 它的输入输出怎么定？
  - 它能不能复用？
  - 它有没有副作用风险？
  - 它未来会不会演化成坏抽象？

### 二、总决策流程图（极简版）

- **按顺序执行以下快速总流程**：
  - 先判断：**是否值得成为独立函数**
  - 再判断：**函数角色**
  - 再判断：**是否公共暴露**
  - 再判断：**是否需要拆分**
  - 再判断：**是否需要编排层**
  - 再判断：**输入输出边界**
  - 再判断：**副作用与错误处理**
  - 最后：**命名**

### 三、一级快速决策表（核心定性）

- **1. 是否应该创建这个函数？**
  - **判断问题**：
    - 这段逻辑是否有独立语义？
    - 它是否有明确输入输出？
    - 它是否能被一个稳定名字概括？
    - 拆出来后是否让主流程更清晰？
    - 它是否不是单纯为了“减少代码行数”？
  - **快速结论**：
    - **是** → 进入下一步
    - **否** → 不要创建函数，保留在原地

- **2. 这个函数属于什么角色？（先判定角色，再决定写法和命名）**
  - **基础动作函数**：执行单一、稳定动作（典型动词：`create` / `get` / `update` / `delete` / `validate` / `parse` / `build`）
  - **过程函数**：表达某个流程阶段（典型动词：`pre_` / `post_` / `prepare_` / `finalize_`）
  - **组合函数**：封装多个基础动作以提升便利性（典型动词：`get_or_create` / `init_and_validate`）
  - **编排函数**：组织多个步骤调用，自身少做细节逻辑（典型动词：`orchestrate` / `run` / `process` / `execute`）
  - **分发器函数**：根据条件选择处理路径（典型动词：`dispatch` / `route` / `select` / `resolve`）
  - **入口函数**：对外统一接入点（典型动词：`handle` / `process` / `execute` / `serve`）
  - **转换函数**：结构化转换（典型动词：`to_` / `from_` / `convert_` / `serialize_` / `deserialize_`）
  - **校验函数**：检查约束或合法性（典型动词：`validate` / `check` / `verify` / `assert` / `can`）
  - **清理函数**：清理状态、资源或中间物（典型动词：`clean` / `cleanup` / `release` / `clear` / `dispose`）
  - **持久化函数**：落地、读取、装载状态（典型动词：`save` / `load` / `read` / `write` / `store` / `persist`）
  - **快速结论**：一个函数必须优先归类到一个主角色；若无法归类，说明抽象未想清楚。

- **3. 这个函数是公共能力还是内部细节？**
  - **判断问题**：
    - 它是否有稳定、独立的语义？
    - 它是否只依赖显式参数而不是隐式上下文？
    - 它是否只服务于某个主流程？
    - 如果别人复用它，是否容易误用？
    - 它公开后，是否会冻结内部实现？
    - 是否已经有真实第二个调用场景？
  - **快速结论**：
    - 仅当前流程使用 / 强依赖上下文 / 阶段性强 → **私有函数**
    - 语义独立 / 输入输出稳定 / 存在真实复用价值 → **公共函数**
    - 阶段函数中包含可复用逻辑 → **提炼公共基础函数 + 阶段函数保留私有**

- **4. 这个函数该不该拆？**
  - **判断问题**：
    - 当前函数是否在做多件事？
    - 多件事之间是否有清晰阶段边界？
    - 拆分后主函数是否更像业务剧本？
    - 子函数是否有稳定名字？
    - 拆分是为了语义清晰，还是只是为了“变短”？
    - 拆分后是否导致读者频繁跳转，反而更难理解？
  - **快速结论**：
    - 有清晰阶段 / 可命名 / 提升理解 → **拆**
    - 只是变短 / 子函数无独立语义 / 上下文过于紧密 → **不拆**

- **5. 是否需要升级为编排函数？**
  - **判断问题**：
    - 当前函数是否包含多个显式步骤？
    - 这些步骤是否存在顺序语义？
    - 主函数是否更适合只负责组织调用？
    - 是否存在天然阶段：前置、主体、持久化、后置？
    - 是否希望主函数像“流程说明书”？
  - **快速结论**：
    - **是** → 升级为编排函数
    - **否** → 保持为基础动作函数

- **6. 拆出来的 pre/post 函数是否可复用？**
  - **判断问题**：
    - 它是流程阶段，还是独立能力？
    - 脱离主流程后语义是否仍成立？
    - 它是否依赖主流程隐式上下文？
    - 其他调用方是否容易误用？
    - 它真正的语义是否应改名为具体动作词？
    - 是否已有真实复用场景？
  - **快速结论**：
    - 默认**私有**。
    - 若确有独立价值 → 抽出公共基础动作，不要直接把阶段函数当公共 API。
  - **推荐模式**：
    - `def normalize_input(data): ...`
    - `def validate_input(data): ...`
    - `def _pre_create_user(data):` (内部调用上述两个公共函数并返回)

### 四、二级快速决策表：输入 / 输出 / 副作用 / 错误

- **7. 输入边界是否合理？**
  - **判断问题**：
    - 这个函数真正依赖哪些输入？
    - 是否传入了过大的对象？
    - 是否存在隐式依赖未显式入参？
    - 参数是否过多？
    - 参数是否应聚合为一个对象？
    - 输入是否可能被函数修改？
    - 是否需要先归一化再处理？
  - **快速结论**：
    - 参数清晰、最小、显式 → **合理**
    - 过多、过散、依赖不透明 → **需要重构参数边界**
  - **快速警报**：
    - 多个布尔参数
    - 业务参数 + 配置参数 + 技术依赖混杂
    - 传整个 `context` 但只用很少字段
    - 传入大对象只为取其中 1~2 个值

- **8. 是否应该使用 context / 参数对象？**
  - **适合使用**：
    - 编排流程有共享状态
    - 多阶段逐步 enrich 同一份上下文
    - 需要携带 `trace` / `request` / `auth` / `runtime` 信息
    - 需要跨多个步骤传递统一结构
  - **不适合使用**：
    - 基础动作函数
    - 纯工具函数
    - 仅为了掩盖参数过多
    - 让函数真实依赖不透明
  - **快速结论**：
    - 共享流程状态明确 → **可以用 `context`**
    - 只是偷懒打包参数 → **不要用 `context`**

- **9. 输出边界是否合理？**
  - **判断问题**：
    - 返回的是结果、状态，还是副作用确认？
    - 返回 `bool` 是否丢失信息？
    - 返回 `None` 的语义是否清楚？
    - 是否需要更丰富的结果对象？
    - 是否返回了不该暴露的内部细节？
    - 失败时是抛异常、返回空值还是错误对象？
  - **快速结论**：
    - 返回值与职责匹配，语义清晰 → **合理**
    - 返回过弱 / 过重 / 泄漏内部 → **需要重构**

- **10. 是否应返回结果对象而不是裸值？**
  - **适合结果对象**：
    - 需要表达 success/failure
    - 需要附带错误原因、警告、元信息
    - 存在部分成功语义
    - 返回值未来会扩展
    - 结果不止一个值，而是一个“结果语义”
  - **不必使用结果对象**：
    - 纯简单函数
    - 返回值极明确
    - 内部辅助函数，包装收益不大
  - **快速结论**：
    - 返回的是“语义结果” → **用结果对象**
    - 返回的是“单一值” → **裸值即可**

- **11. 这个函数是否有副作用？**
  - **判断问题**：
    - 是否修改外部状态？
    - 是否写数据库？
    - 是否发消息？
    - 是否记录审计？
    - 是否修改传入对象？
    - 是否依赖全局状态？
    - 调用两次是否结果不同？
  - **快速结论**：
    - 无副作用 / 可控副作用 → **正常**
    - 副作用隐蔽 / 多副作用混杂 → **高风险，需要重构**
  - **规范动作**：
    - 查询函数尽量无副作用
    - 命令函数应显式承认副作用
    - 关键副作用应尽量放外层编排

- **12. 是否应把副作用推迟到更外层？**
  - **判断问题**：
    - 核心逻辑能否先纯计算，再提交？
    - 是否需要 dry-run？
    - 是否需要事务控制？
    - 是否需要批处理 / 延迟提交 / 异步提交？
    - 当前副作用是否让函数难测、难复用、难回滚？
  - **快速结论**：
    - 核心是决策，副作用是提交 → **分离**
    - 逻辑与副作用本就不可分 → **保持一体，但边界要清晰**

- **13. 错误处理该怎么做？**
  - **判断问题**：
    - 失败是意外还是正常业务分支？
    - 调用者是否需要根据失败原因分支处理？
    - 失败是否应中断整个流程？
    - 调用者是否容易忘记检查返回错误对象？
    - 是否存在部分成功 / 部分失败？
  - **快速结论**：
    - 意外 / 契约破坏 / 系统错误 → **抛异常**
    - 正常业务失败 / 需显式处理 → **返回错误对象 / Result**

### 五、三级快速决策表：命名

- **14. 函数命名是否准确？**
  - **判断问题**：
    - 名字表达的是“做什么”，还是“怎么实现”？
    - 是否用了模糊动词：`do`、`manage`、`handle` (若不是入口)、`process` (若不是流程)？
    - 是否能换成具体动词？
    - 名字是否泄漏实现细节？
    - 名字是否只能依赖注释理解？
  - **快速结论**：
    - 具体动作词清楚 → **合理**
    - 模糊、偷懒、难以理解 → **重命名**

- **15. 该选哪个动作词？（标准动作词速查表）**
  - **创建**：`create` / `build` / `make` / `init`
  - **获取**：`get` / `find` / `fetch` / `read` / `load` / `list`
  - **更新**：`update` / `set` / `patch` / `save` / `write` / `store` / `persist`
  - **删除**：`delete` / `remove` / `clear` / `destroy` / `dispose`
  - **校验**：`validate` / `check` / `verify` / `assert` / `can`
  - **转换**：`convert` / `to` / `from` / `parse` / `format` / `serialize` / `deserialize` / `encode` / `decode` / `normalize`
  - **比较**：`compare` / `match` / `matches` / `diff`
  - **处理入口**：`handle` / `process` / `execute` / `serve`
  - **编排**：`orchestrate` / `run` / `execute` / `process`
  - **分发**：`dispatch` / `route` / `select` / `resolve`
  - **清理**：`clean` / `cleanup` / `release` / `close` / `flush`
  - **并发**：`lock` / `unlock` / `wait_for` / `signal` / `notify` / `retry` / `cancel`

- **16. 是否该使用 pre_ / post_ ？**
  - **使用条件**：
    - 明确表达某主流程阶段
    - 是内部过程函数
    - 阶段语义比具体动作更重要
  - **不应使用**：
    - 替代具体动作词
    - 用来掩盖真实语义
    - 把阶段函数直接当公共 API 暴露
  - **快速结论**：
    - 阶段函数 → 可用 `pre_` / `post_`
    - 独立能力 → 用具体动作词，不用 `pre_` / `post_`

- **17. 是否该使用组合命名？**
  - **允许的标准组合**：`A_and_B`、`A_or_B`、`A_if_xxx`
  - **判断问题**：
    - 这是高频、稳定的组合吗？
    - 组合后命名是否仍清晰？
    - 是否只组合两个动作？
    - 是否真的值得暴露成一个便捷函数？
  - **快速结论**：
    - 稳定高频组合 → **允许**（推荐形式：`get_or_create`、`init_and_validate`、`create_if_absent`）
    - 长链条、多条件、复杂流程 → **改为编排函数，不要堆命名**

- **18. 哪些语义不应进入函数名？**
  - **不建议进入函数名**：`safe`、`pure`、`impure`、`do`、`undo`
  - **建议进入 metadata / 文档 / 规范属性**：
    - 纯/非纯、可撤销/补偿、幂等性、风险级别、生命周期、并发级别
  - **例外**：`unsafe_` 可以作为强语义前缀保留

### 六、四级快速决策表：结构演进

- **19. 何时应该保留为函数，何时升级为对象/类？**
  - **判断问题**：
    - 是否有内部状态？
    - 是否有多种可替换策略？
    - 是否参数越来越多？
    - 是否需要生命周期管理？
    - 是否有一组总一起出现的相关函数？
    - 是否已经表现出角色感？
  - **快速结论**：
    - 无状态、单动作、边界清晰 → **函数**
    - 有状态 / 有策略 / 有生命周期 / 多行为聚集 → **升级为对象/类**

- **20. 何时应该升级为策略对象？**
  - **判断问题**：
    - 同一目标是否有多种实现算法？
    - 是否充满 `if mode/type/...` 分支？
    - 是否需要运行时选择实现？
    - 新增一种处理方式时，当前函数是否必须大改？
  - **快速结论**：
    - 实现差异成为一级复杂度 → **策略对象**
    - 只是少量临时分支 → **保持函数**

- **21. 何时应该升级为 pipeline / workflow？**
  - **判断问题**：
    - 是否有多个稳定阶段？
    - 阶段之间是否有稳定接口？
    - 是否需要插拔 / 配置 / 监控 / 重试 / 阶段复用？
    - 这是否已经不是单个函数，而是一个工作流？
  - **快速结论**：
    - 阶段成为一级抽象 → **pipeline / workflow**
    - 只是简单顺序调用 → **编排函数足够**

- **22. 何时应拆为“准备 + 提交”两阶段？**
  - **判断问题**：
    - 是否存在不可逆副作用？
    - 是否需要 dry-run / 预览 / 二次确认？
    - 是否希望支持批量合并提交？
    - 是否可以把决策与提交分开？
  - **快速结论**：
    - 需要确认、预览、事务控制 → **拆成 prepare/plan + commit/apply**
    - 无需分离 → **保持单函数**

- **23. 何时应拆为“校验 + 执行”两阶段？**
  - **判断问题**：
    - 调用方是否有时只需要知道“能不能做”？
    - 校验逻辑是否值得复用？
    - 校验失败与执行失败是否应分开处理？
  - **快速结论**：
    - **是** → 拆为 `can_` / `validate_` + `execute` / `create` / `update`
    - **否** → 保持一体

- **24. 何时应拆为“解析 + 验证”两阶段？**
  - **判断问题**：
    - 解析错误与业务校验错误是否不同？
    - 调用方是否有时只需要结构解析？
    - 是否存在“可解析但不合法”的中间态？
  - **快速结论**：
    - **是** → 拆为 `parse_` + `validate_`
    - **否** → 可保留 `parse_and_validate_`

- **25. 何时应拆为“构造 + 持久化”两阶段？**
  - **判断问题**：
    - 调用方是否有时只想构造对象，不想立即落库？
    - 持久化是否有 I/O / 事务 / 权限成本？
    - 构造结果是否需要在落地前继续处理？
  - **快速结论**：
    - **是** → `build_` + `save_`
    - **否** → 一体函数可接受，但应明确副作用

- **26. 何时应区分“选择策略 + 执行策略”？**
  - **判断问题**：
    - 是否同时存在“选谁做”和“怎么做”？
    - 分支是否正在膨胀？
    - 新增策略是否造成频繁修改？
  - **快速结论**：
    - 选择复杂度高 → `resolve` / `select` + `execute`
    - 选择简单稳定 → **保持一体**

### 七、五级快速决策表：复用与抽象

- **27. 是否应该立即抽象复用？**
  - **判断问题**：
    - 是否已有真实第二个调用场景？
    - 这两个场景语义是否真正相同？
    - 未来演化方向是否一致？
    - 抽象后命名是否会变模糊？
    - 抽象后是否会出现一堆模式参数？
  - **快速结论**：
    - 共性稳定明确 → **抽象复用**
    - 只是看起来相似 / 未来不确定 → **先复制，后观察**

- **28. 什么时候复制代码比抽象更好？**
  - **适合先复制**：
    - 只有 2 处相似
    - 业务语义尚未稳定
    - 抽象后名字会很差
    - 抽象后要加很多条件参数
    - 演化方向尚未看清
  - **快速结论**：
    - 短期重复 < 错误抽象成本 → **先复制**

- **29. 便捷函数是否应该存在？**
  - **判断问题**：
    - 是否高频使用？
    - 是否组合关系稳定？
    - 是否不会隐藏关键副作用？
    - 是否建立在明确原子函数之上？
    - 是否显著减少样板代码？
  - **快速结论**：
    - 稳定高频组合 → **建立便捷函数**
    - 不稳定 / 模糊 / 隐藏太多 → **不建**

- **30. 原子函数和便捷函数是否应并存？**
  - **判断问题**：
    - 调用者是否有时想一步完成，有时想精细控制？
    - 是否存在清晰的低层能力与高层便利入口？
  - **快速结论**：
    - **是** → 原子函数 + 便捷函数并存
    - **否** → 只保留一种即可

### 八、六级快速决策表：并发 / 幂等 / 资源 / 生命周期

- **31. 是否需要考虑幂等性？**
  - **判断问题**：
    - 会不会被重试？
    - 会不会被重复消费？
    - 会不会被网络重发？
    - 重复执行是否会产生重复副作用？
    - 是否涉及创建、扣费、发消息、状态流转？
  - **快速结论**：
    - 可能重试 / 重放 / 重复消费 → **必须考虑幂等**
    - 纯读取 / 纯计算 → **一般无需额外幂等设计**

- **32. 是否需要考虑可取消语义？**
  - **判断问题**：
    - 是否长时间运行？
    - 是否需要用户中止？
    - 是否分多阶段？
    - 取消后是否需要补偿 / 清理？
  - **快速结论**：
    - 长任务 / 用户交互 / 工作流 → **设计取消语义**
    - 短原子动作 → **一般不需要**

- **33. 是否需要显式资源边界？**
  - **判断问题**：
    - 是否打开文件、连接、锁、事务、会话？
    - 谁负责释放？
    - 函数是否自闭合？
    - 调用者是否容易忘记关闭？
  - **快速结论**：
    - 资源显著 → **显式 `open/close`、`acquire/release` 或上下文管理**
    - 资源局部且安全自闭合 → **内部处理即可**

- **34. 是否需要事务边界？**
  - **判断问题**：
    - 多个写操作是否必须一致成功 / 失败？
    - 是否有双写问题？
    - 是否存在部分成功风险？
    - 是否需要回滚 / 补偿 / 最终一致性？
  - **快速结论**：
    - 一致性强要求 → **明确事务边界**
    - 可接受最终一致 → **设计补偿 / outbox / 异步机制**

- **35. 是否需要批处理接口？**
  - **判断问题**：
    - 调用者是否经常循环调用单条函数？
    - 是否存在明显批量优化机会？
    - 单条执行是否导致重复 I/O / 重复事务？
    - 批量错误语义是否不同？
  - **快速结论**：
    - 循环调用是主要用法 → **增加 `batch_` 或批量接口**
    - 单条为主 → **可先不做**

### 九、七级快速决策表：质量警报

- **36. 以下信号出现时，应立即重新审视设计**
  - **命名警报**：
    - `do_` / `manage_` / `helper_` / `common_` / `misc_`
    - `handle_`（但其实不是入口）
    - `process_`（但其实只是 CRUD）
  - **参数警报**：
    - 参数过多 / 多个 bool 参数 / 大量可选参数
    - `mode` / `type` / `flag` / `options` 过多
    - 技术依赖与业务数据混杂
  - **结构警报**：
    - 基础动作函数开始承担编排
    - 编排函数开始承担所有实现细节
    - 阶段函数被当公共 API 使用
    - 分发器函数开始做大量实际处理
    - 入口函数下沉到领域细节
  - **复用警报**：
    - 因“未来可能复用”而过早公开
    - 一个公共函数被越来越多场景参数污染
    - 抽象后名字越来越模糊
    - 相似代码被错误强行统一
  - **副作用警报**：
    - 查询函数偷偷写状态
    - 校验函数偷偷修复数据
    - 保存函数“顺手”发消息、清缓存、建索引
    - 函数行为需要靠注释才知道
  - **快速结论**：任何一类警报持续出现 → **立即回到“角色判定”和“职责边界”重审**

### 十、给 LLM / 自动化工具的标准执行协议

- **函数设计快速协议（Machine-Readable Human Checklist）**
  - **Step A：函数存在性判断**
    - 判断目标逻辑是否具有独立语义
    - 判断是否具有明确输入输出
    - 判断是否可用稳定名称概括
    - *若以上任一为否，则不建议创建独立函数*
  - **Step B：函数角色判定**
    - 将函数判定为以下一种主角色：`primitive`, `process`, `composite`, `orchestrator`, `dispatcher`, `entry`, `transformer`, `validator`, `cleaner`, `persistence`
    - *若无法归类，则说明抽象不稳定，不应继续生成*
  - **Step C：可见性判定**
    - 若函数仅服务特定主流程、依赖隐式上下文、阶段性强，则设为 `private/internal`
    - 若函数语义独立、输入输出稳定、存在真实复用，则设为 `public/shared`
    - 若阶段函数中含公共逻辑，则生成“公共基础函数 + 私有阶段包装”
  - **Step D：拆分判定**
    - 若函数同时承担多个清晰可命名步骤，并且拆分后主函数更清晰，则拆分，否则保持一体
  - **Step E：编排判定**
    - 若函数主要职责是组织多个步骤执行顺序，则判定为 `orchestrator`
    - 编排函数自身不应承载大量具体业务细节
  - **Step F：输入边界判定**
    - 仅保留真正依赖的参数，避免大对象滥传，避免多 bool 参数
    - 避免业务数据与技术依赖混杂
    - 仅在共享流程状态明确时使用 `context`
  - **Step G：输出与错误判定**
    - 查询结果单一明确 → 裸值
    - 结果包含状态/错误/警告/元信息 → `Result` 对象
    - 失败为意外 → 异常
    - 失败为正常业务分支 → 错误对象/结果对象
  - **Step H：副作用判定**
    - 标记函数是否有外部副作用
    - 若核心为决策且副作用可后置，则拆为“决策/准备 + 提交”
    - 查询函数默认不得隐藏副作用
  - **Step I：命名判定**
    - 优先具体动作词，禁止使用低信息量动词作为主动作：`do`/`manage`
    - `handle`/`process` 仅用于入口或流程
    - `dispatch`/`route`/`select`/`resolve` 仅用于分发
    - `pre`/`post` 仅用于阶段函数
    - 组合命名仅允许：`and`/`or`/`if_xxx`
    - 不将 `pure`/`impure`/`safe`/`do`/`undo` 写入函数名（`unsafe_` 可作为强语义前缀保留）
  - **Step J：结构演进判定**
    - 若复杂性来自状态/策略/生命周期 → 升级为对象/类
    - 若复杂性来自稳定多阶段流程 → 升级为 `pipeline/workflow`
    - 若复杂性来自多策略分支 → 升级为 `strategy`

### 十一、最终超短版：一页式快速决策卡

- **1. 先问是否值得成为函数**
  - 有独立语义吗？有明确输入输出吗？有稳定名字吗？拆出来会更清晰吗？
- **2. 先定角色**
  - 它是：基础动作 / 过程阶段 / 组合便捷 / 编排 / 分发 / 入口 / 转换 / 校验 / 清理 / 持久化？
- **3. 再定可见性**
  - 只服务当前流程 → 私有
  - 语义独立且稳定复用 → 公共
  - 阶段中有公共逻辑 → 抽公共基础函数
- **4. 再定是否拆**
  - 多阶段且可命名 → 拆
  - 只是变短但不更清晰 → 不拆
- **5. 再看副作用**
  - 有无外部状态修改？查询是否偷偷写？是否应把副作用外提？
- **6. 再看输入输出**
  - 参数是否最小、显式、透明？
  - 返回值是否清晰表达结果？
  - 失败是异常还是业务分支？
- **7. 最后命名**
  - 用具体动词
  - 阶段用 `pre_` / `post_`
  - 分发用 `dispatch` / `route` / `select` / `resolve`
  - 编排用 `orchestrate` / `run`
  - 入口用 `handle` / `process` / `execute`
  - 组合仅用 `and` / `or` / `if_xxx`
- **8. 出现这些信号立刻重审**
  - `do` / `manage` / `helper` / `common`
  - 多个 bool 参数 / 参数爆炸
  - 阶段函数被公共复用
  - 查询函数有副作用
  - 名字越来越长 / 编排函数越来越像上帝函数

# 类命名

**抽象命名模板（The Abstract Naming Template）**
基于元角色的概念，我们可以推导出一个适用于任何面向对象语言、任何架构的极简、高度抽象的命名公式：

**终极命名公式：**
类名 = [约束定语] + [核心领域名词] + [抽象元角色]

**模板拆解说明：**

  - **[约束定语] (Constraint / Modifier) —— 可选**
    作用：描述该类的运行环境、状态限制或非功能性特征（如并发性、网络协议、生命周期）。
    词性：形容词 (Adjective) 或 副词性质的词缀。
    示例：Async (异步的), Concurrent (并发的), Remote (远程的), Cached (缓存的), ReadOnly (只读的), Persistent (持久化的)。
  - **[核心领域名词] (Core Domain Noun) —— 必填**
    作用：描述该类操作的核心业务实体或数据主体，回答“它在处理什么”。
    词性：纯名词 (Noun)。
    示例：Order (订单), Message (消息), SensorData (传感器数据), User (用户), Payment (支付)。
  - **[抽象元角色] (Meta-Role / Archetype) —— 必填**
    作用：描述该类在系统中的本质行为和生存方式，回答“它是怎么运作的”。
    词性：动名词 (Verb-er/or) 或 具有功能隐喻的名词。

**核心字典（6大派系）：**

  - **载体型 (Holder)**：Context (上下文), State (状态), Snapshot (快照), Profile (画像)
  - **驱动型 (Doer)**：Evaluator (评估器), Parser (解析器), Extractor (提取器), Converter (转换器)
  - **调度型 (Coordinator)**：Orchestrator (编排器), Engine (引擎), Pipeline (管道), Router (路由器)
  - **边界型 (Boundary)**：Port (端口), Gateway (网关), Proxy (代理), Bridge (桥接)
  - **结构型 (Structurer)**：Registry (注册表), Graph (图/网), Pool (池), Catalog (目录)
  - **孕育型 (Creator)**：Provider (提供者), Factory (工厂), Allocator (分配器)

**公式应用演示：**

  - [异步 Async] + [消息 Message] + [路由器 Router] = AsyncMessageRouter
  - [只读 ReadOnly] + [设备 Device] + [快照 Snapshot] = ReadOnlyDeviceSnapshot
  - [持久化 Persistent] + [任务 Task] + [编排器 Orchestrator] = PersistentTaskOrchestrator
