# 快速开发缓存与任务队列轻量修正执行方案

## 任务目标

交付一组低复杂度修正，用于满足快速开发阶段的缓存与任务队列闭环一致性：

- 统一 memory 与 Redis 的鉴权失败计数窗口语义，避免测试环境和生产环境行为漂移。
- 明确 `task_binding_provider.py` 为空是业务任务绑定占位设计。
- 标注 Funboost/RabbitMQ 中当前仅预留、尚未落地到执行链路的配置字段。

完成判定：源码注释、轻量实现、测试和文档都能明确表达当前快速开发规格；不引入生产级任务平台复杂度。

## 全局约束

- 以源码为准；若历史文档、图谱、执行方案与源码冲突，以源码为准，并说明旧文档可能过期。
- 只做快速开发阶段必要修正，不引入 outbox、分布式事务、任务审计主体扩展、DLQ 监控平台等复杂能力。
- 优先保持现有 public API、配置结构和模块边界不变。
- 缓存计数窗口以 Redis 当前 Lua 行为为准：首次计数设置 TTL，后续递增不刷新 TTL，即固定窗口。
- `task_binding_provider.py` 保持返回空列表，不新增默认业务任务。
- Funboost/RabbitMQ 预留字段只标注生效范围，不强行实现全部配置。
- 日志、注释、文档使用中文，不泄露 token、密码、完整连接串。
- 契约设计遵循“公共头字段 + 强类型扩展字段”规则。
- 如需新增或修改 Pydantic 扩展契约，必须使用判别联合，扩展字段必须有 `kind`、`schema_version`，必须启用 `extra="forbid"`。
- 禁止用 `dict[str, Any]`、`metadata`、`extra_payload` 承载稳定协议。
- 外层类型与内层扩展类型必须一致，至少校验 `detail_kind == detail.kind` 与 `schema_version` 一致。

## 验收标准

- memory 与 Redis 的 `increment_with_expire` 在重复递增时 TTL 窗口语义一致。
- 鉴权失败节流在 memory 后端与 Redis 后端下不会因为 TTL 刷新策略不同而产生不同锁定窗口。
- `task_binding_provider.py` 的空实现被清楚标注为业务项目扩展点。
- Funboost/RabbitMQ 当前预留但未实际生效的配置字段有清晰说明。
- 相关单元测试、路径测试和文档回归完成。
- 不改变现有任务派发入口、缓存配置结构、认证用例调用方式。

## Phase 1

### 目标

统一 memory 与 Redis 计数窗口语义。

当前阶段完成后，`MemoryCacheStore.increment_with_expire()` 与 `RedisCacheStore.increment_with_expire()` 都采用固定窗口：首次递增设置 TTL，窗口内后续递增不刷新 TTL。

### 依赖

- 现有 `CacheStore.increment_with_expire()` 抽象。
- 现有 `MemoryCacheStore`、`RedisCacheStore`。
- 现有 `AuthFailureThrottle` 通过 `CacheService.increment_counter()` 调用底层计数能力。

### 契约

| 英文名 | 中文名 | 中文说明 |
|---|---|---|
| `CacheStore.increment_with_expire` | 带过期计数递增 | 原子递增计数；当 key 首次创建时设置 TTL；窗口内重复递增不得刷新 TTL。 |
| `FixedWindowCounter` | 固定窗口计数 | 以第一次失败为窗口起点，到 TTL 到期前计数累加；TTL 到期后重新开始窗口。 |
| `AuthThrottleStatePayload` | 鉴权节流状态载荷 | 现有强类型缓存载荷，包含 `kind`、`schema_version`、失败次数和锁定截止时间。 |

### 任务清单

- [x] 修改 `CacheStore.increment_with_expire()` 文档，明确固定窗口语义。
- [x] 修改 `MemoryCacheStore.increment_with_expire()`，已有 key 递增时保留原 entry 的剩余 TTL 语义，不重新设置完整 TTL。
- [x] 保持 `RedisCacheStore` Lua 脚本不变，作为固定窗口基准。
- [x] 检查 `CacheService.increment_counter()` 不额外刷新 TTL。
- [x] 检查 `AuthFailureThrottle` 不需要改调用方式。

### 关键代码片段

```python
def increment_with_expire(self, key: str, ttl_seconds: int) -> int:
    with self._lock:
        entry = self._items.get(key)
        if entry is None:
            self._items[key] = MemoryCacheEntry(value="1", ttl_seconds=ttl_seconds)
            return 1
        next_value = int(entry.value) + 1
        entry.value = str(next_value)
        return next_value
```

### 校验

- memory 后端连续递增不会延长原 TTL。
- Redis 后端行为不变。
- 鉴权节流测试仍能通过。

## Phase 2

### 目标

明确 `task_binding_provider.py` 返回空列表是快速开发骨架的业务扩展占位，而不是遗漏实现。

当前阶段完成后，后续开发者能清楚知道：框架不默认注册业务任务，真实项目应通过该 provider 或测试工厂注入 `RegisteredTaskBinding`。

### 依赖

- Phase 1 完成。
- 现有 `ApplicationTaskBindingProvider.build()`。
- 现有 `FastApiAppAssembler` 对 task bindings 的注入逻辑。

### 模拟用法

```python
class ApplicationTaskBindingProvider:
    def build(self) -> list[RegisteredTaskBinding]:
        return [
            RegisteredTaskBinding(
                job_kind="demo_task",
                payload_model=DemoTaskPayload,
                handler=DemoTaskHandler(),
            )
        ]
```

### 契约

| 英文名 | 中文名 | 中文说明 |
|---|---|---|
| `ApplicationTaskBindingProvider` | 应用任务绑定提供器 | 快速开发阶段的业务扩展点；默认不注册业务任务。 |
| `RegisteredTaskBinding` | 已注册任务绑定 | 连接 `job_kind`、payload Pydantic 模型和 `TaskHandler` 实例。 |
| `TaskHandler` | 任务处理器 | 业务任务执行入口，处理强类型 `TypedTaskInvocation`。 |

### 任务清单

- [x] 修改 `src/api/task_binding_provider.py` 的模块注释，说明默认空实现是占位设计。
- [x] 修改 `ApplicationTaskBindingProvider.build()` 注释，说明业务项目应在这里返回真实 bindings。
- [x] 在文档中说明：启用的 `modules.task.registrations` 必须有对应 handler binding。
- [x] 不新增默认 demo handler，避免骨架代码隐式承载业务逻辑。
