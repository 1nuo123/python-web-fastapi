# 缓存基建完善执行方案

> 历史说明：本文中的“统一异常语义”是 2026-05-16 的阶段性描述。当前源码已迁移为按缓存命名空间区分 Redis 不可用策略：认证、鉴权、限流 fail-closed，普通查询缓存可 fail-open；若本文与当前源码或 `docs/2026_5_23_2233_repository事务边界与缓存策略规范执行方案.md` 冲突，以当前源码为准。

## 任务目标
最终要交付一套可在当前 FastAPI 工程中真实落地的缓存基建层，覆盖缓存配置、键空间、强类型值契约、内存/Redis 双后端装配、首个真实消费方接入与测试回归。
完成判定是：
- 当前源码中的缓存能力不再停留在裸 `key/value` 与零散 TTL，而是具备统一键规则、统一序列化、统一默认 TTL、统一异常语义。
- 内存后端与 Redis 后端都能通过同一套缓存基建接口工作。
- 至少一个真实消费链路优先选用现有 `AuthFailureThrottle` 完成接入，证明基建可用而非空转抽象。

## 全局约束
- 严格遵守 `docs/standard/编码规范.md`、`docs/standard/命名规范.md`、`docs/standard/测试规范.md`；注释、日志、文档统一使用中文。
- 若设计文档、图谱、历史方案与当前源码冲突，以当前源码为准，并在文档回归中明确标注旧文档可能过期。
- 缓存基建保持分层：`core` 只定义契约，`infrastructure/cache` 只实现缓存基础设施，业务消费方通过显式依赖接入，不把键拼接、序列化、TTL 决策散落到业务代码。
- 契约统一采用“公共头字段 + 强类型扩展字段”模式；扩展字段必须使用 Pydantic 判别联合；扩展模型必须包含 `kind`、`schema_version`，并启用 `extra="forbid"`。
- 禁止在缓存契约、缓存值、缓存配置中使用 `dict[str, Any]`、`metadata`、`extra_payload`。
- 外层类型与内层扩展类型必须一致；例如 `backend="redis"` 时，扩展配置必须是 Redis 扩展模型，缓存值读取声明的扩展类型必须与实际落库的 `kind` 一致。
- 优先复用现有 `cachetools`、`redis`、`SharedResourceMount`、`AppSettingsLoader`、`AuthFailureThrottle`；不引入新的重型缓存框架。
- 内存缓存必须考虑并发访问边界；Redis 缓存必须保持可诊断的连接失败语义和资源释放语义。

## 验收标准
- `runtime.cache` 完成强类型收口，配置非法时在加载阶段直接失败，且错误信息可定位到具体字段。
- 缓存值完成统一信封化，落库内容可稳定区分公共头与扩展体，扩展体校验失败时有稳定处理策略。
- 内存缓存支持默认 TTL、显式 TTL、过期删除与并发安全；Redis 缓存支持相同语义并保持 `system.cache.unavailable` 异常风格。
- 缓存键具备统一前缀与命名空间规则，不再在业务代码中手写散落字符串键。
- `AuthFailureThrottle` 完成对新缓存基建的接入，行为与现有鉴权频控语义保持一致。
- 受影响测试全部通过，至少覆盖单元、路径、类继承、初始化、异常、边界、集成回归。
- `docs/design_docs/FastAPI统一Web基础设施实现规格.md`、缓存配置示例与最终源码一致。

## Phase 1
### 目标
先把缓存基建的边界定义清楚，解决当前“设计文档要求有命名空间、序列化策略，但源码只有裸字符串接口”的直接问题。
当前阶段完成后的中间结果是：
- `runtime.cache` 不再是扁平且弱约束的配置结构。
- 缓存值具备统一公共头和强类型扩展体。
- 后续实现阶段可以围绕稳定契约编码，而不是边写边补字段。

### 依赖
- 依赖当前 `src/core/cache_contract/cache_store_contract.py`、`src/infrastructure/settings/app_settings_loader.py`。
- 依赖 `docs/design_docs/FastAPI统一Web基础设施实现规格.md` 对缓存能力的历史描述，但若描述与源码冲突，以源码为准，并说明文档可能过期。

### 模拟用法
```toml
[runtime]
backend = "redis"
default_ttl_seconds = 30
key_prefix = "fastapi_web_skeleton"

[runtime.backend_detail]
kind = "redis_cache_backend"
schema_version = "1.0"
redis_url = "redis://redis:6379/0"
socket_connect_timeout_seconds = 2
```

### 契约
| 英文名 | 中文名 | 中文说明 |
|---|---|---|
| CacheRuntimeSettings | 缓存运行时配置 | 缓存公共配置，承载 `backend`、`default_ttl_seconds`、`key_prefix` 等公共头字段，并持有强类型扩展字段。 |
| CacheBackendDetailUnion | 缓存后端扩展联合 | 使用 Pydantic 判别联合承载后端扩展模型；首版至少包含 `MemoryCacheBackendDetail` 与 `RedisCacheBackendDetail`。 |
| MemoryCacheBackendDetail | 内存缓存扩展配置 | 描述内存缓存独有参数，如 `kind`、`schema_version`、`max_entries`；启用 `extra="forbid"`。 |
| RedisCacheBackendDetail | Redis 缓存扩展配置 | 描述 Redis 独有参数，如 `kind`、`schema_version`、`redis_url`、连接超时；启用 `extra="forbid"`。 |
| CacheEntryHeader | 缓存公共头字段 | 描述缓存项的公共头字段，如 `namespace`、`key`、`ttl_seconds`、`value_kind`。 |
| CachePayloadUnion | 缓存扩展体联合 | 使用判别联合承载缓存值扩展模型，禁止裸 JSON；当前至少纳入 `AuthThrottleStatePayload`。 |

### 关键代码片段
```python
class CacheEntryHeader(BaseModel):
    model_config = ConfigDict(extra="forbid")

    namespace: str
    key: str
    ttl_seconds: int
    value_kind: str


class CacheEnvelope(BaseModel):
    model_config = ConfigDict(extra="forbid")

    header: CacheEntryHeader
    data: CachePayloadUnion
```

```python
CacheBackendDetailUnion = Annotated[
    MemoryCacheBackendDetail | RedisCacheBackendDetail,
    Field(discriminator="kind"),
]
```

### 校验
- 使用最小配置加载 `runtime.cache` 时，合法配置可通过，非法 `backend/detail` 组合直接失败。
- `CacheEnvelope` 能正确校验 `header + data`，未知 `kind` 或多余字段会失败。
- 当前设计文档与源码冲突点已被记录，避免后续实现被旧文档误导。

## Phase 2
### 目标
落地缓存基础设施实现，解决当前“只有底层 `get/set/delete`，没有键构造、值编解码、默认 TTL 与后端统一入口”的直接问题。
当前阶段完成后的中间结果是：
- 业务侧可以通过统一缓存服务读写强类型缓存值。
- 内存与 Redis 后端具备一致行为。
- 默认 TTL、显式 TTL、资源关闭、异常转换都由基建层统一处理。

### 依赖
- 依赖 Phase 1 已稳定的缓存配置契约、缓存值契约、命名空间契约。
- 依赖现有 `MemoryCacheStore`、`RedisCacheStore`、`SharedResourceMount`。

### 模拟用法
```python

    namespace=CacheNamespace.AUTH_THROTTLE,
```

### 契约
| 英文名 | 中文名 | 中文说明 |
|---|---|---|
| CacheStore | 缓存底层存储契约 | 保持为后端适配层接口，只负责字符串读写与资源生命周期，不承担键拼接和业务序列化。 |
| CacheService | 缓存服务入口 | 缓存基建统一入口，负责键构造、值编解码、默认 TTL 回填、扩展体读写。 |
| CacheWriteRequest | 缓存写入请求 | 描述命名空间、键片段、扩展体、TTL 的强类型写入请求。 |
| CacheReadResult | 缓存读取结果 | 描述读取到的缓存信封或空值，避免业务侧手写 JSON 解析。 |
| CacheNamespace | 缓存命名空间 | 强类型命名空间枚举，禁止业务层手写散落字符串前缀。 |

### 关键代码片段
```python
class CacheService:
    def write_payload(
        self,
        *,
        namespace: CacheNamespace,
        key_parts: list[str],
        payload: CachePayloadUnion,
        ttl_seconds: int | None = None,
    ) -> None: ...

    def read_payload(
        self,
        *,
        namespace: CacheNamespace,
        key_parts: list[str],
        payload_type: type[T_CachePayload],
    ) -> T_CachePayload | None: ...
```

```python
cache_key = cache_key_builder.build(
    namespace=CacheNamespace.AUTH_THROTTLE,
    key_parts=[channel.value, subject_digest],
)
raw_value = cache_store.get_value(cache_key)
```

### 校验
- 未显式传入 TTL 时，缓存服务自动回填 `default_ttl_seconds`。
- 同一业务值在内存后端与 Redis 后端下读写结果一致。
- Redis 不可用时，仍返回稳定的 `system.cache.unavailable` 语义。
- 内存缓存并发读写不会因为共享可变状态产生明显竞态问题。

## Phase 3
### 目标
把新缓存基建接入真实消费链路，解决当前“缓存层存在但业务仍直接操作底层字符串缓存”的直接问题。
当前阶段完成后的中间结果是：
- `AuthFailureThrottle` 成为首个真实消费方。
- 鉴权频控不再自己负责缓存键拼接和 JSON 编解码。
- 新缓存基建具备继续承接令牌态、会话态等后续缓存场景的能力。

### 依赖
- 依赖 Phase 1 的缓存契约。
- 依赖 Phase 2 的缓存服务、键构造器、编解码器和资源装配。
- 依赖当前 `src/infrastructure/auth/auth_failure_throttle.py` 与相关鉴权测试。

### 模拟用法

```python
state = cache_service.read_payload(
```

### 契约
| 英文名 | 中文名 | 中文说明 |
|---|---|---|
| AuthThrottleStatePayload | 鉴权频控状态扩展体 | 继续作为缓存扩展体之一，纳入判别联合，保留 `kind`、`schema_version` 与 `extra="forbid"`。 |
| AuthThrottlePolicy | 鉴权频控策略 | 继续描述频控阈值、窗口、锁定时长，但不再承担缓存键与落库细节。 |
| CacheNamespace.AUTH_THROTTLE | 鉴权频控命名空间 | 固化鉴权频控缓存前缀，避免业务代码散落魔法字符串。 |
