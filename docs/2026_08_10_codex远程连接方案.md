普通注册用户当前默认不携带 scope，管理员后续授权的基础是正确的：[public_registration_role_synchronizer.py (line 13)](E:/python_web_fastapi/work/src/infrastructure/auth/public_registration_role_synchronizer.py:13)。Codex scope 也已定义，包括 files、terminal、full access 和 admin scope：[auth_scope_code.py (line 32)](E:/python_web_fastapi/work/src/domain/auth/auth_scope_code.py:32)。

**必须明确的边界**

1. **平台管理员权限不等于 Windows 管理员权限。**
   网站管理员可以控制“通过本平台发起的远程 Codex 会话”，但不能阻止电脑所有者在本地直接运行自己的 Codex CLI。
2. **个人电脑专属指平台所有权独占。**
   每个 Host 只能有一个 `owner_subject_id`；不提供共享、成员、协作者和转让接口。一个用户可以拥有多台个人电脑，数量通过配额控制。
3. **暂不做物理硬件反共享。**
   当前设备身份基于用户级设备密钥和 DPAPI。相同物理电脑的不同 Windows 账号理论上可以形成不同 Host。若要禁止这种情况，需要 TPM 或机器级身份，会引入本机管理员权限和隐私问题，不应放入当前阶段。
4. **管理员默认不得查看用户内容。**
   管理员只查看用户授权状态、主机在线状态、版本、doctor 和策略漂移，不查看 prompt、diff、终端输出和文件正文。现有 `codex:admin_content_access` 暂不启用。
5. **不提供通用远程桌面或任意 Shell API。**
   只允许经过强类型产品契约的 Codex thread、turn、approval 等操作。
6. **继续使用本地 stdio App Server。**
   不把 App Server 直接暴露到公网。官方仍将远程 App Server WebSocket 标记为实验能力，现有 Agent 本地启动 `app-server --stdio` 的路线更适合生产。[Codex App Server](https://learn.chatgpt.com/docs/app-server)

**目标权限模型**

权限必须分成两层，缺一不可：

| 层级           | 解决的问题                                               | 实现位置                            |
| -------------- | -------------------------------------------------------- | ----------------------------------- |
| 平台 RBAC      | 用户能否看页面、连接电脑、创建任务、处理审批             | 现有 role/scope                     |
| Codex 执行授权 | Codex 能写哪些目录、是否联网、何时审批、能否 full access | 有效 `auth_scope` + Host capability + Agent 强制校验 |

Codex 操作与 scope 的固定映射：

| 操作 | 所需 scope |
| --- | --- |
| 查看 Host、Workspace、Thread | `codex:read` |
| 创建、运行、steer、interrupt | `codex:operate` |
| 处理审批 | `codex:approve` |
| 注册、撤销和维护 Host | `codex:host_manage` |
| 文件变更 | `codex:files` |
| 终端命令 | `codex:terminal` |
| 联网 | `codex:network` |
| `danger-full-access` | `codex:full_access` |

第一版生产环境应禁止：

- `approval_policy=never`
- 永久 full access
- 全网通配符
- 用户自行扩大可写根目录
- 仅凭前端传入的 sandbox/approval 参数执行

官方也明确将 sandbox 和 approval policy 视为两层不同控制；`requirements.toml` 可以进一步强制用户不可覆盖的本机 sandbox、审批和网络约束。[Agent approvals](https://learn.chatgpt.com/docs/agent-approvals-security#sandbox-and-approvals) [requirements.toml](https://learn.chatgpt.com/docs/config-file/config-reference#requirementstoml)

推荐的最终计算规则是：

```
effective_scopes = enabled(用户直接 scopes ∪ 全部角色 scopes)

allowed = 请求所需 scopes ⊆ effective_scopes

执行参数仍须同时满足 Host capability 与 Agent 本地安全约束
```

任何层级不允许的能力都必须 fail-closed。

## 阶段 2：管理员 Scope 授权产品化

不能继续要求管理员在通用角色页面手填逗号分隔的 scope 和角色 key。当前页面仍是这种方式：[roles.vue (line 27)](E:/python_web_fastapi/typescript-web-nuxt/app/pages/admin/identity/roles.vue:27)。

Codex 授权统一进入通用身份管理，不再维护第二套授权事实源。Host 元数据仍由独立 Codex 管理接口读取。

数据结构：

- `auth_user_scope`：用户直接 scopes
- `auth_user_role`：用户角色
- `auth_role_scope`：角色 scopes
- `auth_scope`：启用状态与 scope 元数据

核心字段：

- 用户直接 scope codes
- 角色 keys 与角色 scope codes
- 过滤禁用项后的最终 scope codes
- 管理操作主体、目标用户和操作类型审计

API：

- `PUT /admin/users/{subject_id}/scopes`
- `GET /admin/users/{subject_id}`
- `GET /admin/codex/hosts`
- `GET /auth/me`

任务清单：

- [x] 新增 `codex:admin_manage` 路由保护。

## 阶段 4：无脑连接和首次使用

初始基线中的 Agent 已经会自动打开带用户码的浏览器，但网站正常入口仍要求手工输入用户码。当前正常路径已迁移为短时、一次性且绑定登录主体与浏览器 session 的 enrollment intent；用户码和二维码仅保留为 fallback。

推荐正常流程：

1. 管理员给用户授予所需 Codex scopes。
2. 用户登录后只看到“连接我的电脑”。
3. 已安装 Agent 时，网站调用 `codexremote://enroll?...`。
4. 未安装时下载签名 MSI；安装完成后自动恢复 enrollment intent。
5. Agent 生成设备密钥并打开已预填的验证页面。
6. 用户只需核对电脑名和短指纹，点击“确认”。
7. Agent 本地弹出一次原生文件夹选择器，选择允许的项目目录。
8. 网站自动选中该电脑和项目，进入“新建任务”。
