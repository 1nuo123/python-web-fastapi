普通注册用户当前默认不携带 scope，管理员后续授权的基础是正确的：[public_registration_role_synchronizer.py (line 13)](E:/python_web_fastapi/work/src/infrastructure/auth/public_registration_role_synchronizer.py:13)。Codex scope 也已定义，包括 files、terminal、full access 和 admin scope：[auth_scope_code.py (line 32)](E:/python_web_fastapi/work/src/domain/auth/auth_scope_code.py:32)。

**必须明确的边界**

1. **平台管理员权限不等于 Windows 管理员权限。**
   网站管理员可以控制“通过本平台发起的远程 Codex 会话”，但不能阻止电脑所有者在本地直接运行自己的 Codex CLI。
2. **个人电脑专属指平台所有权独占。**
   每个 Host 只能有一个 `owner_subject_id`；不提供共享、成员、协作者和转让接口。一个用户可以拥有多台个人电脑，数量通过配额控制。
3. **暂不做物理硬件反共享。**
   当前设备身份基于用户级设备密钥和 DPAPI。相同物理电脑的不同 Windows 账号理论上可以形成不同 Host。若要禁止这种情况，需要 TPM 或机器级身份，会引入本机管理员权限和隐私问题，不应放入当前阶段。
4. **管理员默认不得查看用户内容。**
   管理员只查看用户授权状态、主机在线状态、版本、doctor 和策略漂移，不查看 prompt、diff、终端输出和文件正文。现有 `codex:admin_content_access` 暂不启用。
5. **不提供通用远程桌面或任意 Shell API。**
   只允许经过强类型产品契约的 Codex thread、turn、approval 等操作。
6. **继续使用本地 stdio App Server。**
   不把 App Server 直接暴露到公网。官方仍将远程 App Server WebSocket 标记为实验能力，现有 Agent 本地启动 `app-server --stdio` 的路线更适合生产。[Codex App Server](https://learn.chatgpt.com/docs/app-server)

**目标权限模型**

权限必须分成两层，缺一不可：

| 层级           | 解决的问题                                               | 实现位置                            |
| -------------- | -------------------------------------------------------- | ----------------------------------- |
| 平台 RBAC      | 用户能否看页面、连接电脑、创建任务、处理审批             | 现有 role/scope                     |
| Codex 执行策略 | Codex 能写哪些目录、是否联网、何时审批、能否 full access | Permission Profile + Agent 强制校验 |

推荐首批内置权限模板：

| 模板                          | RBAC                                | 执行策略                                         |
| ----------------------------- | ----------------------------------- | ------------------------------------------------ |
| `codex_read_only`             | `codex:read`                        | read-only、网络关闭                              |
| `codex_standard`              | read、operate、approve、host_manage | workspace-write、on-request、网络关闭            |
| `codex_networked`             | standard + terminal/files           | workspace-write、on-request、域名白名单          |
| `codex_full_access_temporary` | standard + full_access              | danger-full-access、on-request、必须设置过期时间 |

第一版生产环境应禁止：

- `approval_policy=never`
- 永久 full access
- 全网通配符
- 用户自行扩大可写根目录
- 仅凭前端传入的 sandbox/approval 参数执行

官方也明确将 sandbox 和 approval policy 视为两层不同控制；`requirements.toml` 可以进一步强制用户不可覆盖的 permission profile、sandbox、审批和网络约束。[Agent approvals](https://learn.chatgpt.com/docs/agent-approvals-security#sandbox-and-approvals) [requirements.toml](https://learn.chatgpt.com/docs/config-file/config-reference#requirementstoml)

推荐的最终计算规则是：

```
最终权限 =
用户请求
∩ 管理员分配的 Permission Profile
∩ 用户 RBAC scope
∩ Host 实际 capability
∩ Agent 本地安全策略
```

任何层级不允许的能力都必须 fail-closed。

## 阶段 4：无脑连接和首次使用

现有 Agent 已经会自动打开带用户码的浏览器，这是可以保留的良好基础：[agent_setup.py (line 50)](E:/python_web_fastapi/work/src/infrastructure/codex_agent/agent_setup.py:50)。但网站正常入口仍要求用户手动输入 Agent 用户码：[settings/index.vue (line 132)](E:/python_web_fastapi/typescript-web-nuxt/app/pages/codex/settings/index.vue:132)。

7. Agent 本地弹出一次原生文件夹选择器，选择允许的项目目录。

**代码落点建议**

后端继续遵循现有分层：

- `core`：Permission Profile、assignment、policy envelope 强类型契约。
- `domain`：有效权限求交、独占所有权、过期和降级策略。
- `application`：分配权限、解析有效策略、撤销和 Agent policy ack 用例。

- `api`：新增独立 `endpoint_codex_admin`，不把复杂逻辑放 route。
- `Agent`：policy verifier、URI enrollment、原生 folder picker、更新运行时。
- `Nuxt`：`app/pages/admin/codex/` 管理页面及独立 API client/store。

所有外部契约使用 Pydantic `extra="forbid"`，内部结果使用 dataclass，禁止以 `dict[str, Any]` 承载稳定协议；事务仍只由 UoW 提交，类名继续使用 `Policy`、`Usecase`、`Port`、`Repository`、`Gateway`、`Store`，不要新增含糊的 Manager/Helper/Utils。这与现有[编码规范 (line 30)](E:/python_web_fastapi/work/docs/standard/编码规范.md:30)和[命名规范 (line 45)](E:/python_web_fastapi/work/docs/standard/命名规范.md:45)一致。
