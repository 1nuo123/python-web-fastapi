## Phase 1
### 目标
把请求体大小保护从“完整读取后再拒绝”改为“真正的前置/流式限额保护”，保证 413 不再是事后拒绝。

当前阶段完成后的中间结果：
- 超限请求不会先完整进入内存。
- 统一异常与统一响应封装保持不变。

### 依赖
- 现有 `ResponseEnvelopeFactory`、`HttpFaultException`、`SettingsStateHolder`。
- 现有请求作用域中间件先于请求体保护中间件生效。
- 现有 `runtime.web.max_request_body_bytes` 继续作为唯一上限真值。

### 契约
| 英文名 | 中文名 | 中文说明 |
|---|---|---|
| `max_request_body_bytes` | 请求体上限 | `runtime.web` 中的正整数上限，超过即拒绝 |
| `REQUEST_PAYLOAD_TOO_LARGE` | 请求体过大错误码 | 超限时统一返回的业务错误码 |
| `413 Request Entity Too Large` | 请求体过大状态 | 超限时固定返回的 HTTP 状态，响应包结构不变 |

### 任务清单
- [x] 基于 `Content-Length` 做前置拒绝，已超限时不进入完整 `request.body()` 路径。
- [x] 对无 `Content-Length` 或分块传输请求改为限额流式读取，累计超限后立即中止。
- [x] 保留统一异常、统一响应、请求作用域字段与错误码，不引入旁路响应格式。
- [x] 补齐空体、刚好等于上限、上限加 1、无 `Content-Length`、伪造过小 `Content-Length` 的处理分支。

### 关键代码片段
```python
limit = settings.runtime.web.max_request_body_bytes
content_length = request.headers.get("content-length")
if content_length is not None and int(content_length) > limit:
    return build_413_response(...)

received = 0
async for chunk in request.stream():
    received += len(chunk)
    if received > limit:
        return build_413_response(...)

return await call_next(request_with_limited_body)
```

### 校验
- 超限请求不再依赖完整 `request.body()` 才能拒绝。
- 413 响应仍使用既有统一 envelope。
- 合法请求仍可进入后续鉴权、路由、异常链路。

- [x] 路由挂载在前缀生效后仍保留 `app.modules.enabled` 的过滤行为。
